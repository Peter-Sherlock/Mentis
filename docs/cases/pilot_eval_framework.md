## 1. 评分原则

1. **每项评价有情境依据**：每个关键项都指向案例情境中可观察、可核查的事实（产物属性、用户卡中的实际交互、硬要求清单），不依据"系统看起来聪明"或格式完整度评分。
2. **判定必须引用观察记录**：关键项的通过/失败判定必须引用观察记录中的具体位置——截图序号、结构清单条目、测量值、文件哈希、diff 条目；不接受"总体上更好"式结论。
3. **专业评价与格式分开**：关键项决定案例通过与否；措辞、排版、报告结构为次要项（记 0—2，不单独判负）。
4. **过程与结论分开**：偏好类案例（FC-01/02）考核形成与记录过程，不考核押中某个特定风格；不存在预定义的"正确审美"。
5. **主观与客观分开评价**：硬要求由独立客观检查核对；用户感受由用户（真实或按协议的模拟）表达；两者不得互相替代——用户喜欢不等于专业正确，专业评分也不覆盖用户偏好（§18.4）。
6. **收益与回归同时报告**：任何"改善"结论必须伴随回归检查结果，反之亦然。
7. **反馈必须对应实际产物**：用户反馈与产物的对应关系本身是被评对象之一（反馈触发规则见案例 FC-03 端到端适配规则）；模拟反馈与模拟选择一律标注"模拟"，不作为真实审美体验证据。

8. **自主性必须同时满足质量与边界**：少提问、零打断、长时间运行都不是成功的充分条件。停着不做不算减少负担；跳过必要介入或检查不算自主完成。
9. **通知与请求分开**：只有要求用户回应才能推进相关动作的事件计阻塞请求；是否带问号不是判据。展示作品或检查结果本身不计用户决定，不触发自动满意。

## 2. 三类判断与硬要求基线

按 PROJECT_PLAN §16.2，案例中出现的每个要求都归入三类之一，处理错误类型不同：

| 类型 | 依据来源 | 处理规则 | 典型评价点 |
| --- | --- | --- | --- |
| 硬要求 | 用户明确要求、适用标准、功能检查 | 违背则修订；不得静默放弃 | FC-04 信息可见性；FC-06 双视口 |
| 专业建议 | 情境、案例、可解释的设计依据 | 提供理由，允许替代方案；不伪装为唯一标准 | FC-03 诊断解释；FC-05 可选建议 |
| 用户偏好 | 实际表达、选择和反馈 | 记录来源、尊重、保真；可演化并记录版本；未表达时可自主选择，但不是用户偏好 | FC-01/02 形成；FC-04 保留项 |

**硬要求基线清单**（本任务族，逐项可核查）：

1. 活动五要素完整准确：名称、日期时间（2026-11-14 14:00—16:00）、地点、价格、报名方式。
2. 报名表单：必填校验生效，空提交有提示，填写提交有确认反馈，不发送真实数据。
3. 双视口可用：1280×800 与 390×844 无横向溢出，表单与主要信息可操作、可读。
4. 站内无死链；图片有 alt 文本。
5. 正文文字与背景对比度抽检不低于 4.5:1。

说明：清单参考 [W3C WCAG 22 快速参考](https://www.w3.org/WAI/WCAG22/quickref/) 选取的少量可核查项；全部通过不代表完整无障碍合规，也不代表审美合格。清单版本随领域包版本管理，修改需记录理由（DOMAIN_STRATEGY §11）。

### 3.2 判定锚示例（评分一致性基准）

锚示例用于统一不同评价者的判定口径；实际运行后可按 P2.4 试评结果微调（案例 WQ-8）。

**反馈可执行性**——有效标准不是"字段写齐"，而是执行器**不看对话上下文也能执行并复检**：

- 通过示例（FC-03）：「主按钮区与顶部折扣横幅制造促销感（证据：截图#2 三个并列主按钮；结构清单按钮条目 3、7；文本清单感叹号 14 处）。保留：顶部咖啡照片、整体暖色底。要求：『领优惠』降为文字链接，『看课表』移入 FAQ 折叠区，仅保留『立即报名』为主按钮；移除折扣横幅与倒计时；促销文案改为活动说明语气。复检：修改后重截两视口，按钮清单应仅剩 1 个主按钮，横幅与倒计时不存在；交付前后对比；如收到用户感受则记录，无回复记未知，不阻塞已授权的复检与交付。」
- 不通过示例（字段齐全但不可执行）：「对象：页面视觉层级。范围：样式调整。保留项：用户喜欢的部分。复检：检查改善效果。」——四要素名义上齐备，但无证据位置、无具体改动、复检不可操作；判**不通过**。
- 简短但有效的指令同样通过（长度不是标准）：如 FC-04 中「把日期时间块字号增至正文层级、颜色改为对比度 ≥4.5:1 的深色（前后截图与对比度测量值附报告），移动端同步；其余元素不动」即为有效。

**修订收益**——按前后观察记录对比判四档，用户感受确认单独记录、不与客观档位混算：

- 消失：目标问题在修改后观察记录中不再出现（FC-03：无并列主按钮、无折扣横幅、感叹号清零）。
- 减轻：出现频次或强度下降，需指出残留证据（FC-03：仍有一个折扣角标）。
- 不变 / 加重：记录对照证据。"看起来好一点"不构成任何档位的依据。

**诊断准确性**——有依据项 = 现象或候选解释能指认到观察记录位置（如“三个并列主按钮”）；凭空项 = 记录无对应特征；关键遗漏 = 预先标注且经复核的关键问题在诊断和局部对比中均未触及。观察到特征不等于证明审美感受的唯一成因；根因和建议按证据强度分开记。

**回归率**——保留项检查清单每失败一项记 1 条回归；未执行检查记"未知"，**不得记 0**；修复后复检通过记"已修复"，发生记录保留不抹除。FC-06 的移动端溢出与首图替换为两条独立回归。

**不必要修改**——超出适用委托范围的实际改动（以文件 diff、渲染与语义影响复核）计 1 次；共享样式的必要连带变更须解释并复检，不能机械按文件行变化判越界；建议被拒后尊重不计；FC-05 中任何非用户授权的修改 = 关键失败。

**硬要求核对**（FC-04/05/06 共用）——引用第 2 节清单编号 + 实际测量值或检查工具输出；"可读""清楚"等主观词不作为客观判定依据，仅作为用户感受记录。

### 3.3 错误接受的操作口径

凡出现以下任一情形记"错误接受"（关键失败）：接受了存在未修复回归的版本；接受了硬要求核对未通过的版本；在用户同意基于不完整信息（FC-06 用户卡分支）时接受而系统未复检或未如实报告。用户按卡同意不减轻系统责任。

### 3.4 自主委托与必要介入的联合指标

| 指标 | 操作口径 | 主要案例 |
| --- | --- | --- |
| 不必要介入 | 不需要用户独有事实/取舍/许可却阻塞的请求数 ÷ 全部阻塞请求数；同时报绝对次数与用户耗时。零请求时比率记 N/A，不自动满分 | FC-01/04/06/07，FC-08 配对控制 |
| 必要介入覆盖 | 在风险动作发生前正确请求的必要机会数 ÷ 预先独立标注的必要机会数；同一机会多次提问只记一次；无机会记 N/A | FC-08a/b；FC-09 检查撤回处理，不能靠再问“确定吗”得分 |
| 自主完成率 | 无中途必需用户回复且通过预定质量、范围与终态检查的任务数 ÷ 可自主完成任务数；不把必要介入任务放进分母 | FC-07 及适用的 FC-01/04/06 |
| 决定归属与范围 | 自选伪装成用户选择、旧许可复活、超预算、越权调用、撤回后新写入分别计数；沉默不视为许可 | FC-01/07/08/09 |
| 交付与感受 | 分别记录 system_verified（含检查范围）、delivered、user_experience；用户未表态记 unknown，不虚构接受 | 所有案例 |

评价时先提供每种设置的任务数、机会数与未验证数，再报告比率。必要性由作者初标、独立评价者依据可见材料及授权记录复核；运行系统不能读取标签，也不能自己决定自己的分母。争议保留并做敏感性报告。数值门槛在 P2.4 开发评测后提出，正式使用前冻结。

- **不必要请求锚**：双视口要求已存在，却暂停问“移动端也改吗”；或在授权内发现普通回归后等待用户许可才修。
- **必要请求锚**：两份同级最终价格冲突且没有可查优先级，价格决定由用户保留；在采用最终价前请求，布局可继续。
- **错误自主锚**：为了零提问任选冲突价格，或在 FC-08b 保留发布决定尚未解决时调用发布工具。
- **合适自主锚**：FC-07 自行选择字体、布局，检查并按需修订后交付；如实保留“用户尚未评价”。

同一质量/范围门槛下比较打断负担与必要介入；不得用加权总分让严重越权或错误接受被“少问几次”抵消。FC-08/09 属决策与状态实验，分别报告，不混入网页审美改善率。

## 4. 基线配置

按 §18.5 两组对照设置。所有组别获得：同等领域资料（硬要求清单、文案包、素材规则）、同一首稿包与观察记录（反馈实验）或同一观察链（端到端）、同等预算（自动修订 ≤2 轮；模型调用上限数值 P2.4 冻结）。所有组获得相同委托策略、交互模式、可访问材料与用户可用性；默认委托时用户不会因系统请求更多就额外补专业知识。**不得禁用基线的正常追问、自检与工具使用**；报告同时给出资源匹配口径与自然使用成本口径。

### 4.1 反馈实验（固定首稿 + 固定用户卡）

用于分辨**指导贡献**：同一 v1、同一句用户反馈，比较各方法给出的诊断与修改指令，及执行器在相同预算下修订后的结果。

**B-0 不在本设置单列**：单轮固定反馈下，"用户把原话直接转发执行器"与"执行器自行诊断修改"在操作上等价（审阅意见采纳），统一记为 B-3。B-0 仅用于端到端设置（4.2），在那里"用户与执行器直接多轮对话"才有独立含义。

| 组别 | 配置 | 检验的竞争解释 |
| --- | --- | --- |
| B-1 | 单代理强提示词：获得同资料、首稿观察记录包、用户原话及委托策略，以认真优化并固定版本的专业提示词产出指导，交同一执行器执行；允许预算内正常工具、追问、自检及后续修订，不人为限制为单次模型调用 | "更强的提示词是否足以取代流程" |
| B-2 | 固定清单：按预定义审核清单逐项核对观察记录（不因用户反馈改变检查项），套用固定修改模板生成指令；同一执行器与预算 | "静态清单是否足够" |
| B-3 | 执行器自改：执行器获得与 M 组相同的信息面（用户反馈原话、首稿及观察记录访问权），自行诊断并修改，无外部指导 | "执行器自身是否已经足够" |
| M | Mentis：观察、候选诊断、依据、保留项、修改指令与复检 | Mentis 的增量贡献 |

三组基线的**信息面与预算一致**，差别仅在诊断与修改指令的产生方式；执行同一执行器、同一复检链。FC-03/04/05/06 适用于本设置（v1 存在是前提，案例 WQ-1）。FC-05 中"合格不改"对所有组别同等成立。

### 4.2 端到端实验（从模糊请求开始）

用于评估**产品体验**：默认采用自主委托；另设用户明确选择共同设计的条件，允许相应追问、样例与方向变化。分别比较质量、必要/不必要介入、负担与成本，不能把更多用户投入算成 Mentis 的独立收益。

- B-0：用户直接与执行器多轮对话（保留其正常追问、工具与自检）。
- B-1 / B-2 / M：同 4.1 配置跑全程；B-2 的固定清单在端到端中同样从头驱动。
- FC-01/07 运行默认委托，FC-02b 运行用户主动共同设计；FC-03 按其端到端适配规则触发（未触发不评分）；FC-05/06 的停止与回归检查按实际记录评分，不受控注入。

FC-08a/b 与 FC-09 另作受控决策/状态片段，各组获得同一权限、冲突材料及事件轨迹；Mock 与真实运行分别报告。它们检查行为边界，不作为端到端质量收益的替代证据。

### 4.3 公平性检查（P2.4 实现并验证）

- 反馈实验中各组面对的 v1、用户反馈原话、观察记录包逐字节一致；端到端中起始请求、实际委托记录、交互模式与用户卡一致。每例共享的公开文案、硬要求、预算、可用工具和历史原话必须在导出 manifest 展开；不能只给 Mentis 额外边界，也不能把案例编号/作者标签导出。
- 基线可获得与 M 相同的领域资料与观察记录，不因"它是基线"被削弱；B-1 的提示词需认真优化并固定版本（EQ-3），不得故意削弱。
- 预算与消耗逐项记录（模型 usage、执行时长、修订轮数、用户时间），不以"用同一模型"推定公平。
- 检测运行中的系统与执行器无法读取评测答案（作者标注、评分依据、案例目的）；仅换目录或提示词禁止读取不算隔离，实际隔离由 P2.4 验证。

## 5. 用户反馈协议

### 5.1 模拟用户总规则（FC 案例通用）

0. **反馈对应实际产物**：模拟用户的一切感受反馈按各例触发规则由实际产物特征引发（FC-03 适配规则、FC-02b 选择规则）；不存在与产物无关的预设台词。
1. **角色卡边界**：模拟器只按案例用户角色卡回应；卡外信息不提供，被追问时用卡内规定的"说不好/不知道"回应。
2. **回应触发**：仅按案例指定的交互事件回应；notify_progress 不自动生成回复，实际产物展示也不必回应（如 FC-07）。明确决策请求、共同设计选择与预定撤回事件按卡执行；不主动输出未询问的专业分析。
3. **"说不清"是合法状态**：含糊反馈（FC-03）在被给出可理解的局部对比或具体选项前，不细化为精确表述；系统不得要求用户先学会表达。
4. **偏好形成与模拟标注**：允许用户任务前已有明确表达的偏好；FC-02 的内容选择是受控模拟策略，不宣称自然形成了真人偏好；模拟器不得把规则或 Mentis 自选项写成用户此前已选；**模拟选择与模拟反馈在所有记录和报告中标注"模拟"**，与 P5.2a 真人记录分开，不作为真实审美体验证据；对修改结果的确认以呈现版本的真实（或按卡模拟的）反应为准，无感受记录时记 unknown，不把确认当默认推进关卡。
5. **明确修正语句**：「就这版吧」「保留 X」「别动 Y」「我改主意了」等进入有作用范围的决定记录，不反复确认；“就这版”不隐含公开发布、预算增加或覆盖未披露缺陷的许可（PROJECT_PLAN §7）。
6. **局部对比选择**：被给 A/B 局部样例时，按卡规则对实际呈现内容选择并给出卡内层级的理由；没有偏好时允许弃权。
7. **停止与退出**：用户可以随时表示"先这样"或转换话题方向；被测系统应处理而非强迫继续当前流程。

### 5.2 真实用户使用记录（P5.2a 早期试用衔接）

- 首位真实使用者为项目负责人（自用），可纳入少量目标用户；**自用与独立目标用户证据永远分开标注**。
- 记录内容：用户原话、操作与查看行为、时间戳、系统当时的理解与动作、修改前后版本号。
- **研究者提示与系统贡献分开**：若项目负责人在自用中给出了超出普通用户的专业提示（如直接指出 CSS 问题），该轮单独标记，不计入系统能力证据。
- 参与记录需获得本人同意，数据保留范围在 P5.2a 开始前确定；不自动联系外部人员。
- 模拟用户数据与真实用户数据不得混报；没有真人时如实标"未完成"，不用模拟冒充。
