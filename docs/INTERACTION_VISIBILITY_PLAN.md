# Mentis × Coding Agent 交互可见性与 P2.4 递进开发计划

日期：2026-09-29｜性质：**下一阶段实施计划，尚未实现**｜归属：P2.4 的评测准备段（记作 T0—T4），不新增第 23 个工作包。

> 2026-10-08 补充：本文保留 T0—T4 的原始设计与当时基线；实际状态为 T0—T3 已完成、T4 partial，见 [状态文件](DEVELOPMENT_STATUS.md)。后续改进按 [O1—O3 可观测性补强计划](OBSERVABILITY_PLAN.md) 执行：统一记录与决策回放 → 阶段/等待状态 → 本地只读运行页面。O3 补充下文“先做 CLI”的边界，聊天与执行控制仍归 P3.4。本轮只更新计划，无新增可运行功能。

## 1. 要解决的真实问题

项目负责人提出：使用 Mentis 时无法直接看见它与 Codex 如何交流，因此很难判断 Mentis 是否理解了目标、给出了合适的指令、Codex 实际做了什么，以及 Mentis 为什么接受或要求返工。这个问题既影响控制感，也影响 P2.4 对「指导到底带来了什么」的归因。

本阶段的用户目标是：**运行中能旁观，结束后能回放，并能从每一项结论返回原始指令、可观察事件与产物版本。** 展示的是模型和工具实际对外输出的内容，不声称展示不可获得的内部推理。

### 1.1 当前已核对的基线

| 入口 | 当前留下什么 | 缺什么 |
| --- | --- | --- |
| `field-start` | `runtime/field/<id>/session-log.txt` 记录 Mentis 的终端输出；完成后可生成 `usage-record.md` | Codex 子进程运行期间无逐条输出；没有可直接回放的完整委托—执行—复检时间线 |
| `collab` | `state.json`、`session.json`、`report.md` 记录目标、摘要、状态和用量 | 发送给 Codex 的确切 prompt 与执行器事件未作为该运行的独立审计材料落盘 |
| `guide-revise` | `instruction-round*.md` 保存确切修改指令，`codex-round*-events.json` 保存事件类型/状态，报告关联诊断与复检 | 事件不含可阅读的消息/工具动作内容；只有调用结束后才能看 |
| Codex CLI Adapter | 使用 `codex exec --json`，保留终态、用量、thread ID、简化事件 | `_invoke` 以 `subprocess.run(capture_output=True)` 同步等待；`streaming_to_caller` 明确为 unsupported |

P5.2a 的仓库状态仍为 `partial`，本工作区尚未找到完成的 `usage-record.md`。用户报告「P5.2a 已完成」先记为**待核对的用户报告**；T0 核对实际运行目录和原话记录后再更新完成状态。缺记录不阻止不依赖真人数据的可见性开发，也不能由开发者补造真人证据。

## 2. 产品边界与完成后的体验

一次运行应回答五个问题：

1. Mentis 依据哪版目标/约束作出了什么选择？来源是用户选择、系统自主判断，还是待决？
2. Mentis 给 Codex 发送的**确切指令**是什么？它属于哪次委托/修订？
3. Codex 报告了哪些可观察步骤、问题、最终回复与用量？哪些步骤只是开始了，哪些真的完成？
4. 作品从哪一版变到哪一版？Mentis 依据哪些观察、复检和保留项决定接受、修订、暂停或标未知？
5. 运行中断或证据缺失时，最后**可靠**状态是什么？下一步是核对、续接、等待用户决定，还是停止？

终端体验采用两个入口：`field-start`/`collab`/`guide-revise` 在**委托前**打印运行目录和简短进展；另一终端运行 `py -3.14 -m mentis trace --run <运行目录> --follow` 查看详细时间线。结束后同一命令去掉 `--follow` 回放。`Ctrl+C` 停止旁观器只停止读取，不向 Codex 发取消；真正的取消/撤回仍按现有状态契约处理。历史运行如缺事件，只展示可证实材料和「不可回放」缺口，不补写伪事件。

期望的**示意显示**（并非当前真实输出）：

```text
14:02:10 Mentis [brief v1] 从用户目标形成约束；来源：user_selected / agent_selected
14:02:11 Mentis [attempt-1] 已发送指令 → trace/prompts/attempt-1.md（sha256 …）
14:02:13 Codex  [attempt-1] turn.started
14:02:17 Codex  [attempt-1] 检查了 index.html；命令与输出摘要可展开
14:03:21 Codex  [attempt-1] turn.completed；文件变化 → workspace/index.html
14:03:29 Mentis [review] 移动视口复检：通过；保留项：通过；决定：交付
```

本阶段先做 CLI。P3.4 的聊天、预览和前后对比界面以后消费同一份追踪契约，不在这里提前开发完整前端。默认只显示可读摘要和证据链接；本地原始事件如需保存，单独标识为私有调试材料。不会展示或要求模型输出 chain-of-thought，也不把旁观器变成用户必须逐条批准的流程。

## 3. 最小技术设计

### 3.1 一个与执行器无关的追踪契约

在运行目录写入追加式 `trace/events.jsonl`，每条事件至少包含：`schema_version`、`run_id`、单调递增的 `seq`、UTC 时间、`source`、`kind`、`attempt_id`、`brief_version`、`status`、可展示摘要、关联文件路径及其 SHA-256（适用时）。`source` 区分 `user`、`mentis`、`executor`、`observer`；事件类别至少覆盖目标/授权、Mentis 决策、委托准备、执行器开始/进展/终态、观察、复检、修订、待决、撤回和运行终态。

`trace/manifest.json` 记录契约版本、运行/执行器版本、每次委托与 Codex thread 的关联、输入 prompt 和产物的哈希。确切委托文本单独保存为 `trace/prompts/<attempt_id>.md`，在**实际调用前**落盘并写哈希；若落盘失败，不发起这次委托。显示层通过哈希和 ID 关联文本、事件、版本与复检，不从时间先后猜测因果。

Codex Adapter 把原生 JSONL 映射到统一事件；映射器保留未知原生事件的类型和「未解释」状态，不静默丢弃。以后接 Claude Code 等执行器时只增加适配器映射，不改 Mentis 的追踪语义。本轮不接第二执行器。

首版性能目标只约束 Mentis 自身：收到一行完整 CLI 事件后，在正常本地磁盘条件下 **2 秒内**落盘并被 `--follow` 看见；不把 Codex 首次产生事件的等待时间算成 Mentis 延迟。展示长命令和工具输出时默认有界截断并标「已截断」，不能让无限输出撑满内存或终端。任何观察到的「用户目标与确切委托不一致」都单独登记为产品缺陷，不在评测运行中偷偷改 prompt 或评分标准。

### 3.2 采集与显示分层

- **默认可读层**：Mentis 决策理由、确切委托指令、Codex 可公开的消息、命令/工具动作的有界摘要、终态/错误、观察和复检、版本/diff 入口。每项给出来源、时间和尝试 ID。
- **私有诊断层**：可选保留 Codex 原生 JSONL 以排查映射丢失；仅在本地被 Git 忽略的 `runtime/` 保存，不自动显示或导出。原生输出可能含用户资料或命令输出，不宣称简单正则可完全脱敏。
- **导出层**：只导出经过字段白名单处理的时间线和文件哈希；不自动打包原始事件、凭据、整个工作区或用户逐字反馈。涉及私人数据的共享由用户另行决定。

追踪器只观察，不把评测答案、案例作者注释或旁观器内容回灌给受测 Mentis/Codex。写入者仍只有现有运行流程；旁观器只读。单条日志落盘后刷新，读取器容忍末尾尚未写完的一行。事件写入失败时不得显示「已完整追踪」；委托前失败则停止委托，委托期间失败则保留执行器真实状态并将**追踪完整性**标为未知，禁止把缺证据的运行判为可审计通过。

### 3.3 流式执行边界

在保持 `CodexTaskSpec` / `CodexTaskResult` 和现有锁、终态语义兼容的前提下，为 Adapter 加逐行事件回调/迭代接口。真实 CLI 路径改为逐行消费 `codex exec --json` 的 stdout，同时独立收集 stderr；不等待整个 turn 结束才写事件。原有注入式 Fake Runner 可保留兼容包装，不能因为重构让既有测试失效。

超时、进程异常、JSONL 损坏、缺 `turn.completed`、Codex 账号限额或读端中断时，继续沿用 `failed`/`unknown`/核对后续接纪律；**收到进展事件不等于任务成功**。续接创建新 attempt 段并与同一原生 thread 关联，旧段和原始失败判定不覆盖。旁观器退出不杀写入进程；若执行器实际退出但终态不明，保留锁与 `unknown`，先核对再续接。

## 4. 分段实施与退出门槛

各段按顺序推进；默认每轮只完成当前一段并交付可亲自查看的证据。估算仅作排序依据：T0 小、T1 中、T2 大、T3 中、T4 中；真实 CLI 行为可能改变工期。

| 段 | 交付 | 必须实际证明 | 不做什么 |
| --- | --- | --- | --- |
| **T0 证据与契约冻结** | 核对 P5.2a 真实记录；用本机 CLI 帮助与现有运行材料确认 JSONL 能提供的字段；冻结事件字段、状态映射、数据范围和一条历史运行的「可见/不可见」清单；更新状态 | 用户报告、仓库运行记录、开发者 Mock 分开；能指出现有一条真实运行确切指令和缺失的 Codex 内容 | 不因口头完成报告伪造运行记录；不触发付费调用 |
| **T1 事后可审计回放** | 追踪写入器、manifest、确切 prompt 归档，接入 `collab` 与 `guide-revise` 的委托/复检点；`mentis trace --run` | Fake 测试证明 ID/版本/哈希正确，历史缺资料显示「未知」；新离线运行能重建完整的 Mentis 决定→委托→执行终态→复检顺序 | 不宣称实时；不设计图形界面 |
| **T2 Codex 逐行流与实时旁观** | Adapter 流式消费原生 JSONL；`trace --follow`；`field-start` 委托前打印运行目录/旁观命令 | 延迟事件夹具证明事件在 turn 完成前可见；一次受限真实 Codex 运行证明真实流，记录首事件延迟与 CLI 版本；旁观器退出不影响执行 | 不通过轮询桌面窗口或 computer use 假装流式；不自动批准请求 |
| **T3 故障与隐私加固** | 超时/恢复/多 attempt 的连续时间线；`field-start` 异常时也收尾为失败或未知并保留日志入口；敏感字段规则、导出白名单、旧记录兼容说明 | 损坏 JSONL、截断、无终态、限额、续接、撤回、追踪写失败、现场会话异常、旁观器退出及敏感输出夹具通过；不出现假完成、事件丢失或重复判定 | 不做广泛的秘密识别承诺；不改现有权限规则 |
| **T4 真实使用核验** | 一次真实小任务的运行中旁观与事后回放、三入口链接、用户反馈原话和缺口报告 | 用户能独立回答第 2 节五个问题；每个答案能点回同一 attempt/版本的原始记录；报告运行成本与未捕获部分 | 不把看得清楚等同专业指导有效；不声称跨执行器成立 |

T2 的真实运行优先用隔离工作区的小型任务，先检查本机 Codex 登录、CLI JSONL 实际字段和可用预算；不为验证流式而重复整页生成。若真实调用受限，T2 留 `partial`，不能用 Fake 结果标为真实流已验收。T4 必须有本人查看过程后的真实反馈；无反馈时保留技术验证完成、体验验证未完成两种状态。

### 4.1 最少测试矩阵

1. **契约**：seq/时间/ID/brief 版本单调且可追溯；prompt 哈希与实际发送文本一致；旧记录缺失不被回填。
2. **流式**：两条事件之间人为延迟时首条已经落盘且可被 `--follow` 看见；慢读端不阻塞执行器；完整与部分 JSONL 行处理一致。
3. **终态**：成功、进程失败、配额错误、超时、终态缺失、续接多 attempt、待决/撤回均保留真实状态；事件数不是成功依据。
4. **边界**：执行器仅继承已过滤环境；默认展示与导出不含已知密钥字段；本地原始诊断数据不入 Git；追踪写失败不得静默通过。
5. **回归**：现有契约/协作/指导/现场使用测试通过；至少一条真实运行给出运行中与结束后的同一时间线，不把 Mock 说成真实。

| 主要风险 | 处理方式 |
| --- | --- |
| CLI JSONL 版本变化或未知 item | T0 记录本机版本和样例；映射保留未知类型并标未解释；T2 真实冒烟核对，不靠猜字段 |
| 事件已开始但未有可信终态 | 追踪和任务状态分开；保留 `unknown`、写锁、原失败段及核对路径，不以新事件覆盖旧判定 |
| 命令/输出中意外包含私人信息 | 默认本地忽略目录、有界显示和导出白名单；原始诊断文件可选且私有；敏感夹具验证已知字段，不宣称完全自动脱敏 |
| 现场会话中途异常只留下半份日志 | 对 `field-start` 增加异常收尾与关联运行目录的恢复说明；半份记录明确标不完整，不补写未发生事件 |
| 追踪改变运行速度或基线公平性 | 写入常数级、内存有界；所有比较组同一采集口径，记录开销；观察器只读、不向受测 Agent 回灌答案 |

## 5. 之后怎样进入 P2.4 强基线比较

**2026-10-01授权追加**：负责人明确委托Coding Agent整理五问并“开始下一步”。五问辅助回答不计独立本人体验，T4体验继续partial；按开发计划允许继续不依赖真人反馈的评测准备，本轮推进E1探索性材料和配置冻结。E1读隔离退出门槛保持，E2需实测通过；未复核草案不支持正式能力声明。

T0—T4 是 P2.4 的**证据基础设施**，不是 P2.4 的效果结论。其后才执行原计划的比较：

1. 冻结开发评测的页面、用户原话、观察包、案例可见性白名单和版本；作者答案不进入运行端。先覆盖「可自主完成」「需要真实修改」「必要介入」等不同路径，记录每例的人工复核状态。
2. 实现 B-0/B-1/B-2/B-3 的公平对照：同资料、工具、委托权限、用户可用性、正常自检与可比预算。固定首稿反馈实验不单列 B-0，遵守既有评价框架。
3. 对每组都采用**同一追踪契约**，使诊断、具体指令、Codex 执行、前后产物、复检、成本和用户打断可审计；追踪器只读，不成为某组额外能力。将「能看见过程/控制感」与「作品质量/指导收益」分别评分。
4. 人工评价者按可观察依据检查缺陷定位、修订收益、回归、不必要修改、必要/不必要介入、授权边界和成本；模型自评与确定性检查作为证据，不代替独立复核。无人复核只报告探索性结果。
5. 给出继续、简化或收窄的决定；样本小则报告逐案例结果与失败，不以单案例或漂亮时间线宣称 Mentis 已具备普遍专家能力。数值阈值与保留集使用时点按原计划冻结。

| 比较段 | 具体产物 | 退出门槛 |
| --- | --- | --- |
| **E1 样本与基线冻结** | 开发集案例版本、输入白名单、首稿/观察包哈希、人工复核状态、四组配置与资源/预算表；先有自主完成、真实修改、必要介入等不同情境 | 运行端读不到作者答案；每组权限与可用资料相同；未复核案例明确只用于探索 |
| **E2 对照运行** | 固定首稿反馈实验与端到端实验的 B-0/B-1/B-2/B-3 运行包；每包含 trace、产物、观察、成本与失败记录 | 同一设置内可复现配置；不禁用基线的正常自检/追问；任何中断、缺测或越界单列，不算成功 |
| **E3 独立判定** | 按评价框架逐案例评分表、证据位置、分歧与复核记录；质量、偏好、用户负担和过程可见性分开 | 不用 Mentis 自评替代人工复核；无人工复核时只作探索性结果，不报告专业能力通过率 |
| **E4 阶段决定** | 效果/回归/成本与错误接受报告，继续、简化或收窄建议，下一轮冻结阈值与开放问题 | 结论与证据强度相称；若收益不明或无收益，先解释竞争因素，不自动扩建系统 |

## 6. 完成判据与交接

可见性功能完成须同时满足：一条**真实**运行能在 Codex turn 结束前看到新事件；事后回放能找到确切委托、可观察 Codex 行为、Mentis 复检和对应产物版本；失败/未知不被粉饰；旁观与导出不改变权限和执行；用户本人能理解时间线并指出至少一处真实动作/决定的依据。随后更新 `docs/DEVELOPMENT_STATUS.md`、README 和相应进度记录，提供「看结果 / 看变化 / 看依据」及 Mock、真实、未验证清单。

**首轮开发指令（仅 T0）**：先核对 P5.2a 真实使用记录与状态差异，逐一定位 `field-start`、`collab`、`guide-revise` 和 Codex Adapter 的现有证据；冻结统一事件契约和数据边界，给出一条历史运行的材料清单及缺口。不要在 T0 改造执行器、发起真实模型/Codex 调用或把旧摘要称为完整对话。完成 T0 并满足退出门槛后，按现有一轮一段的节奏继续 T1；不为例行开发另设审批门槛。
