## 1. 项目定义与总体判断

### 1.1 一句话定义

Mentis 是代表非专业用户与执行型 Agent 持续协作的代理：帮助形成目标，决定下一步，委托工作，观察实际产物，诊断问题并给出有效修改指导。

专业性首先体现在委托、判断和反馈中。制作、编程和工具操作主要交给执行器；Mentis 仍需要足以指导与审核的领域知识，不能仅凭转述执行器总结作出专业结论。

### 1.2 产品愿景

用户给出目标与适用边界后，Mentis 默认自主调查、选择专业方案、委托、观察和修订。用户可以随时表达偏好、纠正方向或接管，但不承担逐项专业决定。共同设计是按需进入的方式，不是所有任务的必经路径。

一次默认协作可以是：接受委托 → 内部调查或小样 → 专业选择 → 执行 → 自主审核修订 → 交付。小样可供 Mentis 自检，不强制每次展示给用户选择；用户主动要求共同设计时再展开互动。

### 1.3 第一版需要验证的产品主张

在有限任务族内，Mentis 的委托和反馈能否使真实执行结果更贴近用户目标，或在同等质量下减少用户负担，并且收益能够解释额外成本？

真实集成、专业判断与产品收益分别按证据范围记录，具体已验证与未验证项见状态文件。长提示词、更多调用、执行器自己的追问和自检都是需要比较的竞争解释。

### 1.4 价值判断

- 下一步行动有目的，能够说明要减少什么不确定性或改善什么结果。
- 反馈定位到实际产物；要求具体、依据可查，并保留已满足的约束和用户喜欢的部分。
- 修改后检查是否改善及是否产生回归；合格结果可以停止，无必要修改计入失败。
- 支持人改变方向，区分硬要求、专业建议和主观偏好。
- 跨执行器保持任务语义；跨领域不自动继承专业能力声明。

## 3. 核心问题与现有概念的关系

### 3.1 要解决的四类断点

| 断点 | 常见表现 | Mentis 需要做的工作 |
| --- | --- | --- |
| 表达与目标之间 | 用户说“加 Memory”，但期望的行为不清楚 | 保留候选解释，先查上下文或可逆探索，必要时共同定义问题 |
| 目标与专业条件之间 | 没有表达权限、数据更新、失败处理等要求 | 识别条件对决策的影响，选择调查、自决、试验或必要提问 |
| 专业规格与执行之间 | 执行器自行补充假设，任务范围逐渐变化 | 版本化委托、约束范围、记录变更 |
| 执行结果与真实目标之间 | 实现能运行，但没有解决用户真正的问题 | 追踪需求覆盖，检查实际证据和用户体验 |

### 3.2 与现有 Agent 类型的区别

以下是职责侧重比较，不代表这些类别互斥，也不代表其他产品无法实现 Mentis 的能力。

| 概念 | 常见关注点 | Mentis 需要额外证明的部分 |
| --- | --- | --- |
| AI Assistant | 理解与完成用户请求 | 稳定发现用户未表达的关键条件 |
| Persona Agent | 角色表达和行为方式 | 专业判断实际受到证据、规则和门禁约束 |
| Expert Agent | 领域知识、工具与专业输出 | 不完整问题如何被定义，以及何时足以行动 |
| Planner Agent | 任务分解和步骤安排 | 规划之前的问题是否定义正确 |
| Supervisor / Meta Agent | 分配任务、协调执行器 | 委托对象、条件和结果是否符合用户目标 |
| Multi-Agent System | 多 Agent 协作 | 协作是否减少错误，而非只增加调用 |
| Agentic Workflow | 条件流程、工具调用与循环 | 每次推进是否建立在足够证据之上 |

委托和审核循环已有成熟模式；澄清必要性也已有相关研究。Mentis 的创新性需要通过机制、评测和实际收益说明，不能仅通过更换名称或增加角色来主张。[Agent 工作流参考](https://www.anthropic.com/engineering/building-effective-agents)、[澄清必要性研究](https://aclanthology.org/2025.findings-naacl.306/)

### 3.3 明确避免的退化形态

- Persona Prompt Library：主要资产只有角色提示词。
- 固定长问卷：将所有专业问题重新交给用户回答。
- 文档生成器：生成完整规格，但不负责执行和结果核对。
- Coding Agent 外壳：项目状态实际上完全寄存在执行器里。
- 多 Agent 展示系统：角色很多，但无法证明每个角色带来收益。

提示词、模板和清单都可以使用；问题在于它们是否参与可检查的决策过程，以及是否确实改善结果。

## 4. 目标用户与使用场景

### 4.1 首批用户假设

有明确想法、能够比较实际成果，但难以提供专业指导的个人创作者或小团队负责人。第一试点暂定关注小型网页的呈现与交互，不要求用户有设计或前端经验。

### 4.2 核心使用任务

用户表达“温暖一点”“看起来太乱”“我不知道哪里不对”；Mentis 帮助确认具体体验，选择制作样例或调查，查看真实产物，提出局部修改并比较前后结果。专业术语是内部工具，不是用户必须完成的输入表单。

### 4.3 用户不承担的工作

用户不必编写验收脚本、诊断代码、翻译成行业术语或为专业正确性背书。用户可以决定偏好；客观正确性和专业适用性需要对应证据。

## 5. 核心问题与研究假设

### 5.1 核心研究问题

如何在用户委托的目标和边界内自主选择下一步、指导执行端并验证结果，同时准确识别确需用户介入的决定？

### 5.2 技术问题

| 编号 | 问题 | 机制 | 验证 |
| --- | --- | --- | --- |
| T-01 | 目标形成与决策缺口 | 候选解释、样例、决策依赖 | 减少关键遗漏及无关追问 |
| T-02 | 行动选择与专业委托 | 自决、查证、试样、执行、修改、停止及必要介入 | 本轮动作与目的相符 |
| T-03 | 产物诊断与反馈转译 | 实际观察、问题定位、保留项与修改范围 | 诊断正确且指令可执行 |
| T-04 | 修订收益与收敛 | 前后对比、独立标准、成本与停止规则 | 改善目标问题、不破坏既有优点 |
| T-05 | 可组合的领域能力与执行器 | 共用内核、按需资源、观察与执行接口 | 切换时保持意图并暴露能力缺口 |

### 5.3 待验证假设

| 假设 | 预测 | 竞争解释与可能反证 |
| --- | --- | --- |
| H-01 决策相关缺口有用 | 条件处理更准确 | 同预算强提示词已足够 |
| H-02 行动策略有用 | 先小样等选择降低返工与用户负担 | 只是增加轮数或隐藏人工帮助 |
| H-03 产物依据改善反馈 | 问题定位及指令更有效 | 把同样证据给普通审核就能获得同等结果 |
| H-04 指导带来修订增益 | 同起点、同预算下结果更好 | 执行器自行改进同样有效；额外修改带来回归 |
| H-05 接口与资源组合可复用 | 换执行器或任务资源时核心少改 | 仅适合首领域，或隐藏了大量人工定制 |
| H-06 委托边界与介入策略有用 | 相近质量下减少不必要打断，重要决定不漏报 | 只是少问但误解目标、越权或隐瞒不确定性 |

字段和流程测试不能证明以上假设；必须分别报告结果及限制。

## 6. MVP 边界与首个验证领域

### 6.1 首版领域建议

负责人已明确先在**小型网页的界面与交互设计**跑通。Mentis 承担需求、方案、专业指导与验收，Coding Agent 承担实现；网页之外的装修、视频等仍为候选，不解释为当前支持要求。

理由是可以检查实际渲染、交互和局部修改，同时包含硬要求、专业建议与偏好。风险是审美没有唯一答案、评价者可能偏好特定风格、执行器本身可能已经足够好，因此需要用户反馈和公平对照。

### 6.2 首个任务族

一个本地、单页的小型展示或活动介绍页；合成文案与已有合法素材；一种主要交互；明确桌面和移动视口。可以围绕信息层级、阅读体验、氛围、响应式布局与主操作位置进行修改。

不包含真实支付、账户、生产后端、商业转化承诺、部署或对外发布。改动复杂代码的工作交给执行端，Mentis 只读取与判断有关的证据。

原文档问答 12 例保留为需求、来源、权限、版本和审核的工程回归草案，不能作为网页指导能力的充分证据。具体比较与资源组合见 [领域设计](DOMAIN_STRATEGY.md)。

### 6.3 完整 MVP 能力

| 编号 | 能力 | 最小边界 |
| --- | --- | --- |
| F-01 | 委托式协作 | 默认自主推进；用户能补充、否定、改目标、接管 |
| F-02 | 目标与条件 | 轻量版本化 brief，来源与偏好分开 |
| F-03 | 下一步与介入选择 | 自行调查、委托、小样、修改、停止；必要时才问用户 |
| F-04 | 专业委托 | 目的、上下文、范围、保留项、交付与检查 |
| F-05 | 真实执行 | 一个执行器先闭环；完整 MVP 两个执行器 |
| F-06 | 实际产物观察 | 首领域的渲染、结构和关键交互 |
| F-07 | 专业诊断 | 证据定位、依据、严重度、不确定性 |
| F-08 | 有界迭代 | 指令、修订结果、收益与回归检查 |
| F-09 | 状态与恢复 | 版本、授权、尝试和证据可追踪 |
| F-10 | 能力边界 | 资源加载不等于能力已验证 |
| F-11 | 价值评测 | 强基线、早期反馈、保留集与正式试用 |

本版重新定义 F 编号的含义，历史报告应带规划版本。完整 MVP 仍需两个真实执行器；单执行器早期闭环是研究原型，不提前宣布 MVP。

### 6.4 不做

不做通用领域市场、每个领域一套 Agent、多 Agent 自治团队、全量长期记忆、自动训练、技能自动发布、多用户 SaaS、自动部署与外部业务写入。首版不承诺视频质量评审或装修施工判断。

### 6.5 最小闭环

目标与委托范围 → 自主调查/小样/专业选择 → 真实首稿 → 实际观察 → 预算内自主修订 → 前后比较与交付。必须同时覆盖无需中途输入的任务、必须介入的决定、用户收回委托，以及合格不改和修改回归；不能用全程沉默代替能力。

### 6.6 下一版本的本地产品形态

先提供本机单用户服务，通过浏览器给目标、旁观执行、回答必要决定、反馈与纠正、查看作品及前后依据。当前只读查看器作为基础复用，完整交互归 P3.4，并保留持久化与真实恢复前置。无需域名或公共部署；本地界面与编排服务不等于模型离线推理，启动说明须明确模型/执行器连接和调用消耗。

交付顺序：O2 可靠运行状态 → C1 最小任务专业配置 → O3 一次真实核验 → 持久化/故障与恢复 → 本地浏览器任务闭环。专业效果与身份一致性分开验证，自动优化安排在可复核评价之后。[路线、资源与门槛](LOCAL_PRODUCT_ROADMAP.md)

## 7. 人机协作：关键节点介入的委托式协作

### 7.1 默认职责

用户决定目标、不能违反的条件及需要自己作出的重要取舍；Mentis 负责专业判断、执行端沟通、自主验收与预算内修订。用户可以随时插话、纠正或接管。自主程度由实际委托范围约束，不由模型自信程度决定。

当前默认方式是用户最新明确方向，更新 ADR-002；这不自动确认网页领域或授予部署、付费、外部发送权限。

### 7.2 轻量委托约定 DelegationPolicy

| 字段 | 含义 |
| --- | --- |
| goal / constraints | 当前目标及硬约束 |
| delegated_decisions | Mentis 可以自行选择的专业事项 |
| user_reserved_decisions | 用户明确保留或情境要求用户作出的重要取舍 |
| execution_scope / budget | 操作、数据、工作区、资源和修订边界 |
| intervention_triggers | 哪些实际条件触发询问或停止 |
| communication_preference | 简短进展、按需详情、共同设计等偏好 |
| source_refs / version | 约定来源、适用版本、变更与撤销记录 |

从已有请求、上下文和持续适用的授权形成约定，不用固定问卷让用户填写全部字段。“设计细节你决定”可授予专业取舍空间，不授予未说明的付费、发布等操作。缺少非关键偏好可选择合理默认并记录为 Mentis 的决定。

### 7.3 谁来解决未知

| 情况 | 默认动作 | 是否等待用户 |
| --- | --- | --- |
| 客观事实可读取 | 自行查或委托执行器调查 | 否 |
| 专业方案在已授予范围内 | 比较后自行选择，记录依据 | 否 |
| 效果未知但试错可逆且在预算内 | 做小样、测量并选择 | 否 |
| 缺少非关键偏好 | 采用可修改的默认值 | 否 |
| 结果不合格且可在范围内修正 | 指导执行器修订并复检 | 否 |
| 重要目标/事实冲突，只能由用户解决 | 说明影响并给出具体问题或选项 | 是，仅暂停受影响动作 |
| 下一动作超出授权或预算且无范围内替代 | 请求对应决定；没有答复不执行 | 是 |
| 超出专业能力、持续失败或无进展 | 停止相关自动循环，说明证据与可选下一步 | 视情况需要用户或外部专家 |

检查重要性、可查性、可逆性、预算与已有委托。模型一句“我不确定”不能单独触发询问；也不能为了少问而自行编造事实。

### 7.4 非阻塞通知与用户决定

notify_progress 仅告知动作、主要决定或结果，发出后继续已授权工作；request_decision 请求无法代决的事项，暂停受影响动作。ask_user 作为审核处置可以保留，落实为明确的 request_decision。

请求包含实际触发原因、为何不能自行解决、可理解的选择或所需事实、推荐及影响范围。相关问题合并，用户已回答的内容不重复确认。无答复或模糊答复不构成批准；未受影响的工作可以继续。

不设置每次规格、小样、首稿、修订都必须用户确认的固定关卡。符合标准时可先交付，用户体验状态记“未反馈”，不能虚构“用户满意”。

### 7.5 共同设计与撤销

用户要求比较方向时进入共同设计；说“你决定”时回到相应委托范围内自主推进。用户可在任何时刻收回某项委托。撤销后停止相关新动作，核对已经在途的执行与实际产物，明确中断能力限制；不得把新旧授权混用。

### 7.6 可见性与创造性

“看结果、看变化、看依据”始终可用，但查看入口不是强制审批。用户可以保留独特要求、提出新方向；可逆探索也可由 Mentis 自主发起。体验评价、专业判断与操作权限分开记录。

**2026-09-29 项目负责人补充决定**：阶段性交付的含义是“初稿做好，可以查看”。Mentis 仍以完成最终任务为目标；用户查看当前版本后可以指出不满意之处，Mentis 将反馈形成下一轮任务，继续与 Codex 交互，并保留版本变化与修改依据。当前轮的“已交付”不代表最终任务完成或用户满意；没有反馈时保持“未反馈”，不要求用户每轮强制确认。

## 8. 第一版架构

### 8.1 原则

一个共用协作内核；专业委托与反馈为主线；先验证最小真实闭环，再完善存储和恢复。基本版本、权限、预算、单写入与拒绝处理从第一轮真实执行就存在。

### 8.2 关系

    用户 ↔ 目标、偏好与反馈
                 ↓
    Mentis 共用决策循环
      ├─ 上下文与任务定义
      ├─ 领域资源选择与证据获取
      ├─ 下一步行动及委托
      ├─ 产物观察与诊断
      └─ 修改指导及收益检查
                 ↕
    执行器 Adapter / 观察工具 / 资料工具

### 8.3 职责

- 共用内核管理目标、决定、版本、预算、授权和循环。
- 领域资源提供概念、条件、案例、评价标准，不各自实现一套工作流。
- 观察器提供可核查产物信息；网页使用渲染、结构与交互，视频将来需要时间维度观察。
- 执行器 Adapter 传递任务、收集事件和产物，不决定专业质量。
- 模型提出语义候选；程序验证结构、来源位置、权限与状态。结构合法不保证语义正确。

### 8.4 最小实现

早期只保存一个项目的 brief、动作、真实任务身份、产物与评审版本、修订前后结果。模块先以函数或简单服务组织；不因本图出现多个名称就创建多个独立 Agent 或服务进程。

### 8.5 任务专业配置与阶段角色

复用已有资源选择、brief、策略和评估计划，增加任务专业配置快照：专业职责与适用范围、资源版本/内容哈希、目标和授权引用、可执行/可观察范围与已验证证据。配置先保存再使用；计划/诊断/委托/复检取用同一有效版本的相关部分，继续保留阶段分工与盲评的信息隔离。

用户改变目标或资源需要更新时，记录原因并生成新版本，重新核对受影响工作；未改变的适用授权继续复用。运行内可以选择不同解决办法，专业配置不能因模型自评而悄悄改写。版本绑定证明依据一致；专业水平通过真实结果和独立评价验证。[配置与后续优化边界](DOMAIN_STRATEGY.md)

## 9. 领域能力：共用内核与按需组合

### 9.1 复用单位

不为装修、导演、设计等每个职业手写完整流程。按“任务 + 产物 + 当前决策”组合少量能力资源：例如信息层级、视觉风格、网页交互可以用于不同网页业务。

资源包括适用条件、关键判断、依据、正反例、修改策略、观察需求与评价办法。知识可来自模型既有能力、已审查资料或现场检索；新增主张仍需证据，不能因检索到资料就升为专家能力。

### 9.2 按需装配

先读资源元数据，再按当前决策加载有关片段、例子或检查方式；不把所有资料塞进一次提示词。外部文档是数据，不能覆盖用户指令、执行权限或评价标准；不自动安装或运行陌生 Skill 中的代码。

### 9.3 领域切换

从目标与产物识别所需能力 → 选择资源 → 核对观察与执行工具 → 形成可用评价标准 → 记录未知 → 开始受限任务。信息不足时先问一个会改变路由的问题；允许多个能力共同参与而非强制单分类。

切换时保留用户目标、通用约束和来源；撤销不再适用的规则与未验证评审，把新资源版本绑定到新任务。用户偏好不默认跨项目迁移。

### 9.4 能力声明

分别记录“有资料”“能执行”“能观察”“已在某些任务验证”，不能合并成一个 expert=true。候选、试验、有限验证是内部范围标签；数量门槛不能代替有效证据。无观察工具时明确未验证；高后果专业结论不能靠自动拼装资源交付。

完整模型、示例、切换行为与首版边界见 [DOMAIN_STRATEGY.md](DOMAIN_STRATEGY.md)。

## 10. Knowledge Gap Detection 与介入策略

### 10.1 缺口不是待用户填写的表单

为每个影响决定的缺口记录：重要性、谁掌握信息、能否读取/试验、误判后果、可逆性、适用委托及下一动作。优先自行调查、向执行器索取证据或采用可验证假设，不把所有未知退回用户。

### 10.2 下一步选择

识别当前决定 → 检查已知信息和委托 → 提出有限候选动作 → 比较获取证据与试错成本 → 自主行动或请求必要决定 → 观察结果并更新记录。

可以直接选合理方案制作首稿；不以“必须问过问题”“必须生成多个方案”作为专业性的证明。自行选择应标记 agent_selected/provisional，而非伪装为 user_selected。

### 10.3 介入判定

只在实际影响当前目标或动作的条件下触发，例如必须由用户确定的重大冲突、无法查得的重要业务事实、未获授予的操作、预算不足或已无法有效推进。已有范围内可行的替代方案应优先考虑，不为假设中的风险发起无必要审批。

Readiness 与 Authorization 独立。专业判断已委托时不逐项确认；事实尚未知时不得靠授权代替调查。

### 10.4 停止与回复

用户决定只影响相关动作；其他工作可继续。等待超时保持待定，不静默扩大范围。用户纠正目标、收回委托或预算耗尽时更新状态，核对在途任务。

### 10.5 Unknown Unknowns

用案例、反例、异常和实际失败提高发现率；不承诺穷尽未知。遇到陌生领域先核对知识、执行与观察范围，不让低打扰目标覆盖能力边界。

## 11. 任务定义与执行端沟通

### 11.1 规格的职责

Professional Specification 是持续更新的任务定义，首轮可以是短 brief；探索、制作和修订使用同一套来源与版本规则。不要为制作一个小样先强制生成完整架构文档。

### 11.2 委托记录

| 字段 | 含义 |
| --- | --- |
| objective / purpose | 用户目标和本轮动作目的 |
| context_refs | 与当前动作有关的事实、资料和产物 |
| constraints / preserve | 硬约束、用户偏好、必须保留的部分 |
| delegation_policy_ref | 用户已委托事项、保留决定、预算及介入条件的版本引用 |
| requested_change | 本轮要做什么；允许执行器自行决定的实现细节 |
| deliverables | 返回哪些真实文件、预览或记录 |
| checks | 怎样判断结果及哪些部分尚待用户体验 |
| spec_version / baseline | 对应任务定义与产物版本 |
| execution_envelope | 工作区、授权范围、预算 |

给执行器足够上下文，同时避免用未经验证的实现细节过度指挥。执行器可以反问、指出矛盾或提议替代方案；Mentis 必须处理这些反馈。

### 11.3 修改指令

每条包括观察到的现象、证据位置、影响的目标、待核实或已核实的解释、保留项、修改要求和复检办法。不要把猜测的根因直接当事实。执行器提出专业问题时，Mentis 先查委托和证据，自行回答或调查；只有真正属于用户保留事项才转交用户。

### 11.4 变更规则

明确用户修正直接进入新版本；未决定取舍保持待定。旧产物与旧评审保留，但不能作为新版本的通过证据。用显式引用实现影响检查，不先建设知识图谱。

## 12. State 与基本对象

### 12.1 早期闭环必需

| 对象 | 最小职责 |
| --- | --- |
| Brief | 目标、范围、约束、偏好、来源与版本 |
| DelegationPolicy | 自主事项、用户保留项、授权范围、预算、介入条件与撤销 |
| InteractionRecord | notify_progress 或 request_decision、触发依据、受影响动作与回复状态 |
| CapabilityContext | 当前资源、版本、适用性和可观察范围 |
| ActionRecord | 下一步动作、目的、依据、授权与预算 |
| ExecutionAttempt | 委托、原生任务身份、状态和对应版本 |
| Artifact | 产物路径、版本/哈希、生成者及观察记录 |
| Review | 现象、证据、评价依据、不确定性与处置 |
| RevisionRecord | 修改指令、前后产物、改善及回归检查 |

名称是逻辑职责，不要求每个对象建立独立数据库表。Conversation、Requirement、Assertion、Decision、Gap、Evidence 等可先作为以上对象的字段；出现需要再拆分。

### 12.2 语义与不变量

用户陈述、系统观察、模型推断、用户偏好分开；额外区分用户选择、已委托的专业决定、暂定假设及等待用户决定。确认偏好不等于验证事实。执行 completed 不等于 accepted。不能接受过期版本、无真实产物或自报验证；未知执行状态不得盲目重发。

### 12.3 逐步持久化

早期保存可回查的任务与产物记录即可；无可靠恢复时重启后进入待核对，不能假装自动恢复。P1.3 完善 SQLite 事务、迁移与恢复；P1.4 验证离线异常，P3.3 验证真实异常。

## 13. 工作流与恢复

### 13.1 循环

定义目标与委托范围 → 选择动作 → 自主委托/调查/观察 → 诊断 → 预算内修改/接受；只在必要节点请求决定或升级。

状态可以保留 defining、ready、executing、reviewing、revising、waiting_input、accepted、failed/unknown。notify_progress 不进入 waiting_input；request_decision 只阻塞受影响动作。探索动作也绑定范围与版本，不受“必须完成最终规格”的限制。

### 13.2 最小安全与运行要求

真实调用前已有工作区身份、权限范围、预算、一个写入者、版本绑定和明确拒绝处理。提交后保存原生身份；超时先核对，不自动重复创建任务。

### 13.3 恢复与继续

沿用原生会话或明确标注的新会话续接；中断请求不等于已停止，也不等于回滚。P3.3 对进程退出、拒绝、中断、晚到结果与修改目标做真实验证。

### 13.4 有界迭代

初始实验最多两轮自动修改，按开发集调整并固定版本。无改善、重复问题、能力不足或预算耗尽时停止自动循环；符合目标时直接交付。不能为了收敛降低标准或抹去用户偏好。

## 14. Memory

项目内保存原始用户输入、当前目标与偏好、版本化决定、产物、评审和修改历史。记录哪些指导有用、哪些产生回归，但一次成功不自动升为跨领域规则。

工作状态与能力资料不同：前者属于具体项目，后者经过版本和适用性管理。切换领域仅加载相关资料；不让其他项目的用户偏好或推断静默进入当前项目。

首版不建设长期个人画像、向量记忆平台或自动自我训练。新经验先进入待复核案例，经评测后才能更新共享能力资源。

## 15. Tool、模型与多 Coding Agent 接入

### 15.1 三个独立接口

| 接口 | 面向的能力 | 例子 |
| --- | --- | --- |
| Model Gateway | 理解、提议、结构化输出和语义审核 | Mentis 自身调用的模型 |
| Tool Gateway | 有明确输入输出的单项操作 | 读取文件、查询资料、Git diff、运行检查 |
| Executor Adapter | 具有自身执行循环和会话的 Agent | Codex、第二个 Coding Agent |

直接调用模型 API，不等于获得完整 Coding Agent 的文件操作、执行循环、会话和权限机制。三种接口可以使用同一厂商，但不能混成同一个抽象。

### 15.2 工具的最小契约

每个工具声明输入输出 Schema、读写属性、资源范围、所需权限、超时、输出大小限制和是否可安全重试。外部写入操作还需要说明幂等性和可逆性。

第一版工具优先提供：工作区读取、受限检索、Git 状态与 diff、受控测试执行、产物读取。网络搜索按任务需要启用；搜索结果只作为外部材料，不拥有修改系统规则的权限。

### 15.3 执行器的逻辑契约

以下是 Mentis 拟定义的行为，不是厂商现有 API 名称：

| 行为 | 目的 |
| --- | --- |
| describe_capabilities | 返回当前版本已支持、已验证和未知的能力 |
| start_task | 在明确工作区和规格版本下开始任务 |
| observe_task | 获取状态、进度或最终结果；可为流式或轮询 |
| continue_task | 在现有任务上下文中提交修订，可选 |
| answer_request | 回答执行器产生的澄清或审批，可选 |
| interrupt_task | 请求中断并报告是否确认停止，可选 |
| recover_task | 程序重启后定位原会话和运行状态，可选 |
| collect_artifacts | 收集或定位变更、日志和其他产物 |

缺失可选能力时，Adapter 返回明确的不支持；工作流选择受限模式，不伪造成功。

### 15.4 能力声明

至少覆盖：流式事件、同会话继续、重启恢复、状态查询、中断、运行中追加输入、审批往返、结构化结果、使用量统计、工作目录限制和权限粒度。

每项记录 native、emulated、unsupported 或 unknown，以及验证版本和证据。通过重发上下文开启新任务属于 emulated continuation，不能标为原生恢复。

### 15.5 统一事件

Mentis 层建议归一化为 task_started、progress、input_required、approval_required、artifact_available、task_completed、task_failed、task_interrupted。

事件携带 task_id、attempt_id、native_event_id 或本地序号、时间、规格版本及 payload。保留经过脱敏的厂商原始事件用于排障，核心流程不直接依赖厂商字段。

消息丢失和恢复时，以可核对的执行状态和产物为准；不能仅通过自然语言中出现“完成”判定终态。

### 15.6 第一执行器：Codex

建议先评估官方 SDK。官方文档目前列出 TypeScript 与 Python 接口，支持本地会话的创建和继续；Python SDK 底层使用本地 App Server。文档确认不代表本机已经兼容或完成认证。[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)

如果 SDK 暴露的功能不能满足真实的中途交互需求，再评估 App Server。其双向协议提供更细的会话与事件控制；官方仍提示 App Server 命令的实验性状态，WebSocket 也有单独限制。首个实验优先本地进程通信，固定版本并做协议验证。[App Server](https://learn.chatgpt.com/docs/app-server)、[迁移及状态说明](https://learn.chatgpt.com/docs/mcp-server)

旧的 codex mcp-server 已被移除。Codex 调用外部 MCP 工具与“把 Codex 本身作为 MCP Server”是两个不同方向，不使用已移除入口设计新系统。[官方说明](https://learn.chatgpt.com/docs/mcp-server)

### 15.7 第二执行器候选：Claude Agent SDK

官方说明提供 Python / TypeScript 接口，将 Claude Code 的 Agent 循环和工具能力嵌入应用。因此它可以作为不同执行运行时的验证候选，而不仅是把 Mentis 的底层模型换成 Claude。[Agent SDK 概览](https://code.claude.com/docs/en/agent-sdk/overview)

实际纳入第二执行器前，需要单独核对：所选版本、Windows 运行要求、会话与审批映射、认证方式、使用条款、成本和本机实测结果。此阶段不假定可直接复用任何桌面产品的登录态或订阅额度。

如果该候选受环境或接口限制，按同样的能力条件选择其他真实 Coding Agent；替换选择需要记录理由，不以 Mock 冒充第二执行器。

### 15.8 标准协议的地位

ACP 致力于标准化编辑器与 Coding Agent 的通信，并通过版本和能力协商区分支持范围。未来可作为某些 Adapter 的接入路径；采用协议不意味着所有执行器具备相同功能。[ACP 官方仓库](https://github.com/agentclientprotocol/agent-client-protocol)

MCP 用于工具和上下文接入。用户提到的 A2A、Social Harness、AAP 等长期方向在本稿中只保留扩展位置，尚未指定具体协议、版本或产品依赖。

Mentis 的规格、判断和验收语义由自身核心负责；传输协议只解决其中一部分通信问题。

### 15.9 为什么不以 Computer Use 为主要集成方式

SDK、结构化 CLI 或协议可以直接取得事件与状态。界面自动化还需处理窗口、焦点、截图和界面变化，会增加与专业能力无关的失败来源。

Computer Use 可以作为无编程接口工具的后续补充能力；首版不通过点击 Codex 或其他 Agent 的聊天窗口完成主流程。

## 16. Professional Review 与指导质量

### 16.1 观察真实产物

网页试点同时需要渲染画面、结构与关键交互；截图只能证明当时视口的呈现，不能证明所有交互、响应式或无障碍要求。无法取得观察结果时记录未验证，不能只读代码或执行端总结就判断视觉质量。

### 16.2 三类判断

| 类型 | 依据 | 处理 |
| --- | --- | --- |
| 硬要求 | 用户明确要求、适用标准、功能检查 | 违背则修订 |
| 专业建议 | 情境、案例、可解释的设计依据 | 提供理由，允许替代方案 |
| 用户偏好 | 实际选择和反馈 | 尊重偏好，不伪装为唯一标准 |

### 16.3 诊断—指导—复检

先定位现象，再检验解释；修改指令包含保留项和复检方式。比较前后产物，检查目标改善、已满足要求的回归及新增问题。没有问题时接受，不为展示能力刻意修改。

### 16.4 处置

accept、revise、ask_user、escalate 继续保留。ask_user 必须说明实际介入条件；委托范围内的常规修订无需用户重新确认。用户表达不满意时可以重新探索，而不一定只修补当前方案。新目标引起新版本；同一目标下比较修订收益，不混用新旧标准。

### 16.5 证据独立性

执行器可编写辅助测试，但不能定义全部成功条件。评审可以使用同一底层模型；独立性来自真实观察、预先标准、受测系统不可见的保留评价和人工复核，不能靠角色名称保证。

### 16.6 交付入口

真实任务的每次交付至少提供三个可检查入口：**看结果**（当前作品在哪里，能否直接打开和操作）、**看变化**（上一版与这一版有什么不同，哪些部分保留）、**看依据**（哪句话触发修改、观察到了什么证据、向执行器发出了什么指令、复检结果是什么）。这些外部记录帮助用户检查系统有没有误解目标、越界修改或虚报完成，不需要用户阅读模型内部推理。人工制作的样例、Mock 演示与真实 Mentis 运行必须分别标注。用户可随时查看，不要求每次查看、回应或批准才推进。开发过程中的每轮交付要求见 AGENTS.md 第 6 节。

### 16.7 评估计划先行与可验证性（2026-10-02，ADR-008）

评估标准在首次委托前形成，作为版本化的评估计划落盘，不在看到产物后现场生成。计划只组装、实例化四层来源的标准：内核、用户、领域资源、任务实例；Mentis 推导的条目标为 provisional，不阻塞交付。每个维度写明检查方式（确定性检查 / 盲比 / 用户判断 / 无法验证）。只有前两类候选可以进入自主修订；用户判断类以非阻塞选项告知用户；无法验证的不修订，也不授予 improved。模型复检用前后盲比、正反两序，不一致记为 unknown。一个领域里哪些维度给得出检查方式，决定了 Mentis 在该领域是自主验收、辅助判断，还是明确不可见（DOMAIN_STRATEGY §7—§8）。这是设计决定，实施与证据见 P2.4-V1/V2。

## 17. 权限、可靠性与运行边界

### 17.1 最小执行边界

第一版在独立测试工作区执行写入，以当前 Git 提交和初始工作区指纹记录基线。工作区存在未登记改动时先检查来源，不覆盖用户进行中的工作。

分别记录只读探索、工作区内变更、安装依赖、联网和外部写入的权限范围；依据现有任务授权判断，不把分类管理变成每次操作前都请求确认。任务描述中的 allowed_paths 是约束说明，只有运行时沙箱或相应权限机制才能实际落实边界；事后 diff 检查不能替代访问控制。

### 17.2 本地与外部数据

- 默认本地保存状态与产物，但调用外部模型或 Coding Agent 时仍可能传输上下文。
- 工具网关负责最小必要上下文；不把整个项目、凭据和无关文件默认发给服务。
- 首版使用合成或明确授权的非敏感案例。
- 日志不记录明文密钥；认证交给对应运行时或本地秘密存储。
- 外部文档、代码注释和执行器消息属于任务材料，不能改变系统权限或冒充用户授权。

### 17.3 失败处理

| 失败 | 处理方式 |
| --- | --- |
| 结构化模型输出不合法 | 有界修复；仍失败则保留原输入并报告 |
| 关键资料不可获得 | 记录缺口，缩小下一行动或请求必要输入 |
| 执行器拒绝权限 | 停止相关动作，解释所需权限，不换通道绕过 |
| 进程退出或网络中断 | 恢复记录、查询状态、核对工作区；不盲目重跑 |
| 测试环境失败 | 区分环境问题与项目缺陷，未运行测试不能计为通过 |
| 用户改目标 | 更新规格，失效相关门禁和审核，处理旧执行 |
| 审核无法取得证据 | 标记未验证，不自动交付为已接受 |
| 预算耗尽 | 停止新增工作，保存状态并报告已完成与未完成部分 |

### 17.4 并发与边界

第一版允许只读查询并行，但一个工作区只允许一个写入任务。未来跨执行器并发必须有隔离工作区、合并策略与冲突处理，不能直接共享同一目录写文件。

有限范围内未发生越界只证明该范围的测试结果，不能宣称生产安全认证或全面安全性。

## 18. Evaluation：指导是否带来价值

### 18.1 证据层级

E-1 是契约和离线流程；E-2 是真实模型的观察与诊断；E-3 是真实执行与修订；E-4 是用户体验和独立效果比较。不同证据不能互相冒充。

### 18.2 两类实验

- 反馈实验：固定目标和同一首稿，让不同方法给出指导，执行器在相同预算下修改，比较结果。
- 端到端实验：默认从目标和委托开始，包含中途无需用户输入的路径；关键节点才请求决定。另保留用户主动共同设计的路径，分别比较质量、打断、偏好和成本。

前者用于分辨指导贡献，后者用于评估产品体验。两类分开报告。

### 18.3 数据与可见性

作者资料、用户角色资料、运行输入和评价答案分开。运行中的 Mentis 与执行器只见用户实际提供的信息、授权工作区和检索材料；预期行为、允许方案集合、根因标签、评分依据、案例名称中的答案提示均不可直接输入。

初始 12 例已修正文档可见性说明，但尚无隔离实现或运行证据。P0.4 定义新案例视图；P2.4 验证实际隔离。独立评测身份/挂载范围等技术隔离需实际测试，仅换目录或提示词禁止读取不算隔离。

### 18.4 人工复核

AI 案例标为 pending_human；开发探索允许使用草案但不作专业结论。正式评测由具备相关能力的人工复核者检查要求、证据及评分标准，保存分歧。用户喜欢不等于专业正确，专业评分也不覆盖用户偏好。

### 18.5 对照

| 组别 | 配置 |
| --- | --- |
| B-0 | 仅端到端：用户直接与 Coding Agent 交互，保留正常追问、工具和自检 |
| B-1 | 同模型/资料/工具/执行器的强专业提示词 |
| B-2 | 固定清单、固定审核步骤 |
| B-3 | 同一首稿与用户反馈，由执行器自行诊断并改进 |
| M | Mentis 的动态委托、观察、诊断和指导 |

反馈实验中 B-0 与 B-3 合并，不重复单列。各组获得同等资料、委托范围、用户可用性和可比预算；B-1 允许预算内工具与自检，不人为限制为一次调用。资源匹配与自然使用成本分别报告。不能禁用基线的正常能力，或把更多调用带来的收益全部归因于架构。

### 18.6 主要指标

| 指标 | 操作口径 |
| --- | --- |
| 诊断准确性 | 指出的真实问题、遗漏问题、无依据问题，按独立复核计算 |
| 反馈可执行性 | 能否明确对象、范围、保留项和检查方法；格式完整不能代替有效性 |
| 修订收益 | 相同目标与首稿下，目标问题改善与整体结果变化 |
| 回归率 | 原已满足要求或应保留部分被破坏 |
| 不必要修改 | 合格产物被无依据否定或反复调整 |
| 偏好保真 | 用户明确选择在修改与切换中保留；目标变更另记 |
| 终态质量与错误接受 | 独立验收及目标用户评价，分别报告 |
| 用户负担与成本 | 时间、轮数、理解难度、执行/模型消耗 |
| 不必要介入率 | 不需要用户却阻塞求答的请求数 / 全部请求数；无请求时记不适用，并报告每任务打断数 |
| 必要介入覆盖与时机 | 已识别并在受影响动作前处理的必要节点 / 标注必要节点；漏报单列 |
| 委托内自主完成率 | 无需额外用户决策且满足独立质量/范围要求的任务 / 标注可自主完成任务 |
| 决策归属与撤销一致性 | agent_selected 不冒充 user_selected；委托收回后不继续受影响动作 |

过程指标与质量、回归、偏好及越权联合报告，不能靠所有任务都不问或都停止优化分数。专业验收可由系统完成，用户未回复时体验评价保持 unknown，不强制补一轮确认。

### 18.7 数据规模与冻结

P0.4 先设计少量反馈链案例，不先批量生产 80 例。原“20 场景族 × 4 变体”只作为历史估算；在 P2.4 根据成本、差异和评分稳定性设计正式规模，不能用固定数量保证统计充分性。

同源、同模板变体按族放在同一侧；保留集调参后不再是未见测试。正式比较前冻结版本、预算、阈值、主要指标和分析方法。

### 18.8 用户试用前移

P5.2a 在首个真实闭环后开展早期形成性试用，可以先由项目负责人实际使用；清楚标记与独立目标用户的区别。没有参与者就报告未完成，不能用模型扮演替代真人证据。P5.2 保留后期独立目标用户试用，原 6—10 人仅为招募规模建议，非效果证明。

### 18.9 评价方法

主观比较尽量隐藏系统来源并随机左右顺序；硬要求独立检查；报告评价者分歧。模型裁判仅辅助整理与评分，不单独自证。记录失败、超时、人工接管，不只汇报成功修订。多次运行按预算开展，重复次数不构成充分样本保证。

### 18.10 价值门槛

保留 ADR-005 的预先冻结、合理成本、同等质量下降低负担或减少关键错误原则。本轮补充自主完成、必要/不必要介入及撤回处理，与修订收益、回归和不必要修改联合评价，最终主指标和阈值仍待开发数据支持后、保留集之前确定。无法证明有收益可收窄或简化机制；不能把接通两个执行器当作价值已成立。

## 20. 技术选型与预算

继续采用已记录的本地单用户、Python 核心、SQLite 持久化、轻量 Web 方向。网页试点的交付物前端技术与 Mentis 自身界面分开，避免把试验载体做成大型平台。

首执行器仍以 Codex 为候选，第二候选 Claude Code 对应官方可编程运行时。接口、认证、版本、价格与本机支持在接入包核对；不在本轮锁定 SDK 版本或承诺复用订阅。SDK/协议/CLI 优先于桌面操作。

早期 CLI 配合本地网页预览与产物链接就能试验，不能把“CLI 对话”解释为“只能看文本”。观察工具应验证实际渲染、截图和关键操作的能力。

Windows 验证中文及空格路径、UTF-8、进程与文件锁、超时和退出。记录模型 usage、执行时长、用户时间、修订次数与人工帮助；费用未知时不编造金额。

## 21. Git、工程结构与文档管理

### 21.1 起点与当前状态入口

规划开始时，Mentis 目录为空，且不属于 Git 仓库。总体规划阶段只创建本规划文档；后续补充了开发计划、状态入口和根目录 AGENTS.md，仍未初始化仓库、安装依赖或创建远程仓库。之后的状态以 [当前开发状态](DEVELOPMENT_STATUS.md)及实际检查为准。

### 21.2 开始实现时的顺序

1. 检查现行路线与状态入口，按 P1.1 建立工程起点；后续顺序不按包编号排序。
2. 初始化本地 Git，先纳入规划、忽略规则和工程约定，建立可回溯基线。
3. 凭据、本地数据库、执行日志、临时工作区和用户数据默认不入库。
4. 每阶段使用明确的小步提交，关联任务、检查结果及文档更新。
5. 在需要时创建远程仓库和发布流程；本地 Git 建立不等于授权公开发布。

### 21.3 最小工程结构，按需增长

    Mentis/
      docs/                   当前规划、决定与案例
      src/mentis/             起初只有入口和当前闭环必需代码
      resources/              小型能力元数据、资料与案例引用
      tests/                  当前不变量及关键行为
      runtime/                默认忽略；项目状态与真实产物

以上不是预先生成目录的清单。P1.1 只建运行入口；对象、决策循环、观察工具、Adapter、存储与界面在相应包出现时再拆文件。资源按判断能力组合，不按所有职业建立空文件夹。

隐藏评测数据由独立评测进程持有，并通过独立账户、沙箱挂载范围或经过验证的读取限制隔离。只放在另一个目录、只更名为 holdout，或仅在提示词中要求不读，都不能证明隔离成立。需检查运行中的 Mentis 和执行器均无法直接读取答案与评分条件。

### 21.4 测试原则

必要测试集中在状态、权限、版本、恢复、协议映射和关键用户结果。不要为每个文案或低影响格式变化建立重复测试。

真实接口检查按需求运行，记录成本和版本。Mock 主要用于可重复故障分支；真实集成测试用于证明实际接口；用户任务评测用于判断专业价值。

### 21.5 需要持续维护的文档

- 项目规划：范围与阶段。
- 架构说明：真实模块、数据与控制流程。
- ADR：重要取舍、考虑过的替代方案和重评条件。

## 附录 A：历史文档问答协作案例（工程回归用途）

本例用于检查规划是否连贯，所有角色发言和执行结果均为设计示例，不是真实运行记录。

### A.1 用户起始表达

“我想做一个能回答团队文档问题的工具，最好回答时能告诉我依据。”

Mentis 提取候选目标：帮助团队依据文档获取信息；引用可能是关键要求。多人使用、文档范围和问题类型尚未确定。

### A.2 先处理会改变方案的条件

Mentis 先读取用户授权的项目说明，发现已有 Markdown 文档加载器；不再让用户回答文档解析库等可以自行调查的问题。

Mentis 询问：“不同同事能看的文档是否相同？这会影响哪些文档能够被检索和引用。”

用户说明所有试用者暂时看同一批公开样例，未来可能增加限制。

系统记录：当前范围为公开样例；未来权限隔离是后续事项，不把它自动加入本轮企业级功能清单。

### A.3 人参与创造性定义

Mentis 提出直接回答加引用的候选方案。用户补充：“有些文档说法不一样，我更想看到差异，不希望它直接替我选一个。”

这产生一个新的产品决定：发生来源冲突时展示差异及出处；不能静默合并成一个确定答案。

系统可以提供两个界面样例，让用户比较解释方式；先将用户选择转成验收要求，再委托实现。

### A.4 规格示例

| 要求 | 来源 | 验收 |
| --- | --- | --- |
| R-01：答案提供可定位引用 | 用户起始请求，经例子澄清 | 给定问题返回文档 ID 和对应文本位置 |
| R-02：证据不足时明确说明 | 对失败行为的后续决定 | 无相关证据的问题不生成无依据结论 |
| R-03：冲突来源分开展示 | 用户主动提出的独特要求 | 冲突样例保留两种说法及出处 |
| R-04：本轮只处理公开样例 | 当前范围决定 | 不连接真实内部文档或对外部署 |

### A.5 委托与审核

Mentis 在隔离工作区把规格 v1 交给执行器 A。执行器报告完成。

审核发现普通问题有引用，但冲突样例仍被合并。系统记录 R-03 失败，附上输入、输出和相关代码位置，生成修订任务。

修订后再次检查。如果样例通过但缺少真实用户体验反馈，交付时分别写明“已通过指定样例验证”和“尚待体验确认”。

### A.6 用户改变要求

用户希望新增文档删除功能。Mentis 形成规格 v2，保留 v1 成果，补充删除后的检索和引用行为要求。旧测试通过不代表 v2 已验收。

如果此时换用执行器 B，Mentis 提供规格 v2、相关决定、代码基线和未完成项。无需迁移执行器 A 的全部内部对话；也不承诺复原其未显式记录的内部状态。

### A.7 对应的失败案例

- 用户未说明真实文档权限，系统直接将所有文档开放：错误推进。
- 用户已明确只有公开样例，系统仍坚持完成企业多租户问卷：不必要阻塞。
- 用户提出冲突展示，系统改写成“选择最可信答案”：偏好丢失。
- 执行器声称测试通过，但没有日志且未运行检查：证据不足。
- 新规格已生效，系统仍接受旧版本结果：版本门禁失败。
