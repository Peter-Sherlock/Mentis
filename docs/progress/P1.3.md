# P1.3 持久化与状态恢复（2026-10-08）

性质：按[开发计划 §P1.3](../DEVELOPMENT_PLAN.md) 完善可靠持久化——SQLite 保存任务规范状态与关键状态事件，落实事务、数据库版本和迁移；重启跨进程真实恢复。本轮为**离线验证轮**：真实模型/执行器调用 0；跨进程恢复用**全新 Python 进程**验证；执行器侧全部为 Fake（与真实 Codex 委托分开记账）。前置：O3 已完成（基线 `3bea487` = 标签 `p2.4-o3-baseline`）。

## 1. 先核对的关系（不另建平行实现）

- `TaskSession`（mentis/session.py）：规范状态机——briefs/policies/authorizations/interactions/attempts/artifacts/reviews/revisions/user_feedback，全部不变量（版本门禁、授权、待决阻塞）在操作层强制。
- `collab`：`_persist` 落盘 `session.json`（TaskSession JSON 导出，p1.2 契约版本校验）+ `state.json`（运行级元数据）；`collaboration_from_state`→`load_state` 从两个 JSON 恢复。
- 追踪记录：`trace/events.jsonl` + sidecars = 证据事实；`professional-config/`、`evaluation-plan/` = 配置/计划文件（自带哈希核验，C1）。
- 结论：**新增存储，不动状态机语义**——库与 JSON 导出共用 `persist.py` 同一套映射（新增 `session_rows`），不建第二套转换。

## 2. 职责边界（本包退出条件：摘要不成为第二事实来源）

| 层 | 职责 |
| --- | --- |
| **任务库** `state.sqlite3`（`mentis-task-store/1`，新模块 mentis/store.py） | 任务规范状态 + 关键状态事件（task.* 转换记录，按内容哈希去重）的事实记录；**恢复以此为准** |
| **原始证据文件**（trace/、配置/计划文件、workspace 产物） | 证据事实来源；库只存**引用与内容哈希**，不复制正文 |
| **JSON 导出**（session.json/state.json） | 人读与既有只读入口用的导出；与库不一致时**以库为准**并留痕（`restore_notes`），不反向改写库 |
| **报告/页面/状态视图** | 投影；缺证据标缺口，不反推事实 |

## 3. 实现

- **事务**：`save_task_state` 单事务（BEGIN IMMEDIATE）全量同步九张规范表 + meta；规范化失败（如不可序列化对象）与事务中失败都转 `StoreError` 并整体回滚——**不留半套规范状态**（测试：毒对象注入后库保持先前完整摘要）。同一状态重复保存幂等（`changed=False`）。
- **库版本与迁移**：`meta.db_version` + `PRAGMA user_version`；版本高于支持范围显式报错（不降级、不重建）；迁移逐版本执行，**迁移前整库备份**（`state.sqlite3.bak-v<版>-<时刻>`），失败还原备份并抛错（原库未被改动）；迁移框架带测试（失败回滚 + 成功推进 + 幂等）。
- **恢复**（`restore_task_state`）：quick_check 完整性 → 重建 TaskSession（沿用 p1.2 映射，id 计数续排）→ **摘要重算一致**（锚定库内存档的 meta 原文，结构演化不破坏校验）→ **配置/计划绑定哈希与现文件核对**。任一不符 → `StoreError`（进入待核对），不静默新建任务、不悄悄换用最新资源。
- **损坏恢复办法**（错误消息内注明）：从 `.bak-v*` 备份还原；或由 JSON 导出重新导入（`import_json_run`——库损坏时先**隔离留存**坏文件 `.corrupt-<时刻>` 再重建，不就地删除）。
- **关键状态事件**：`record_task_event`（task.answer_applied / task.stale_reply_archived / task.answer_duplicate_skipped）按内容哈希去重；任务库不存在时**不创建库**（避免遗留 JSON 运行恢复中途留下空库遮蔽导出）。
- **通知不复活为等待**：恢复按 kind 原样重建；只有无回答的 `request_decision` 是等待（测试断言）。

## 4. 恢复内容与不变量（对照包指令逐项）

| 恢复对象 | 落点 | 验证 |
| --- | --- | --- |
| 目标与 brief | briefs 表（版本化） | 往返摘要一致；计数续排（新 id 不复用） |
| 委托策略与撤回状态 | policies / authorizations（含 revoked/superseded 状态） | 撤回后恢复：全部 revoked、`dispatch` 抛 UnauthorizedAction、零新增委托 |
| 专业配置与评估计划绑定 | meta 绑定事实（文件名+内容 sha256） | v2 资源出现仍绑 v1；v1 被篡改 → 恢复显式失败（不悄悄换最新） |
| 待决定事项 | interactions（kind/blocking_action/回答字段 + **请求/回答时 brief 版本**） | 未决恢复后仍阻塞依赖动作；通知不复活为等待 |
| 执行尝试与原生任务标识 | attempts（status 原样，含 unknown；native_task_id） | unknown 恢复后仍需核对；恢复零外部委托 |
| 产物版本 | artifacts（路径+sha256+producer） | 往返哈希一致 |
| 已用预算 | meta（model_usage 记录值）+ attempts/repairs_used 规范行 + `budget_registered` 透传 | status 分账继续可用；剩余额度缺失不给（沿用 O2 规则） |

**去重与版本校验**（会话层 + 库层双防线）：
- 已回答的请求再答 → `InvalidInteraction`（session 层拒绝，不覆写）；collab/guidance 续办对重复回答**幂等跳过**，重放同一回答零新增外部委托（测试）。
- **旧版本回复不批准新范围**：请求/回答记录各自 brief 版本；续办时若请求所属 brief 已被替代 → 回答只入档（`task.stale_reply_archived`），apply-answers 委托不发起、方向回答不触发构建，要求按当前目标重新确认（测试）。未知归属（历史运行无版本字段）不猜测，按可回答处理并如实说明。
- **unknown 不重发**：恢复不自动 confirm、不自动委托；unknown 只能经人工核对 `confirm_outcome` 转换（既有语义，回归保持）。
- **单写入者**：单事务 + `busy_timeout=5s`；meta 记录最后写入者 pid。多进程并发写入依赖 SQLite 锁排队/报错，不做分布式协调（边界：不承诺"恰好一次执行"）。

## 5. 接线（真实链路，非演示平行实现）

- `collab._persist`：每次落盘先写任务库（失败不阻断收尾，`state.json.task_db.state="failed:…"` 如实留痕 + 通知），再写 JSON 导出。
- `collab.load_state`：`state.sqlite3` 存在 → 库为规范态（损坏/版本不符**显式报错**，不静默降级到可能陈旧的导出）；无库（历史运行）→ JSON 导出路径（恢复说明进 `restore_notes`，下次落盘自动建库完成迁移）。
- `collab-resume` / `guide-resume` 的回答路径：幂等跳过 + 旧版本回复门控（collab 拦截续办委托；guidance 拦截重复推进并如实通知）。
- `mentis status`（共用 `render_state_markdown`）：新增「任务库」行——存在（schema/版本/摘要/导出不一致标注）或未创建（历史运行迁移路径说明）。
