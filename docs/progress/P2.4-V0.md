# P2.4-V0 评估先行规划修订

日期：2026-10-02。性质：**纯文档轮，没有新增可运行功能，没有调用模型或执行器。** 状态：completed（文档修订）；V1、V2 均为 not_started。

## 起因与授权

负责人读了两篇 Anthropic 文章后提出两个问题：Mentis 评估一个结果和生成它一样难时怎么办？作为通用的专家切换 Agent，怎样确定评判基准？讨论后负责人又提出：规划者不应只规划执行，开局就应规划好评估的维度和方法。随后负责人指示"请帮我调整开发计划，然后给我下一步开发的 prompt"。本轮据此修订规划，范围仅限文档。

## 起始事实（读代码确认）

- `mentis/guidance.py` 的 `run_model_review`：复查模型拿到修改前的诊断清单和修改后的观察，判断"问题是否仍存在"；没有前后对照，与诊断同源（deepseek-flash）。
- `mentis/collab.py` 的 `_adjudicate_candidates`：不属于保持现状、溢出、保留项三类的候选，默认 `adopt`。
- `mentis/collab.py` 的 `_expected_values`：硬编码试点事实"手冲 / 2026-11-14 / 梧桐街 / ¥99"。
- `mentis/contracts.py` 的 `Brief` 只有 objective、constraints、preferences，没有评估计划对象；`CapabilityContext` 有观察能力与 unknown_needs，没有逐维度的检查方式。
- 真实运行 `20261001_020003-73ca`："暖色加深"被采纳，修改 1 行，同源复查判 `resolved=[d1]`，最终 `DELIVERED improved`。
- `resources/web_pilot/*.md` 的规则已经带有 hard_constraint / guideline / preference / hypothesis 性质，可以直接作为领域层来源。

## 关键取舍

- **V1/V2 排在 E1 公平运行器之前，而不是之后。** 理由是不在一个已知存在盖章问题的 M 版本上花真实对照预算，同时避免运行器因 M 的记录形态变化而返工。代价是 E2 推迟两步。旧版行为通过现有真实运行和 P5.1 消融保留对照，不另加开关。
- **不新增工作包、不新增 Agent。** 评估计划是 Mentis 内核流程中的一步。
- **协商式 sprint contract（执行器先提案）暂不做。** V1 只由 Mentis 从计划派生验收项写入指令。
- **E1 v1 冻结材料不动。** M 方法描述在运行器步骤另存为新版本。B-1 是否加"评估先行"变体在 E2 前决定。

## 下一步：V1 开发指令（可直接复制给下一轮 Agent）

> 请接手 Mentis，执行 **P2.4-V1「评估计划先行」**，只做这一步。
>
> **先读：** AGENTS.md、docs/DEVELOPMENT_STATUS.md、docs/DEVELOPMENT_PLAN.md（P2.4 节的 V1 行）、docs/decisions/ADR-008.md、docs/progress/P2.4-V0.md；再读 PROJECT_PLAN §16 与 DOMAIN_STRATEGY §6—§8；检查 Git 状态。开始前用几句话说明本轮工作包、目标、交付和验收方式。
>
> **要解决的已观察问题：**
> 1. 硬要求检查写死在代码里：`mentis/collab.py` 的 `_expected_values` 硬编码了试点的"手冲 / 2026-11-14 / 梧桐街 / ¥99"，换一个任务即失效，标准来源也无法追踪。
> 2. 专业标准只在看到产物后由诊断现场生成，复检没有事先冻结的依据。
> 3. 用户在委托前看不到"Mentis 打算怎样判断成功"。
>
> **本轮目标：** 每个 collab 任务在首次委托执行器之前，形成一份版本化的评估计划（EvaluationPlan），先落盘、算哈希，再委托。此后的硬要求检查读这份计划，不再读硬编码的值。用户体验上的变化是：给出目标后，在首稿出来之前就能看到 Mentis 将如何判断成功、每条依据来自哪里。
>
> **必须满足：**
> - **只组装，不发明。** 条目来自四层：
>   - 内核：与领域无关的固定标准，包括忠实于意图、约束与保留项不被破坏、无回归、不越界、未验证不宣称已验证。
>   - 用户：brief 的约束与偏好，沿用其 Provenance / source_ref。
>   - 领域：已加载的 `resources/web_pilot` 规则，带 id@版本与 hard_constraint / guideline / preference / hypothesis 性质。
>   - 任务实例：从任务素材推导出的具体验收项，例如活动事实。
>
>   每条都标注来源。Mentis 或模型推导的条目标 agent_selected + provisional，不能阻塞交付；hypothesis 规则不阻塞交付，也不作为修改依据。
> - **每个维度至少写明：** 含义、类别、来源、需要的观察、检查方式、通过线、是否阻塞、无法检查时如何处置。检查方式四选一：deterministic / pairwise_blind / user_judgment / unverifiable。整份计划另写优先级与取舍、停止条件、不评估的范围。
> - **保持短。** 首试点大约 5—10 个维度。标准写结果，不写实现：写"价格在移动端首屏可见"，不写字号或位置。
> - **模型实例化。** 用现有 Model Gateway（deepseek-flash，ADR-007）把领域规则实例化为本任务可检查的条目。模型只能引用已加载的规则 id 或用户原话；虚构来源的条目拒收并留痕。无凭据或调用失败时，退回纯确定性组装并如实标注，不阻塞任务。
> - **时序可审计。**
>   - 计划落盘及其哈希写入 trace。新增事件 kind 时，按 TRACKING_EVENT_CONTRACT 的附录程序记录理由。
>   - 首个执行器委托事件引用该哈希；计划落盘失败时，执行器零调用。
>   - 委托指令里写入从计划派生的本轮验收项。执行器可以看到这些验收项；作者材料与评分答案不得进入指令。
> - **`hard_requirement_review` 改为读取计划中的确定性条目。** 咖啡试点的判定结果必须回归不变；另做一套事实不同的夹具任务，也要能正确判定。
> - **计划只能有原因地修订。** 只有目标变化、标准本身有错、发现新盲区三种情况可以改，改了就出新版本并写明原因。旧尝试的结果仍绑定旧版本，不改写。brief 改版时（例如价格 ¥99 改为 ¥129），计划随之改版，受影响的条目失效。
> - **用户可见，但不设门。** 计划形成时发 notify_progress，不等待回复；报告的"看依据"列出计划和每条来源。不新增任何审批或 request_decision。
> - **提供一个可亲自执行的入口。** 例如 CLI 子命令：只生成并打印某个目标的评估计划，默认离线组装，加 `--real` 才调用模型。
> - **不改变：** 权限规则、ADR-002 默认自主、预算、单写入者；`docs/evaluation/e1/` 的冻结字节；两个 T4 历史运行目录；候选审查 `_adjudicate_candidates` 与复检 `run_model_review` 的逻辑（这些属于 V2）。
>
> **验证：**
> - **离线测试，覆盖：**
>   - 四层来源组装；
>   - provisional 与 hypothesis 不阻塞；
>   - 计划先于委托，落盘失败时执行器零调用；
>   - 硬要求读计划：咖啡试点回归不变，异事实夹具判定正确；
>   - brief 改版后计划改版，旧结果不改写；
>   - 模型虚构来源被拒收；
>   - 无凭据时降级。
>
>   全量测试通过，runtime 零泄漏。测试里的模型响应是 Fake，必须标注。
> - **真实核验：** 用一次真实 DeepSeek 调用，为标准试点目标生成计划，不调用 Codex。逐条核对来源是否真实存在、检查方式是否成立、是否有实现层面的过度规定，并记录 tokens。如果还要跑一次端到端，最多一次，并在记录中与计划生成核验分开写。
> - **记录：** 写 docs/progress/P2.4-V1.md，并更新 DEVELOPMENT_STATUS.md。按 AGENTS.md §6 提供：入口、用户可亲自执行的一条命令及预期结果、实际输出、Mock 与未实现清单。
>
> **停止点：** V1 的退出门槛满足就停止，推荐下一步 V2，不要顺手修改候选路由或复检。guide-revise 路径如果本轮没接入，要在记录中写明，作为 V2 待补。遇到需要负责人取舍、又影响本轮的问题，先完成不依赖答案的部分，再提问。
