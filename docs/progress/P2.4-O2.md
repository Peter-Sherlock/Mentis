# P2.4-O2 记录：运行阶段、等待与活动状态（2026-10-08）

性质：按 [O2 开发 prompt](../prompts/P2.4-O2.md) 实施的一轮开发。范围只含 O2；C1（专业配置冻结）与 O3 完整核验（一次登记预算的真实任务）未实施。**真实模型/执行器调用 0 次**；受控演练明确标注「开发验证，非真实 AI 任务」。

## 1. 本轮目标与结果

**目标**：让现有本地页面和 CLI 准确显示当前阶段、等待原因、耗时、生产者活动与最后可靠状态；恢复后的新代次不被旧收尾/旧 manifest 覆盖；旁观器与页面刷新不冒充生产者活跃。

**结果**：完成技术门槛。针对性测试 23 项新增（`tests/test_run_state.py`），全量离线回归 **324 项通过（1 项跳过 = 既有浏览器集成 opt-in）**；两个受控子进程场景（等待、恢复）由真实 HTTP 页面与 CLI 消费并有 Chrome 实拍；真实 E2 样例 74 个文件读取前后字节一致，判定 no_change 不变。

## 2. 变更清单

### 阶段记录（三入口共用）

- `mentis/trace.py`：`StageTracker` + `trace/stages.jsonl`（`mentis-run-stage/1`，追加式）。阶段固定九类：plan / build / observe / diagnose / adjudicate / revise / reverify / waiting_user / finalize，**只记录实际发生的**。start/end 配对，含 instance、generation、attempt、brief/计划引用、detail/reason/blocking；end 记执行器真实终态与 duration_s（单调时钟；异常记 null，无负耗时）。未关闭阶段如实记 `interrupted`（新阶段开始、恢复对账、收尾兜底三处触发）；**未决的等待用户阶段保持打开**（等待跨进程持续）。损坏行原样保留；写失败计 `write_failures`。
- 三入口接入：eval-run（计划→构建/修订→诊断→处置→复检→等待→收尾，按真实委托与终态）、collab（计划→委托→观察→诊断→处置→修订→复检→ask_user→恢复回答）、guide-revise（计划→诊断→等待→委托修订→复检→恢复回答）。零委托运行无 build/revise 阶段记录（不虚构）。

### 生产者活动信号（独立于旁观器）

- `Heartbeat` + `trace/heartbeat.json`（原子重写：临时文件+replace，单写者；`mentis-heartbeat/1`）：后台线程周期刷新（默认 15s / 有效期 45s），记录 run_id、generation、producer{pid, role}、time_utc、ttl_s、source。`start_heartbeat/stop_heartbeat` 由三入口的 run/resume 调用；**停止不写「已停止」记录**——信号自然过期。读取侧 `activity_status` 六类：fresh / stale（过期=无法确认活跃，不判失败、不解锁、不自动重发）/ corrupt（损坏）/ missing（未采集）/ old_generation（旧代次信号不代表当前生产者）/ unclear（时刻异常）。活跃不等于有进展；子进程活动未采集时如实说明。

### 运行代次与 --follow 修复

- generation = 1 + `run.resumed` 事件数（确定性推导；无事件流=unrecorded）。
- `follow_timeline` 代次语义：`run.resumed` 清除「当前代次已收尾」标记——**旧收尾+旧 manifest 不再使恢复中的运行被误报完成**；「manifest 静默收尾」兜底只适用于从未恢复过的运行（T2 原语义保持，有回归测试）；恢复后的静默只在活动信号类别变化时汇报（不刷屏）；附着时打印当前代次与活动摘要。本轮先在受控目录**复现了旧收尾误报**（旁观器在旧 finalize+manifest 上立即报告「已收尾」），随后修复并配回归。

### 最后可靠状态（CLI / 投影 / 页面共用）

- `run_projection.load_run_state`（`mentis-run-state/1`）+ `render_state_markdown` + CLI **`mentis status --run`**：当前阶段（进行中/最近结束与耗时）、未决等待（原因、开始时刻、只阻塞依赖动作；通知不阻塞）、生产者活动（类别+来源+有效期）、最近业务事件、**最后采集时刻与读取方时刻分列**、收尾归属（当前代次 vs 旧代次「不据此视为完成」）、预算（上限/已用/剩余——缺任一项不给剩余；eval 读取 runner-state/manifest 两种形状，collab/guidance 如实标 unrecorded）、模型调用/HTTP 实发/执行器委托分账（历史 eval 运行降级读 runner-state.model_requests）。
- 页面（`run_view.py`）新增「当前状态」面板（普通语言、细节可展开），fingerprint 含状态；顶栏改为「旁观器 HH:MM:SS 已读取记录；这只表示读取成功，不代表任务进程仍在运行」。CLI、`--follow`、页面共用同一 `load_run_state`。

### 契约与文档

- [追踪契约](../TRACKING_EVENT_CONTRACT.md) 新增 §18（O2 附录）：两个 sidecar、代次语义、--follow 语义、状态投影；`mentis-trace/1` 事件结构不变；sidecar 不入导出白名单。

## 4. Mock / 受控 / 未验证与限制

- **本轮无真实 AI 集成证据**：三入口的阶段/心跳集成只有离线夹具证据（FakeAdapter/FakeGateway + 受控子进程演练）；含真实委托的运行表现待 O3 一次登记预算任务。
- 受控演练的生产者是脚本（drill_producer.py），只验证记录与读取链，不冒充真实执行器/模型任务。
- 阶段粒度按现有流程边界记录，未覆盖字段级内部步骤；等待类只有 waiting_user（用户决定）——执行器长等待由 executor 事件与活动信号共同说明，无独立「等待执行器」阶段记录。
- 心跳为进程内后台线程：进程崩溃后信号最长在 TTL（45s）内仍显示 fresh，之后转 stale——「确认活跃」有最长 45s 滞后，已如实写入页面说明。
- 页面刷新间隔固定 4 秒（O3 实现），未做成可配置；`--follow` 轮询 0.5 秒。
- E2 样例等历史运行不回填阶段/心跳，页面显示「未采集」——这是设计行为，不是缺陷。
- C1 专业配置、O3 真实任务核验、T4 本人体验、E2 独立评审：各自真实状态不变（pending / pending_human / partial）。
