## 3. 修复内容

- **A（O2 等待关联）**：`trace.emit`/`StageTracker.start` 新增可选 `interaction_id`（`decision.requested/answered/received` 与 `waiting_user` 行产生时写入；不提供不留字段，历史不回填）；投影按标识配对——答复只关闭对应等待，`waiting_user` 阶段行与事件行不重复计数；历史事件按摘要中的 `ix-*` 确定性解析（大小写不敏感）；无法关联的回答记录只记缺口（"待决事项按未回答保留，不臆造对应"），不清空全部等待；回答时按标识关闭对应 `waiting_user` 阶段（`finish_waiting(interaction_id=…)` 无匹配不误关其他未决等待）。生产端接线：collab `ask_user`/`resume(answers)`（此前恢复回答**不产生** decision.answered 事件，已补）、guidance 请求/恢复回答、eval `_request_decision`（新 `IX-E*` 标识入 state.pending）/`answer`。
- **B（快照不可变）**：快照路径改为**内容哈希寻址** `resources/<sha前16>-<资源id>.<ext>`——内容不同→新文件（改版不覆盖旧引用）；内容相同→同一文件幂等复用不重写。恢复/视图读配置 `grounds[].snapshot` 记录路径（不猜文件名）；旧布局配置保持可读且读取不改写；注册表漂移仍按既定规则留痕并复用冻结内容。
- **C（同实例持续核验）**：`ensure()` 内存缓存路径每次使用前 `_reverify()`——配置字节（对冻结哈希）、绑定记录存在性、资源快照哈希，与冷恢复同一规则；任一不可核验抛 `ConfigPersistenceError`。调用方不吞：collab `_plan_resources` 显式重抛；guidance/eval 入口无宽捕获。Fake 证明：collab 两次完整夹具运行后分别篡改配置/快照，`_dispatch_codex` 抛错且 `adapter.calls` 新增为 **0**。
- **D（首次恢复一致性）**：`_conditions_changed(config, brief)` 改为显式比较"磁盘读回的配置"（原实现误比内存值，冷恢复首调 `self._config` 尚为 None 而漏判）——第一次 `ensure()` 即完成有原因改版；阶段 `config` 字段、调用关联、`binding()` 随新版本一致。
