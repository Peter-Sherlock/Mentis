# Mentis 递进式开发计划

| 项目 | 内容 |
| --- | --- |
| 版本 | v0.1，供开发 Agent 执行 |
| 日期 | 2026-09-27 |
| 产品与架构依据 | docs/PROJECT_PLAN.md |
| 当前进度入口 | docs/DEVELOPMENT_STATUS.md |
| 默认执行单位 | 一个工作包，而非整个项目或整个里程碑 |
| 本稿编写时范围 | 只编写开发节奏与交接材料；后续范围依据用户新指令 |

## 1. 本文解决什么问题

总体项目规划说明 Mentis 要做什么、为什么做以及最终架构。本文说明接手 Agent 每一轮具体做什么、先验证什么、交付什么、做完在哪里停。

采用两级节奏：P0—P5 是六个里程碑；P0.1、P1.1 等是十九个可独立检查的工作包。包编号在后续交接中保持稳定。包内可拆步骤，不为新增步骤重排整个计划。

默认一轮完成一个包。用户明确授权“完成整个 P1”或其他多个包时，按授权范围连续执行，逐包验收，不重复请求同一授权。没有满足前置条件时，先处理实际缺口，不靠提前生成后续模块制造进度。

## 2. 接手流程与资料分工

### 2.1 接手后的前五步

1. 读根目录 AGENTS.md 和 DEVELOPMENT_STATUS.md，找到当前包与最近证据。
2. 检查实际文件、Git 状态和相关测试，不假定上一位 Agent 的总结仍然准确。
3. 只读本计划中当前包及其前置包，再查总体规划对应章节。
4. 根据用户当前指令确定本轮范围，简述目标和验收方式后开始。
5. 做完当前包的必要工作，更新状态及报告，按范围停止。

如果状态文档过期，以实际可核查产物和用户最新指令修正。不要删除旧证据，也不要把不明来源的代码重新生成覆盖。

### 2.2 四份文件的分工

| 文件 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| PROJECT_PLAN.md | 产品与总体架构、研究问题和全局验收 | 实时开发进度 |
| DEVELOPMENT_PLAN.md | 包的顺序、边界、依赖和退出条件 | 声称某包已经完成 |
| DEVELOPMENT_STATUS.md | 当前包、事实证据、阻塞与下一步 | 自动授权后续实施 |
| AGENTS.md | 接手和执行约定 | 复制所有架构细节或动态状态 |

用户最新决定优先。若改变任务族或接口方向，更新相关决定和受影响包；不因为旧计划不同就重复询问已明确的问题。

### 2.3 默认一轮的交付过程

    核对当前状态
        ↓
    确定本轮工作包与验收
        ↓
    只实现这个包需要的最小能力
        ↓
    运行与变更相称的验证
        ↓
    对照退出门槛，记录通过、未通过或未验证
        ↓
    更新状态、阶段报告与必要文档
        ↓
    汇报并停止，或继续用户已明确授权的下一包

不要求固定天数内完成一个包。总体规划中的工期只是粗估，不能替代验收。一个包跨多个会话时，始终保存同一个工作包编号。

## 4. 包 P0.1：将规划建议整理成明确决定

**本轮目标：** 让接手 Agent 知道要为谁做什么，以及哪些关键决定仍未完成。

**读取：** 总体规划第 2、6、7、18、23 节；用户最新指令。

**工作步骤：**

1. 整理 ADR-001 至 ADR-005：首用户与任务族、人机协作、MVP 完成定义、运行形态、评价原则。
2. 每项写清当前建议、理由、一个必要的替代方案、影响范围和决定来源。
3. 从已有用户表述提取已决定内容，不将本计划建议冒充用户决定。
4. 对确实影响推进的缺失选择，先给出具体可审阅方案，再提出少量问题。
5. 已有明确授权或用户指定方案时直接记录，不重新请求批准。

**交付物：** docs/decisions/ 中的决定记录；更新后的状态入口。文件格式可简单，不需要实现 ADR 管理工具。

**验收：** 每项决定有 selected 或 pending 状态和真实依据；P1 所需范围与评价方向清楚。若关键选择仍 pending，本包可交付部分成果但不能标记 completed。

**本轮不扩展：** 不初始化工程，不安装 SDK，不开发 UI，不生成全部未来模块。

**停止位置：** 决定包交付和状态更新后。下一包为 P0.2。

## 5. 包 P0.2：先建立 12 个案例

**本轮目标：** 在代码之前定义何谓正确行为，避免后续 Agent 自己出题、自己宣布通过。

**前置：** P0.1 的必要产品决定已明确；纯指标数值可按总体规划在保留集前冻结。

**工作步骤：**

1. 编写 12 个小案例，覆盖充分信息、重要遗漏、歧义、可查事实、矛盾、用户不知道、修改目标、结果不合格等类别。
2. 每例分开写起始输入、可获得事实、需要决定的事项、合理路径及验收依据。
3. 至少包括一组起始请求相似但正确决定不同的案例，以及一个不应追问的案例。
4. 演练一个完整成功流程和一个失败流程。
5. 检查每条预期要求是否由情境支持；AI 起草案例标记为草案，不虚构人工复核。

**交付物：** docs/cases/initial_cases.md 或等价结构化文件；案例复核状态与问题清单。

**验收：** 12 例具备可解释依据，至少能检查何时询问、何时调查、何时执行、何时不能接受；专业评价与“格式是否完整”分开。当前项目负责人审阅可支持开始开发，但正式效果结论仍需总体规划所述独立复核。

**本轮不扩展：** 不批量生成正式 80 例，不运行模型排名，不把未经审阅的 Gold 当正确答案。

**停止位置：** P0 案例与决定具备进入工程的条件，记录仍待后续验证事项。下一包为 P1.1。

## 6. 包 P1.1：建立 Git 和最小工程

**本轮目标：** 建立可回溯的开发起点和一个能运行的入口。

**前置：** P0 退出条件具备证据，用户当前指令已进入工程实施范围。

**工作步骤：**

1. 核对目录和未提交内容，初始化本地 Git；若已存在，沿用并检查。
2. 添加忽略规则，排除凭据、运行数据库、日志和临时工作区。
3. 将已审阅规划和协作约定建立为 Git 基线，记录真实提交标识；若提交因权限或身份配置未完成，明确记录，不虚构 SHA。
4. 根据已选语言建立最小包配置、运行入口和必要开发检查。
5. 运行入口只需显示项目版本或启动信息，不接模型、不假装完整聊天系统。

**交付物：** 最小工程配置、README 运行说明、忽略规则、基线与检查记录。

**验收：** 可以按说明运行入口；基础检查成功；Git 基线可回查；没有秘密进入追踪范围。

**本轮不扩展：** 不按总体目录树预建所有空模块，不创建远程仓库，不发布，不接模型。

**停止位置：** 可重复启动和 Git 基线完成。下一包为 P1.2。

## 7. 包 P1.2：最小规格与来源契约

**本轮目标：** 把目标、要求、假设和证据来源保存为真实对象。

**读取：** 总体规划第 11、12 节。

**工作步骤：**

1. 只实现本阶段需要的 Project、Requirement、Assertion、Decision、Gap、Specification 等对象；其余对象到使用它的包再增加。
2. 区分来源类型、验证状态和用户选择状态。
3. 建立规格 ID、不可变版本与有效版本引用。
4. 支持结构化保存和可读 Markdown 导出，使用同一份数据。
5. 用初始案例验证字段缺失、来源引用和版本替代。

**交付物：** 数据契约、序列化与导出、必要的行为测试、示例规格。

**验收：** 一个规格可以无损往返保存；无来源推断不能被标成已验证事实；更新生成新版本而不覆盖已委托版本。

**本轮不扩展：** 不实现自动记忆检索、不接模型、不创建数据库全部未来表。

**停止位置：** 数据含义和版本行为可检查。下一包为 P1.3。

## 8. 包 P1.3：持久化状态与事件

**本轮目标：** 程序退出后仍知道项目在哪一步。

**读取：** 总体规划第 12—14 节。

**工作步骤：**

1. 持久化当前项目、规格、决定和待处理事项。
2. 记录关键状态事件，并建立必要的事务边界。
3. 给事件和任务分配稳定 ID，重复事件不重复应用。
4. 保存并恢复一个中途等待用户输入的流程。
5. 清楚区分对话原文、当前结构化状态和用于展示的摘要。

**交付物：** 存储层、最小迁移机制、恢复说明及必要测试。

**验收：** 重启后状态一致；重复输入不会产生重复业务变更；数据库与导出摘要不会成为两个冲突的事实来源。

**本轮不扩展：** 不做完整事件溯源框架、不做多租户或云同步、不宣称外部任务恢复已验证。

**停止位置：** 本地状态可恢复。下一包为 P1.4。

## 9. 包 P1.4：离线的最小工作流

**本轮目标：** 用确定性输入证明流程和门禁按设计工作。

**工作步骤：**

1. 实现 defining、ready、executing、reviewing、revising 等当前需要的状态及合法转换。
2. 分开检查 Readiness、Authorization、规格版本和任务预算。
3. 建立最小只读工具与工作区身份，避免在模型出现之前模糊访问边界。
4. 用明确标注的 Fake Executor 走通成功、需要输入、拒绝和失败分支。
5. 验证执行 completed 不会直接变成项目 accepted。

**交付物：** 可运行的离线流程、Fake Executor、门禁与失败路径测试、P1 报告。

**验收：** 缺条件或无授权的动作不运行；旧版本结果不能接受；不合格结果走修订；达到修订预算会停。

**本轮不扩展：** 不接真实 Coding Agent，不声称专业理解能力已验证。

**停止位置：** P1 完成仅表示 E-1 核心流程验证。下一包为 P2.1。

## 10. 包 P2.1：领域规则与缺口分析

**本轮目标：** 让缺口与专业决定建立明确联系。

**读取：** 总体规划第 9、10 节及已确认任务族。

**工作步骤：**

1. 创建首个小型领域包：范围、决定目录、条件规则、问题策略和检查方式。
2. 规则从已有案例提炼，不按专业术语数量扩充。
3. 将已有事实与决定前提对比，产生缺失、冲突或过期项。
4. 每个缺口说明影响什么、怎样取得信息、哪些动作因此受限。
5. 对信息充分和无关缺口案例验证不过度阻塞。

**交付物：** 版本化领域包、规则分析器、缺口报告和对应案例检查。

**验收：** 能解释缺口的决定影响；规则不会要求所有任务都回答全部清单；硬约束与经验建议区分。

**本轮不扩展：** 不实现通用本体、知识图谱或自动发布新规则。

**停止位置：** 基于规则的覆盖已知，模型补充能力仍未验证。下一包为 P2.2。

## 11. 包 P2.2：真实模型的受约束接入

**本轮目标：** 让真实模型产生可验证的理解候选，避免直接控制项目状态。

**前置：** 可用模型、认证、可传输数据范围和实验预算明确；已获得的适用授权不重复询问。

**工作步骤：**

1. 核对所选模型的官方接口，固定本轮模型、参数、提示词及领域包版本。
2. 实现一个小型 Model Gateway，先支持本轮需要的调用和错误报告。
3. 从用户输入生成候选目标、来源引用、缺口或澄清建议。
4. 验证输出结构、引用存在性和状态转换条件，再由程序写入状态。
5. 做有界格式修复，记录真实响应、失败和使用量，并避免记录秘密。

**交付物：** 一个真实模型接入、结构化提议处理、失败路径和 E-2 初始记录。

**验收：** 有真实调用证据；结构合法不被当作内容正确；虚构来源、不合法字段和调用失败不会静默推进任务。

**本轮不扩展：** 不同时接多家模型，不微调，不自动写代码，不把 Mock 响应纳入真实成功数。

**停止位置：** 单模型接入与边界验证完成。下一包为 P2.3。

## 12. 包 P2.3：CLI 中的专业协作与规格形成

**本轮目标：** 用户可以实际完成一段需求讨论并得到有来源的规格。

**工作步骤：**

1. 把模型提议、规则、工具读取和待用户决定项连成 CLI 对话。
2. 根据缺口选择询问、调查、受限实验或保留未知。
3. 支持“我不知道”“我不同意”“先探索其他方案”和明确目标修改。
4. 形成规格并说明关键决定，不强迫用户掌握术语。
5. 更新规格后使受影响的 readiness 和既有审核失效。

**交付物：** 可运行的 CLI 专业协作路径、对话样例、规格导出和相关验证。

**验收：** 含歧义任务能澄清，充分任务可以前进；用户独特要求不被模板覆盖；旧信息修正后不继续使用。

**本轮不扩展：** 不做 Web UI，不接真实 Coding Agent，不开发跨项目长期用户画像。

**停止位置：** 用户请求到专业规格的真实闭环完成。下一包为 P2.4。

## 13. 包 P2.4：开发集基线与价值检查

**本轮目标：** 在扩大工程之前，检查缺口与协作机制是否值得保留。

**读取：** 总体规划第 18 节。

**工作步骤：**

1. 为开发案例实现可重复评测入口，标注草案、人工复核和场景族。
2. 建立强单 Agent 与固定清单基线，提供同样的可用资料、工具和合理预算。
3. 比较关键缺口、错误推进、不必要追问、无依据要求及成本。
4. 抽查失败案例，区分模型、规则、状态和案例标注问题。
5. 给出继续、收窄或简化机制的建议及依据。

**交付物：** 开发评测入口、基线配置、原始记录、第一份失败分析报告。

**验收：** 比较可回查且基线未被刻意削弱；明确哪些收益已观察到、哪些不确定。是否继续后续包按已约定的阶段规则与当前用户授权处理，不能仅凭一个高分自动决定。

**本轮不扩展：** 不使用正式保留集调参，不声称下游真实执行效果，不为提升分数修改 Gold。

**停止位置：** P2 结论形成。下一包为 P3.1；若收益未建立，先处理报告中的具体缺口。

## 14. 包 P3.1：Codex 接口能力实测

**本轮目标：** 用隔离的小任务确认官方接口在本机实际能做什么。

**前置：** P2 的专业定义路径可运行；本轮真实调用、工作区和预算范围明确。

**工作步骤：**

1. 重新核对当前官方文档、所选 SDK / 运行时版本、认证与权限，不只引用旧规划。
2. 创建一次只读任务，记录原生会话 ID、事件、结果和失败表现。
3. 在明确隔离的测试工作区验证一个小修改，收集实际 diff 和验证记录。
4. 检查继续会话、状态查询、中断、恢复、审批等能力；未测试项标为 unknown。
5. 写入能力矩阵，决定正式 Adapter 所需的最小方法和降级方式。

**交付物：** Codex 兼容性记录、最小 Adapter、真实任务证据和能力矩阵。

**验收：** 能定位真实产物和原生会话；文档声称、实测支持、模拟实现和未知明确分开；不支持的能力不会伪造成功。

**本轮不扩展：** 不建设完整编排平台，不操作桌面窗口，不自动复用未核实的登录或额度。

**停止位置：** 接口可用性与限制已知，尚不宣称专业审核闭环完成。下一包为 P3.2。

## 15. 包 P3.2：真实委托、审核和修订

**本轮目标：** 跑通 Mentis 的第一个真实完整工作闭环。

**工作步骤：**

1. 从已形成的规格生成委托，绑定 task_id、attempt_id、版本、工作区基线和授权。
2. 通过 Adapter 调用 Codex，记录状态和产物。
3. 用独立工具检查实际 diff、运行记录和要求覆盖。
4. 为不合格项生成具体修订任务，继续会话或采用明确标注的降级路径。
5. 将通过与不通过情况写成可回查交付报告。

**交付物：** 委托管理、审核服务、有界修订、真实端到端案例。

**验收：** 至少一个任务真实完成；至少一个故意设置的不合格结果被阻止接受并获得具体问题说明；执行 completed 与 accepted 不混用。

**本轮不扩展：** 不接第二执行器，不部署、不自动推送或发布，不接受仅有口头测试声明的成果。

**停止位置：** 单执行器闭环成立，异常恢复仍需下一包验证。下一包为 P3.3。

## 16. 包 P3.3：真实恢复、权限和中断

**本轮目标：** 遇到真实中断时，能清楚知道哪些工作发生了。

**工作步骤：**

1. 验证提交超时、程序退出、执行失败和用户改变目标。
2. 保存待分发记录和原生身份，先核对外部状态与工作区，再决定继续。
3. 处理 approval_required 和 input_required，依据已有授权或转交用户，不自行扩大权限。
4. 验证拒绝后的行为，以及 interrupt_requested 到已确认停止的区别。
5. 检查同一工作区不会同时启动第二个写入者。

**交付物：** 异常路径实现、恢复指南、真实故障记录及必要回归测试。

**验收：** 重启不盲目重发；无法确定外部状态时进入 unknown；拒绝不被绕过；中断后已写文件得到检查。不可用的原生能力保留准确的受限路径。

**本轮不扩展：** 不承诺全场景恰好一次执行，不把中断等同于回滚，不通过降低权限约束换取成功。

**停止位置：** 受支持异常路径具备证据。下一包为 P3.4。

## 17. 包 P3.4：轻量本地聊天界面

**本轮目标：** 让用户通过清楚的界面使用已经验证的核心流程。

**工作步骤：**

1. 提供主聊天、当前目标、重要决定、关键未知和下一步摘要。
2. 展示正在执行、需要输入、审批、审核及交付状态。
3. 提供规格、diff、测试证据的按需查看入口。
4. 支持补充、否定、改变目标及按已验证能力中断任务。
5. 复用应用服务，不在前端复制状态机或领域规则。

**交付物：** 本地 Web 入口、最小操作说明、关键交互检查记录。

**验收：** 用户能完成一个真实任务流程并定位证据；等待输入和执行中状态清楚；用户改变方向能传播到核心状态。

**本轮不扩展：** 不做账户体系、计费、多租户、复杂设计系统或完整日志控制台。

**停止位置：** 单执行器工程 Alpha 可用。下一包为 P4.1。

## 18. 包 P4.1：第二执行器适配

**本轮目标：** 用另一个真实运行时检验执行契约。

**工作步骤：**

1. 根据实际环境确认第二候选，并核对官方接口、认证、版本和权限。
2. 运行与 P3.1 同等范围的能力探测。
3. 实现 Adapter 和事件映射，不复制专业规格或审核逻辑。
4. 明确 native、emulated、unsupported、unknown 能力。
5. 运行统一契约检查和一个隔离的真实任务。

**交付物：** 第二 Adapter、能力矩阵、真实调用与产物记录。

**验收：** 实际接入另一个 Coding Agent；核心没有充斥厂商条件分支；需要变更通用契约时有明确差异证据。

**本轮不扩展：** 不接第三个执行器、不做自动价格路由、不以更换主模型冒充更换执行运行时。

**停止位置：** 第二接口接通，但跨执行器闭环需要 P4.2。

## 19. 包 P4.2：跨执行器任务与审核一致性

**本轮目标：** 验证更换执行器不会丢失 Mentis 的目标与判断依据。

**工作步骤：**

1. 在等价工作区基线上，把一组相同规格分别交给两个执行器。
2. 使用相同独立验收条件收集结果与成本。
3. 验证修订、提问、权限和状态差异的降级处理。
4. 确认旧执行已经停止后，通过 Mentis 的规格、决定和产物切换执行器。
5. 记录核心改动量、无法迁移的能力和不支持场景。

**交付物：** 跨执行器闭环记录、兼容性报告、更新后的架构说明。

**验收：** 两个真实执行器都能完成所声明的闭环；规格与证据语义一致；没有把新任务重发伪装成原生会话迁移。

**本轮不扩展：** 不追求代码输出一致，不并发写同一工作区，不宣称任意 Coding Agent 都已兼容。

**停止位置：** P4 多执行器目标具备实际证据。下一包为 P5.1。

## 20. 包 P5.1：保留集与正式比较

**本轮目标：** 对 Mentis 的实际收益给出边界明确的结论。

**工作步骤：**

1. 检查案例分组、人工复核、保留集隔离和评价条件。
2. 在运行前冻结代码、模型、提示词、领域包、预算、阈值和分析规则。
3. 运行预定基线、Mentis 和必要消融，保留失败与超时。
4. 按场景族报告结果、成本及不确定性。
5. 如依据保留集调参，标记该集合已被使用，不继续宣称未见评测。

**交付物：** 可回查评测报告、配置、记录索引和结论限制。

**验收：** 无数据泄漏和自定成功标准；能够准确说明有收益、无收益或证据不足。未达到价值目标时不宣布 MVP 通过。

**本轮不扩展：** 不为更高分临时降低门槛，不无预算穷举实验，不编造缺失运行。

**停止位置：** 评测结论形成。下一包为 P5.2，或按结果回到一个明确的修复包。

## 21. 包 P5.2：真实用户形成性试用

**本轮目标：** 检查用户是否理解、控制并从 Mentis 中受益。

**前置：** 参与者、任务、数据范围和记录方式准备好。没有真实参与者时可以完善试用材料，但不能声称试用完成。

**工作步骤：**

1. 按总体规划组织小规模目标用户试用。
2. 记录任务表现、澄清负担、关键取舍理解和用户独特要求保留。
3. 区分界面问题、专业判断问题及执行器限制。
4. 记录用户否定建议、改变方向或无法回答时系统的行为。
5. 形成有优先级的修正建议，并保留样本局限。

**交付物：** 经允许记录的试用材料、分析和问题清单。

**验收：** 结论来自真实使用记录；不把 LLM 模拟用户记为真实用户；不将小样本形成性试用扩大为普遍有效性证明。

**本轮不扩展：** 不自动联系外部人员，不公开参与者资料，不直接开展大规模用户实验。

**停止位置：** P5.2 证据或明确阻塞已记录。下一包为 P5.3。

## 22. 包 P5.3：MVP 交付

**本轮目标：** 交付一个能力与证据相匹配的版本。

**工作步骤：**

1. 对照总体规划第 24 节，逐项核对功能、证据和文档。
2. 整理安装、配置、数据处理、故障恢复和执行器能力说明。
3. 记录未解决问题和已验证范围，核对 Git 与实际产物。
4. 给出“通过 MVP 验收”或“工程可运行、部分价值未证实”的准确结论。
5. 只建议下一阶段，不自动扩展新领域或建立多 Agent 团队。

**交付物：** 本地可复核交付版本、验收报告、使用和限制说明。

**验收：** 任何能力声明都能找到相应证据；未完成项没有被删除或改写为通过。

**本轮不扩展：** 不因交付自动推送、发布、部署或公开仓库；这些动作遵循用户实际授权。

**停止位置：** v0.1 的真实交付结论与后续建议完成。

## 23. 文档、测试与证据的阶段要求

| 阶段 | 主要验证 | 允许的结论 | 不允许的结论 |
| --- | --- | --- | --- |
| P0 | 决定、案例和语义检查 | 范围与判断标准已明确 | 系统已可用 |
| P1 | 状态、契约、恢复和离线故障测试 | 对应离线流程工作正常 | 真实专业能力已成立 |
| P2 | 真实模型案例与开发基线 | 固定案例中的观察结果 | 下游 Coding Agent 闭环已完成 |
| P3 | 一个真实执行器闭环与异常路径 | 声明范围内的 Alpha 能力 | 多执行器或生产能力已成立 |
| P4 | 两个运行时与同一任务契约 | 声明范围内可替换 | 任意 Agent 都兼容 |
| P5 | 保留集与真实用户试用 | 有边界的收益与交付结论 | 普遍专家能力保证 |

只运行与当前变更和未解决风险有关的必要检查。检查通过后不重复扩大测试来拖延交付；新变更、失败或明确疑点才触发追加验证。

真实 API、模型和执行器检查会产生成本或涉及数据传输，应在对应包明确范围与预算；不因计划列出这些检查就认为所有未来调用已授权。

## 24. 状态与交接模板

### 24.1 工作包状态

| 状态 | 含义 |
| --- | --- |
| not_started | 尚未开始 |
| in_progress | 正在进行，退出条件尚未全部满足 |
| partial | 已交付可用部分，剩余范围明确 |
| blocked | 存在无法在当前条件解决的具体依赖 |
| completed | 退出条件具备实际证据 |
| superseded | 用户改变方向或范围后被替代，保留原因 |

包 completed 不等于已提交 Git、不等于用户验收了整个产品、不等于获得下一阶段授权。需要人工决定的部分单列状态，不把所有测试通过都变成额外人工审批。

### 24.2 每轮报告内容

    工作包：P?.?
    本轮范围：本次用户指令或已持续适用的授权
    开始状态：实现、Git、前置条件
    完成内容：具体变更及原因
    产物：真实路径、任务 ID 或记录
    验证：实际运行的命令/操作、环境、结果
    未验证：未运行、缺少条件或只能模拟的部分
    退出门槛：每项是否满足及证据
    当前状态：completed / partial / blocked / in_progress
    剩余事项：阻塞原因和可继续的独立工作
    Git 状态：真实提交/未提交变更，不伪造标识
    下一步：推荐工作包及进入条件

报告可以保持简洁，但不能只写“已完成，测试通过”。代码包写入 docs/progress/<工作包编号>.md；修复同一包时追加本次记录，不覆盖之前失败的事实。

### 24.3 继续开发的规则

- 当前包未完成：优先完成该包，不自动跳到下一包。
- 当前包完成且用户说“继续”：进入下一包，先检查前置条件。
- 用户明确要求修复某问题：按问题范围工作，关联受影响的包。
- 用户要求多个包：按顺序执行，保留每包的验证和交接。
- 状态文件过期：用当前 Git、文件和证据修正，注明修正依据。
- 需要用户决定：先做可独立完成的工作，再提出具体问题；不要重复请求已授予权限。
