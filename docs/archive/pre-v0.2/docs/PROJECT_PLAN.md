## 1. 项目定义与总体判断

### 1.1 一句话定义

Mentis 是一个代表用户进入专业领域的协作代理：与用户共同定义问题、发现认知与信息缺口、探索方案、形成专业规格、委托执行，并依据证据审核和修订结果。

用户面对的是持续协作的专业伙伴。模型、Coding Agent、搜索、MCP 工具和其他专业角色，是 Mentis 可以使用的工作资源。

### 1.2 产品愿景

让用户能够从“我有一个想法或问题”开始，逐渐获得：

1. 对问题和选择的更清楚理解。
2. 与自己目标一致、可以修改的专业任务定义。
3. 由合适执行器完成的工作成果。
4. 对成果依据、验证情况、局限和下一步的可理解说明。

长期可以发展为多个专业角色协作的 Virtual Professional Team；第一版不需要先建立完整虚拟公司。

### 1.3 第一版需要验证的产品主张

在一个明确的任务范围内，Mentis 能否让缺少部分专业知识的用户，以可接受的交互成本，得到比强通用助手更符合真实要求、更容易验证的工程结果？

这是待验证的主张。当前没有证据证明 Mentis 已经具有专家级判断能力，也没有证据证明复杂编排必然优于一个强 Agent。

### 1.4 项目价值的判断标准

- 能发现会改变方案的遗漏，而非只增加问题数量。
- 能保存用户的独特目标，而非把所有需求改写成模板。
- 能说明要求和结论的依据，而非只生成结构化文本。
- 能在结果不合格时提出可执行的修订要求。
- 能区分应由工具调查、用户决定、专业人士判断的事项。
- 能更换执行器，保持项目目标、规格和审核标准的连续性。
- 在相近资源条件下，收益足以解释额外成本。

## 2. 已表达方向、规划建议与待验证假设

### 2.1 用户已经明确表达的方向

| 编号 | 方向 | 对规划的约束 |
| --- | --- | --- |
| U-01 | 先讨论产品、架构和 MVP，再实现 | 本阶段只形成可审阅规划 |
| U-02 | Agent 代表用户进入不熟悉的专业领域 | 核心不能退化为提示词润色工具 |
| U-03 | 重视 Knowledge Gap Detection 与专业需求挖掘 | 必须存在显式缺口模型与评测 |
| U-04 | 形成 Professional Specification | 要求、假设、来源、验收应当可追踪 |
| U-05 | 需要定义—委托—审核—修订的闭环 | 不能把执行器最终回答直接当成交付 |
| U-06 | 专业性体现在架构中 | 领域规则、工具、验证和能力边界要参与控制流程 |
| U-07 | 处理 Fake Expertise | 必须区分事实陈述、推断、建议和未验证结论 |
| U-08 | 保留人的参与及创造性贡献 | 人能够探索、质疑、修改目标和决定取舍 |
| U-09 | 不绑定 Codex，支持其他 Coding Agent | 执行契约与具体接入协议分离 |
| U-10 | 追求技术深度，逐步完成 | 通过真实任务和对照评测决定扩展，不能只依赖 Demo |

### 2.2 本文提出、尚待确认的建议

- 首个专业领域选软件工程；首个任务族选“小型文档问答功能的需求定义、实现与验收”。
- 首批用户以有明确软件目标、但架构和验收经验不足的个人开发者、小团队负责人为主。
- 第一版采用一个面向用户的专业代理，内部使用多个受约束的处理步骤。
- 采用本地运行、单用户、单项目、串行写入工作区的产品边界。
- 第一执行器候选为 Codex；第二候选为 Claude Agent SDK。第二个真实执行器接入属于 MVP 验收范围。
- 核心使用 Python 的方案优先评估；通过 SDK 适配执行器；先做轻量聊天界面。
- 默认不自动部署、不推送代码、不创建外部业务记录。

这些建议用于让规划具体可讨论。变更它们需要更新关联设计，不应将其当作用户已经确认的需求。

### 2.3 不能作为前提的判断

- “当前模型已经足以完整胜任专业人士”。
- “人类在所有创造性任务上都优于 AI”。
- “增加审核 Agent 就能获得独立验证”。
- “支持两个执行器就能支持任意 Agent”。
- “离线测试通过就代表真实集成可靠”。
- “MVP 在软件领域有效就证明法律、医疗等领域可用”。

## 3. 核心问题与现有概念的关系

### 3.1 要解决的四类断点

| 断点 | 常见表现 | Mentis 需要做的工作 |
| --- | --- | --- |
| 表达与目标之间 | 用户说“加 Memory”，但期望的行为不清楚 | 保留候选解释，用场景共同定义问题 |
| 目标与专业条件之间 | 没有表达权限、数据更新、失败处理等要求 | 识别条件对决策的影响，选择调查或提问 |
| 专业规格与执行之间 | 执行器自行补充假设，任务范围逐渐变化 | 版本化委托、约束范围、记录变更 |
| 执行结果与真实目标之间 | 实现能运行，但没有解决用户真正的问题 | 追踪需求覆盖，检查实际证据和用户体验 |

### 3.2 与现有 Agent 类型的区别

以下是职责侧重比较，不代表这些类别互斥，也不代表其他产品无法实现 Mentis 的能力。

| 概念 | 常见关注点 | Mentis 需要额外证明的部分 |
| --- | --- | --- |
| AI Assistant | 理解与完成用户请求 | 稳定发现用户未表达的关键条件 |
| Persona Agent | 角色表达和行为方式 | 专业判断实际受到证据、规则和门禁约束 |
| Expert Agent | 领域知识、工具与专业输出 | 不完整问题如何被定义，以及何时足以行动 |
| Planner Agent | 任务分解和步骤安排 | 规划之前的问题是否定义正确 |
| Supervisor / Meta Agent | 分配任务、协调执行器 | 委托对象、条件和结果是否符合用户目标 |
| Multi-Agent System | 多 Agent 协作 | 协作是否减少错误，而非只增加调用 |
| Agentic Workflow | 条件流程、工具调用与循环 | 每次推进是否建立在足够证据之上 |

委托和审核循环已有成熟模式；澄清必要性也已有相关研究。Mentis 的创新性需要通过机制、评测和实际收益说明，不能仅通过更换名称或增加角色来主张。[Agent 工作流参考](https://www.anthropic.com/engineering/building-effective-agents)、[澄清必要性研究](https://aclanthology.org/2025.findings-naacl.306/)

### 3.3 明确避免的退化形态

- Persona Prompt Library：主要资产只有角色提示词。
- 固定长问卷：将所有专业问题重新交给用户回答。
- 文档生成器：生成完整规格，但不负责执行和结果核对。
- Coding Agent 外壳：项目状态实际上完全寄存在执行器里。
- 多 Agent 展示系统：角色很多，但无法证明每个角色带来收益。

提示词、模板和清单都可以使用；问题在于它们是否参与可检查的决策过程，以及是否确实改善结果。

## 4. 目标用户与使用场景

### 4.1 首批目标用户假设

| 用户 | 已有能力 | 主要缺口 | 希望得到的价值 |
| --- | --- | --- | --- |
| 独立开发者或技术学习者 | 能说明目标、运行项目、阅读部分代码 | 架构取舍、质量标准、边界条件 | 少走弯路，理解关键决定 |
| 小团队产品负责人 | 熟悉使用场景和业务约束 | 技术方案与可验证规格 | 将真实需求稳定传递到实现 |
| 有经验的开发者 | 能完成工程判断 | 缺少时间，容易遗漏检查 | 减少重复工作，保留关键控制权 |

第一版不以“完全不懂电脑且无需任何开发环境”的用户体验作为承诺。执行器认证、工作区准备和技术验收仍可能需要项目负责人协助。

### 4.2 核心使用任务

用户从一个模糊的软件功能请求开始，能够在同一项目中：

1. 说明目标、展示已有代码或样例。
2. 与 Mentis 探索方案，并逐步补齐关键条件。
3. 查看简明规格、待决策事项和理由。
4. 将明确范围交给一个 Coding Agent。
5. 查看结果、证据和问题，并提出修订。
6. 在后续会话继续工作，或换用另一执行器。

### 4.3 用户不应被迫完成的工作

- 先掌握全部领域术语才能回答问题。
- 判断自己没有能力检查的专业结论是否正确。
- 阅读多个 Agent 的全部内部对话。
- 重复提供已经确认且仍有效的信息。
- 因为程序退出而重新描述整个项目。

## 5. 核心技术问题与研究假设

### 5.1 核心研究问题

面对信息不完整的任务，系统如何识别会改变专业决策的缺口，选择合理的信息获取方式，并判断当前证据足以支持哪一种下一步行动？

用户知识不足只是可能原因之一。系统要管理的是任务中的不确定性，而不是给用户贴“懂或不懂”的标签。

### 5.2 五个值得投入的技术问题

| 编号 | 问题 | 拟研究的机制 | 可观察结果 |
| --- | --- | --- | --- |
| T-01 | 决策相关缺口识别 | 领域规则、候选解释、决策依赖与反例检查 | 更少遗漏关键条件、少制造无关问题 |
| T-02 | 自适应需求挖掘与停止 | 比较行动价值、询问成本、工具可得性、下一步门禁 | 更少错误推进和无意义追问 |
| T-03 | 需求形成与变更传播 | 来源记录、版本化规格、决定与证据依赖 | 用户改主意后，计划和验收正确更新 |
| T-04 | 可验证的委托与专业审核 | 执行契约、独立产物检查、需求—证据映射 | 更少错误接受，修订能解决具体问题 |
| T-05 | 人机协作与执行器可替换性 | 用户决策界面、能力协商、统一项目状态 | 保留用户意图，跨执行器维持工作连续性 |

### 5.3 待检验假设与竞争解释

| 假设，状态均为 candidate | 可区分的预测 | 竞争解释 | 反证或不确定结果 |
| --- | --- | --- | --- |
| H-01：显式记录缺口及其决策影响，能够减少关键要求遗漏 | 在同模型、同领域资料、同预算条件下，错误推进率降低 | 收益只是更多 token 或更详细的提示词 | 匹配预算后收益消失，或误报导致交互负担明显上升 |
| H-02：按缺口类型选择询问、读取资料或实验，比固定问卷更有效 | 同等终态质量下，用户负担下降；充分信息案例不被反复询问 | 固定规则已经足够，动态策略没有额外价值 | 与强清单基线无差异，或动态选择经常浪费工具调用 |
| H-03：保留探索、候选方案及用户修改路径，能提高目标匹配 | 用户独特约束保留更好，重要取舍理解更清楚 | 只是让用户投入更多时间，或评价者偏好更长输出 | 匹配时间后收益消失；质量与偏好保真没有提升 |
| H-04：基于可核对证据的审核，比执行器自述更少错误接受 | 能识别遗漏要求、伪称测试通过和过期产物 | 只是增加一轮模型调用 | 相同额外预算的普通复核同样有效，或关键问题仍漏检 |
| H-05：执行契约能够隔离大部分执行器差异 | 第二执行器主要通过 Adapter 接入，核心领域逻辑保持稳定 | 两个执行器恰好能力相似 | 为第二执行器大量重写核心，或降级后无法满足任务要求 |

这些假设的结果需要分别报告，不因某一项成立就宣称全部架构成立。功能测试验证流程是否按设计工作；对照实验才用于评估设计是否带来收益。

## 6. MVP 边界与首个验证领域

### 6.1 领域选择建议

第一领域建议选软件工程，理由是成果、修改记录和测试相对容易获得，能在本地限制工作范围，也便于比较多个 Coding Agent。

法律、医疗、金融等领域保留为长期可能性。其专业责任、验证资源和外部后果差异很大，不纳入第一版承诺。

### 6.2 首个任务族

在一个准备好的小型项目中，定义并实现文档问答功能的有限变更。初始文档为 Markdown / TXT，使用小规模、可检查的合成或明确授权的非敏感语料。

任务变体可以围绕：

- 回答是否需要给出可定位的引用。
- 找不到证据时应当怎样回应。
- 文档更新、删除后如何反映到检索结果。
- 不同可见范围下，哪些文档允许参与检索。
- 用户真正需要的是直接回答、证据比较，还是帮助形成下一步问题。

这些变体用于验证 Mentis；文档问答系统本身只是试验载体。Mentis 不应成为另一个通用 RAG 平台。

访问边界案例使用可控测试身份和文档标签；通过测试不等于实现了生产级身份认证、多租户或企业权限治理。

### 6.3 MVP 必须具备

| 编号 | 能力 | 最小实现边界 |
| --- | --- | --- |
| F-01 | 同一项目持续对话 | 单用户，项目历史可恢复 |
| F-02 | 结构化理解 | 目标、约束、假设、来源、候选解释 |
| F-03 | 缺口检测和下一步选择 | 有限领域规则加受约束模型提议 |
| F-04 | 用户参与 | 支持补充、否定、修改、选择及“不知道” |
| F-05 | 专业规格 | 带版本、来源和验收条件，可导出 Markdown / JSON |
| F-06 | 委托执行 | 明确工作目录、基线、范围和任务预算 |
| F-07 | 专业审核 | 检查 diff、运行证据、需求覆盖与剩余风险 |
| F-08 | 有界修订 | 能继续执行会话，达到预算或阻塞时停止 |
| F-09 | 恢复和审计 | 状态、任务 ID、产物和关键事件可追踪 |
| F-10 | 多执行器验证 | 两个真实执行器顺序接入，同一任务契约可复用 |
| F-11 | 评测 | 强基线、独立验收案例和明确的失败报告 |

一个执行器完成闭环可称为工程 Alpha；完整 MVP 验收还需要第二执行器和评测证据。

### 6.4 第一版不做

- 通用领域市场、自动生成任意专业角色。
- 多 Agent 自治公司、开放社交网络或跨组织协商。
- 多用户 SaaS、计费、企业管理后台。
- 自动训练专业模型、自动学习并发布新的领域规则。
- 全量长期个人记忆、向量记忆平台、知识图谱平台。
- 通用浏览器/桌面遥控系统。
- 自动发布、部署、合并 PR 或代用户完成外部业务动作。
- 大型遗留系统改造、跨多个仓库并发写入。
- 保证发现所有 Unknown Unknowns。

### 6.5 一次最小闭环的完成标准

从自然语言请求出发，完成至少一个关键缺口的正确处理，形成可执行规格，由真实执行器完成变更，经过独立证据检查，必要时修订，并给用户一个能追踪到要求与证据的交付说明。

如果输入本来已经充分，直接推进也是正确行为；不能为了展示 Agent 能力而强制提问。

## 7. 人机协作与创造性设计

### 7.1 人的职责

| 身份 | 主要贡献 | 不应被转嫁给用户的责任 |
| --- | --- | --- |
| 情境提供者 | 现实流程、具体经历、组织限制 | 查找程序能够直接读取的事实 |
| 目标与偏好决定者 | 值得做什么、愿意接受什么取舍 | 用专业术语独立设计全部方案 |
| 共同创作者 | 新方向、反例、直觉、不满意之处 | 为每次探索提供完整解决方案 |
| 体验验收者 | 是否解决真实问题、使用是否符合预期 | 为自己无法核查的专业正确性背书 |
| 专业复核者，必要时另请 | 检查系统能力边界之外的专业结论 | 由普通用户点击确认来替代专业复核 |

### 7.2 默认交互形式

一个主聊天区，加一个可折叠的项目摘要。摘要优先呈现：当前目标、已做决定、关键未知、下一步及待用户处理的事项。

用户可以按需展开专业规格、候选方案、修改记录、执行日志和审核证据。默认不展示大量内部角色对话，不要求用户管理多个 Agent 聊天窗口。

面向用户的决定卡包含：需要决定什么、为什么现在需要、可理解的选项、主要后果、建议及依据。允许用户自行描述答案，不能用选项穷尽其意图。

### 7.3 探索与收敛

- 探索阶段允许改变问题、增加候选路径、保留尚未证实的设想。
- 收敛阶段确认当前要验证的方向、必要条件和验收方式。
- 验证阶段用样例、测试或原型检查设想。
- 用户随时可以要求回到探索；已有执行是否需要中断，由改动影响判断。

领域规则必须区分硬约束、经验建议和可检验假设。非常规方案不能仅因“不符合惯例”而被否定，但也不能因“有创意”而绕过真实边界。

### 7.4 对话约定

- 单轮通常提出 1—3 个相关问题，这是初始交互建议，不是固定问卷要求。
- 每个问题应当说明它会影响什么；涉及明显事实时保持简短。
- 用户回答“不知道”后，优先展示实例、读取环境或设计小实验。
- 草案、偏好、决定和执行授权分别记录。
- 沉默、超时、继续讨论或“看起来不错”，不能自动解释成范围外操作授权。
- 已明确授予且仍适用的授权可以复用，不反复打断用户。

### 7.5 创造性需要评测

研究提示，AI 辅助可能改善个体作品评价，也可能使不同作品趋同；该结果不能直接推广到软件架构创造性。Mentis 需要单独检查方案差异、用户独特要求保留和真实可行性。[创造性实验](https://arxiv.org/abs/2312.00506)

不能把“人参与了”当作协作有效的证据。优先记录人的输入改变了哪些决定，以及这种改变是否改善最终任务结果。

## 8. 第一版架构

### 8.1 架构原则

1. 一个面向用户的专业代理，内部模块不等于独立 Agent。
2. 模型提出语义判断；确定性程序负责数据验证、状态变更、权限和预算约束。
3. Mentis 保有项目状态，执行器保有自己的工作会话。
4. 核心依赖统一契约，不直接依赖某个厂商的会话对象。
5. 领域知识必须关联决策、证据或验收，避免无界堆积资料。
6. 先实现可恢复的单机流程，再考虑分布式编排。

### 8.2 组件关系

    用户
      ↕
    对话界面 / 项目摘要
      ↕
    Mentis 应用服务
      ├─ 目标与规格管理
      ├─ 缺口分析与信息获取策略
      ├─ 工作流控制器与行动门禁
      ├─ 委托管理与审核服务
      ├─ 领域包
      ├─ 模型网关
      └─ 状态、事件与证据存储
             ↕
        工具网关 / 执行器契约
             ├─ 文件、Git、测试与资料读取
             ├─ Codex Adapter
             └─ 第二执行器 Adapter

### 8.3 模块职责

| 模块 | 输入 | 输出 | 不能做的事情 |
| --- | --- | --- | --- |
| 对话服务 | 用户消息、待决策事项 | 对用户的解释、问题与摘要 | 把模型回答直接当作已提交状态 |
| 意图与规格管理 | 消息、来源、决定 | 带版本的任务定义 | 擅自确认用户未表达的目标 |
| 缺口分析器 | 当前规格、领域包、证据 | 缺口候选及其决策影响 | 宣称所有未知已被穷尽 |
| 信息获取策略 | 缺口、成本、能力 | 询问、调查、实验或升级建议 | 越权调用工具 |
| 工作流控制器 | 验证后的事件和策略建议 | 合法状态变更与下一行动 | 让模型自由跳过门禁 |
| 委托管理 | 已就绪任务、执行器能力 | 执行记录、事件和产物 | 把执行完成当作验收成功 |
| 审核服务 | 规格、产物、检查结果 | 接受、修订、问用户或升级 | 仅凭自报测试通过接受产物 |
| 存储服务 | 状态变更、证据与审计事件 | 可恢复记录与查询 | 把摘要当作完整事实来源 |

### 8.4 确定性代码与模型的分工

模型适合提出候选解释、发现相关条件、将专业问题转成用户语言、比较方案和生成审核意见。

程序负责字段校验、引用完整性、版本匹配、权限检查、任务预算、事件去重和状态机推进。语义审核仍然可能出错，需要评测和外部证据；把它放进模块并不会自动变成确定性判断。

## 9. 专业领域包 Domain Pack

### 9.1 最小组成

| 内容 | 用途 |
| --- | --- |
| 适用范围与能力边界 | 明确支持的任务类型和不能承诺的结果 |
| 概念与行为映射 | 将术语映射到用户能观察到的需求 |
| 决策目录 | 说明关键条件如何影响方案 |
| 条件规则 | 哪些场景触发哪些缺口或检查 |
| 问题策略 | 可理解的问题、例子及“不知道”的处理方式 |
| 工具映射 | 哪些信息可以通过读取或实验取得 |
| 验收规则与审核量表 | 怎样验证要求、评价剩余问题 |
| 来源登记 | 适用版本、检索日期、来源、有效性限制 |
| 案例与反例 | 验证规则的适用边界 |

### 9.2 示例规则

规则 DP-DOC-ACL-01：

- 触发：任务涉及多人使用文档问答，且文档可见范围未确定。
- 决策影响：检索过滤、索引组织、引用显示及测试身份。
- 需要的信息：是否存在不能互相看到的文档；权限来自哪里。
- 获取方式：先查已有权限设计；资料不足时用具体使用场景询问。
- 原型边界：可在隔离、合成数据、固定测试身份下验证思路。
- 阻塞边界：不能据此默认所有真实用户都能检索全部文档。
- 验收线索：受限文档不得进入不具备权限的测试请求结果。
- 规则性质：条件规则；不会因“多人”自动要求完整企业多租户平台。

### 9.3 如何避免领域包退化为 Prompt 集合

每个重要规则应当至少连接到一个条件、决策、证据要求或测试案例。规则变更需要版本号、变更理由和回归结果。

第一版以可审阅的结构化文件管理领域包，不建立通用规则市场。模型提出的新规则先进入候选列表，由人检查后才能影响后续执行门禁。

## 10. Knowledge Gap Detection 与需求挖掘

### 10.1 缺口的基本类型

| 类型 | 例子 | 优先解决方式 |
| --- | --- | --- |
| 意图歧义 | “记住我”是续接任务还是保存偏好 | 展示行为差异并询问 |
| 用户偏好未知 | 更重视速度还是证据完整 | 用户决定，可用具体例子辅助 |
| 环境事实缺失 | 项目是否已有身份认证 | 读取代码、配置或文档 |
| 证据不足 | 声称所有引用都能定位但没有检查 | 运行验证或检查产物 |
| 条件冲突 | 要求零外网，同时指定仅远程可用服务 | 解释冲突并讨论可行路径 |
| 能力边界不明 | 依赖一个未经验证的执行器特性 | 小范围能力探测 |
| 专业知识不足 | 系统无法判断特定设计是否可靠 | 权威资料或专业人士复核 |

### 10.2 最小算法流程

1. 将用户表达提取为候选目标、约束和来源引用，不直接覆盖已确认状态。
2. 根据任务类型加载适用领域规则，并列出下一步需要作出的决定。
3. 比较每个决定的前提与已有证据，生成缺失、冲突或过期项。
4. 让模型补充规则之外的候选缺口，并要求说明它影响哪个决定。
5. 做反事实检查：不同答案是否可能改变方案、验收或行动权限？
6. 合并重复项，标注无关项；保留判定理由以供评测。
7. 为有效缺口选择询问、工具读取、实验、暂定假设或升级路径。
8. 新信息到达后更新缺口和依赖决定，重新计算下一行动是否就绪。

Schema 完整性只能验证格式；“这个缺口真的重要吗”仍是语义问题，必须由案例和评测约束。

### 10.3 问题选择策略

初期采用透明分级规则：先处理会使当前行动越界或整体方案失效的问题，再处理会改变方案的问题，最后处理可低成本修正的细节。

同一等级内，优先通过可靠工具取得事实，减少用户重复劳动；必须由用户决定的价值取舍不能由工具代替。

可用“预计减少的决策损失减去信息获取成本”解释策略方向，但第一版不把 LLM 自报概率当作经过校准的期望值，也不直接训练强化学习策略。

### 10.4 Unknown Unknowns 的能力边界

- 用户未知、领域规则已知：通过规则覆盖发现。
- 现有规则未覆盖、当前模型或资料能够提示：提出候选风险，获取证据。
- 系统自身也无法识别：不能保证发现。通过异常案例、专家复核和后续事件扩充覆盖。

“没有检测到缺口”应当表述为“在当前任务范围和已应用检查内未发现阻塞项”，不等于“信息完整”或“没有风险”。

### 10.5 停止澄清的条件

停止不是所有字段填满，而是针对某个具体行动：

- 该行动需要的关键条件已经解决，或存在明确允许的受限试验方式。
- 用户目标与硬约束没有未处理冲突。
- 未解决假设已标注，且不会被静默升级为事实。
- 产物和验收方式足以判断这一步是否成功。
- 行动在当前权限、能力和预算内。

预算不足时可以结束调查并报告尚未就绪，不能因为问不下去而自动放行执行。

### 10.6 Readiness 与 Authorization 分离

Readiness 表示信息和证据是否足以支持当前行动；Authorization 表示用户或系统策略是否允许该行动。两者都满足才能进行对应的有副作用操作。

就绪判断应绑定规格版本、工作区基线、目标行动和适用证据。任一相关条件变化后，旧判断需要重新检查。

## 11. Professional Specification 模型

### 11.1 规格的职责

规格是用户意图、专业决定和执行任务之间的可审阅契约。它既供用户理解，也供执行器工作；结构化版本与可读版本必须来自同一份数据。

### 11.2 最小字段

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| spec_id / version | 规格身份与版本 | 已委托版本不可原地覆盖 |
| objective | 目标和预期用户价值 | 关联用户消息或明确决定 |
| scope / non_goals | 本轮范围与明确排除项 | 避免执行器自行扩大目标 |
| requirements | 行为要求 | 每项有 ID、优先级、来源和状态 |
| constraints | 技术、资源、环境及操作约束 | 区分硬约束和可协商偏好 |
| assumptions | 尚未验证但用于推演的前提 | 记录影响、失效条件和处理办法 |
| options / decisions | 候选方案及当前决定 | 保留选择理由与未选方案的关键代价 |
| acceptance_criteria | 可观察的验收条件 | 映射要求、检查方式与证据需求 |
| evaluation_plan | 准备如何判断结果 | 不允许以执行器自述替代检查 |
| risks / open_questions | 风险和待处理缺口 | 标明影响的行动和处理人 |
| evidence_refs | 支持事实与决定的依据 | 包含来源位置、获取时间及适用版本 |
| execution_envelope | 本轮委托的环境与授权边界 | 绑定工作区、权限引用和预算 |

### 11.3 来源与验证必须分开

“用户说文档每天更新一次”是一个用户陈述；“系统观测到同步任务每天运行一次”是另一个观测。它们可以互相支持，也可能冲突。

来源可信度、用户是否认可、内容是否已经验证，是不同维度。不能用一个 confirmed 字段同时表达这三件事。

### 11.4 规格变更规则

1. 新消息先产生变更提议及影响说明。
2. 明确的用户修正可以直接更新对应目标或偏好，不重复要求确认。
3. 涉及新取舍时，保留待决策状态；相关执行暂不采用未定内容。
4. 生成新版本，标注被替代要求。
5. 检查受影响的委托、测试与审核结论；必要时请求中断旧工作。
6. 旧版本结果可以保存，但不能直接用于接受新版本任务。

第一版不做复杂的自动图谱传播。使用明确的 requirement_id、decision_id、evidence_id 引用关系即可实现受影响项查询。

## 12. State 与核心数据对象

### 12.1 最小对象模型

| 对象 | 关键字段 | 主要用途 |
| --- | --- | --- |
| Project | id、scope、active_spec_version、workspace_ref | 项目边界与当前工作版本 |
| ConversationEvent | id、speaker、content_ref、time、project_id | 原始交互记录 |
| Assertion | statement、source_type、source_ref、verification_status、validity_scope | 保存事实陈述、推断和冲突 |
| Requirement | id、description、source_refs、status、acceptance_ids | 可追踪的用户要求 |
| Decision | id、options、selected_option、status、rationale、dependencies | 记录尚未决定或已决定的取舍 |
| Gap | id、kind、affected_decisions、impact、resolution_path、status | 管理影响下一步的不确定性 |
| Evidence | id、kind、artifact_ref、locator、captured_at、version_scope | 连接结论与可检查材料 |
| ActionReadiness | action_type、spec_version、basis_refs、blocking_gap_ids、status | 判断某一步是否可以进行 |
| Authorization | action_scope、resource_scope、issuer、validity、revocation | 与就绪判断独立的权限记录 |
| Delegation | task_id、spec_version、executor_id、baseline_ref、status | 一次明确委托 |
| ExecutionAttempt | attempt_id、native_session_id、native_turn_id、status、budget | 记录每次真实执行尝试 |
| Artifact | id、type、path、hash、producer、baseline_ref | 文件、diff、日志及其他产物 |
| Review | target_attempt、spec_version、findings、coverage、disposition | 基于证据的审核结论 |
| PendingInteraction | id、kind、question、scope、status | 用户输入与操作审批队列 |

### 12.2 字段语义

- Assertion 的来源可为 user_report、tool_observation、retrieved_source、model_inference。
- verification_status 可为 unverified、supported、contradicted、stale；supported 必须指向适用证据，不表示绝对真实。
- Decision 的状态可为 proposed、selected、superseded；涉及用户取舍时记录选择者。
- Gap 的状态可为 open、investigating、resolved、deferred、out_of_scope；deferred 不能伪装成 resolved。
- Review 的处置为 accept、revise、ask_user、escalate；事实证据不足时不能自动 accept。

### 12.3 不变量

1. 没有来源的模型推断不得写入已验证事实集合。
2. 每个被执行的任务都必须引用一个不可变规格版本。
3. 同一可写工作区同时只有一个活动写入者。
4. completed 表示执行尝试结束；accepted 表示对应规格经过审核。
5. 权限拒绝不能通过换执行器或重试绕过。
6. 人工确认偏好不会把技术结论变成已验证事实。
7. 重复事件不得导致重复业务状态变更。
8. 用户修改关键条件后，相关就绪判断和接受结论必须重新检查。

### 12.4 存储建议

第一版建议使用 SQLite 保存规范化对象、事件和待提交任务；较大产物存储在本地文件目录中，以哈希和路径关联。

状态更新、审计事件和待分发委托尽量在同一数据库事务中提交。日志导出为 JSONL 用于分析，但 JSONL 不同时充当另一个独立事实数据库。

不在第一版实现完整分布式事件溯源系统。恢复主要依靠持久化状态、执行器身份映射和工作区检查。

## 13. Workflow 与恢复语义

### 13.1 项目工作阶段

| 阶段 | 主要活动 | 进入下一阶段的条件 |
| --- | --- | --- |
| exploring | 理解目标、探索候选问题和路径 | 有可讨论的任务边界 |
| defining | 补齐关键条件、形成规格 | 对目标行动的 readiness 通过 |
| ready | 准备委托并检查环境、能力和授权 | 三类条件均满足，预算有效 |
| executing | 执行器完成工作，接收事件 | 执行结束或需要介入 |
| reviewing | 检查实际产物和证据 | 形成审核处置 |
| revising | 提交针对性修订 | 重新进入执行与审核 |
| delivered | 交付对应版本的结果和局限 | 用户可继续提出下一轮变更 |

等待输入、等待审批、阻塞、执行失败和取消是需要独立记录的运行状态，不应全部压缩成“暂停”。

### 13.2 执行尝试状态

planned → dispatched → running → completed / failed / interrupted

运行中还可能进入 awaiting_input、awaiting_approval、interrupt_requested 或 unknown。unknown 表示 Mentis 尚未确认外部执行是否结束，不代表失败，也不允许自动启动第二个写入者。

### 13.3 中断与继续

- 用户改变目标：先分析变更影响。相关工作仍在运行时请求中断，确认终止状态并检查已产生的文件。
- 正常修订：沿用同一原生会话，或在不支持继续时创建带必要上下文的新会话。
- 程序重启：恢复项目记录，查询原任务状态，核对工作区后决定继续。
- 网络超时：优先查询已提交任务，不立即重复提交有副作用的任务。
- 中断成功不等于文件已回滚；恢复文件需要单独检查和明确策略。

### 13.4 提交一致性

本地 task_id 与 attempt_id 唯一；保存外部 session / turn 标识。采用持久化待分发记录可减少“状态写入但未发送”的问题，但不能凭此保证外部副作用恰好执行一次。

若执行器不提供幂等提交或状态查询，提交超时应进入 unknown，保留人工核对路径。不得将盲目重发当作可靠恢复。

### 13.5 有界循环

默认实验配置建议最多进行两轮自动修订。该值是控制成本的初始参数，应在开发集上调整并记录。

连续出现同类问题、修订没有改善、权限不足、核心假设失效或预算耗尽时，结束自动循环并报告下一步。不能为了显示成功而降低验收条件。

## 14. Memory 模型

### 14.1 第一版真正需要的记忆

| 类型 | 保存内容 | 第一版处理方式 |
| --- | --- | --- |
| Conversation History | 用户和系统交互 | 持久化，可按来源回查 |
| Working State | 当前目标、缺口、计划、等待事项 | 结构化任务状态 |
| Task / Project Memory | 规格、决定、审核、产物 | 跨会话保留，有版本和有效范围 |
| Domain Knowledge | 专业规则和参考材料 | 版本化领域包 |
| User Preferences | 当前项目中明确表达的偏好 | 默认项目内使用，可修改或删除 |
| Episodic Memory | 跨任务案例经验 | MVP 后评估；第一版只保留运行记录 |
| Procedural Memory | 自动学到的执行方法 | 不自动启用；转为待人工审阅的候选规则 |

### 14.2 边界

- 不把 checkpoint 等同于长期用户记忆。
- 不因一次随口表达就建立永久用户画像。
- 不依赖向量检索保存任务关键约束；关键状态必须可以准确查询。
- 对话摘要可以帮助构造上下文，但不是原始来源的替代品。
- 首版仅检索当前项目与授权领域资料，不自动跨项目传递信息。

### 14.3 修正、删除与过期

用户修正内容后，保留可审计的替代关系，并让旧值退出当前有效状态。删除项目时应覆盖数据库记录、产物和本地缓存；外部执行器或模型服务的留存独立于 Mentis，不能承诺通过本地删除同步消除。

MVP 不启用未经说明的远程备份。项目数据保留周期、日志最小化和导出范围需在试用前确定。

## 15. Tool、模型与多 Coding Agent 接入

### 15.1 三个独立接口

| 接口 | 面向的能力 | 例子 |
| --- | --- | --- |
| Model Gateway | 理解、提议、结构化输出和语义审核 | Mentis 自身调用的模型 |
| Tool Gateway | 有明确输入输出的单项操作 | 读取文件、查询资料、Git diff、运行检查 |
| Executor Adapter | 具有自身执行循环和会话的 Agent | Codex、第二个 Coding Agent |

直接调用模型 API，不等于获得完整 Coding Agent 的文件操作、执行循环、会话和权限机制。三种接口可以使用同一厂商，但不能混成同一个抽象。

### 15.2 工具的最小契约

每个工具声明输入输出 Schema、读写属性、资源范围、所需权限、超时、输出大小限制和是否可安全重试。外部写入操作还需要说明幂等性和可逆性。

第一版工具优先提供：工作区读取、受限检索、Git 状态与 diff、受控测试执行、产物读取。网络搜索按任务需要启用；搜索结果只作为外部材料，不拥有修改系统规则的权限。

### 15.3 执行器的逻辑契约

以下是 Mentis 拟定义的行为，不是厂商现有 API 名称：

| 行为 | 目的 |
| --- | --- |
| describe_capabilities | 返回当前版本已支持、已验证和未知的能力 |
| start_task | 在明确工作区和规格版本下开始任务 |
| observe_task | 获取状态、进度或最终结果；可为流式或轮询 |
| continue_task | 在现有任务上下文中提交修订，可选 |
| answer_request | 回答执行器产生的澄清或审批，可选 |
| interrupt_task | 请求中断并报告是否确认停止，可选 |
| recover_task | 程序重启后定位原会话和运行状态，可选 |
| collect_artifacts | 收集或定位变更、日志和其他产物 |

缺失可选能力时，Adapter 返回明确的不支持；工作流选择受限模式，不伪造成功。

### 15.4 能力声明

至少覆盖：流式事件、同会话继续、重启恢复、状态查询、中断、运行中追加输入、审批往返、结构化结果、使用量统计、工作目录限制和权限粒度。

每项记录 native、emulated、unsupported 或 unknown，以及验证版本和证据。通过重发上下文开启新任务属于 emulated continuation，不能标为原生恢复。

### 15.5 统一事件

Mentis 层建议归一化为 task_started、progress、input_required、approval_required、artifact_available、task_completed、task_failed、task_interrupted。

事件携带 task_id、attempt_id、native_event_id 或本地序号、时间、规格版本及 payload。保留经过脱敏的厂商原始事件用于排障，核心流程不直接依赖厂商字段。

消息丢失和恢复时，以可核对的执行状态和产物为准；不能仅通过自然语言中出现“完成”判定终态。

### 15.6 第一执行器：Codex

建议先评估官方 SDK。官方文档目前列出 TypeScript 与 Python 接口，支持本地会话的创建和继续；Python SDK 底层使用本地 App Server。文档确认不代表本机已经兼容或完成认证。[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)

如果 SDK 暴露的功能不能满足真实的中途交互需求，再评估 App Server。其双向协议提供更细的会话与事件控制；官方仍提示 App Server 命令的实验性状态，WebSocket 也有单独限制。首个实验优先本地进程通信，固定版本并做协议验证。[App Server](https://learn.chatgpt.com/docs/app-server)、[迁移及状态说明](https://learn.chatgpt.com/docs/mcp-server)

旧的 codex mcp-server 已被移除。Codex 调用外部 MCP 工具与“把 Codex 本身作为 MCP Server”是两个不同方向，不使用已移除入口设计新系统。[官方说明](https://learn.chatgpt.com/docs/mcp-server)

### 15.7 第二执行器候选：Claude Agent SDK

官方说明提供 Python / TypeScript 接口，将 Claude Code 的 Agent 循环和工具能力嵌入应用。因此它可以作为不同执行运行时的验证候选，而不仅是把 Mentis 的底层模型换成 Claude。[Agent SDK 概览](https://code.claude.com/docs/en/agent-sdk/overview)

实际纳入第二执行器前，需要单独核对：所选版本、Windows 运行要求、会话与审批映射、认证方式、使用条款、成本和本机实测结果。此阶段不假定可直接复用任何桌面产品的登录态或订阅额度。

如果该候选受环境或接口限制，按同样的能力条件选择其他真实 Coding Agent；替换选择需要记录理由，不以 Mock 冒充第二执行器。

### 15.8 标准协议的地位

ACP 致力于标准化编辑器与 Coding Agent 的通信，并通过版本和能力协商区分支持范围。未来可作为某些 Adapter 的接入路径；采用协议不意味着所有执行器具备相同功能。[ACP 官方仓库](https://github.com/agentclientprotocol/agent-client-protocol)

MCP 用于工具和上下文接入。用户提到的 A2A、Social Harness、AAP 等长期方向在本稿中只保留扩展位置，尚未指定具体协议、版本或产品依赖。

Mentis 的规格、判断和验收语义由自身核心负责；传输协议只解决其中一部分通信问题。

### 15.9 为什么不以 Computer Use 为主要集成方式

SDK、结构化 CLI 或协议可以直接取得事件与状态。界面自动化还需处理窗口、焦点、截图和界面变化，会增加与专业能力无关的失败来源。

Computer Use 可以作为无编程接口工具的后续补充能力；首版不通过点击 Codex 或其他 Agent 的聊天窗口完成主流程。

## 16. Professional Review 与证据

### 16.1 审核输入

审核服务接收不可变规格版本、对应执行尝试、工作区基线、实际 diff、测试日志、产物，以及仍未解决的假设。

不能只把执行器最后一段总结交给另一个模型评分。审核与执行可以使用同一个底层模型，但独立性来自不同证据和检查方式，不能仅靠不同角色名称宣称。

### 16.2 审核层次

| 层次 | 检查内容 | 典型证据 |
| --- | --- | --- |
| 契约检查 | 任务版本、文件范围、产物完整性 | ID、哈希、Git 基线与 diff |
| 确定性检查 | 程序行为与可自动验证要求 | 测试退出码、输入输出、引用定位检查 |
| 专业语义检查 | 方案适用性、遗漏条件、设计权衡 | 领域规则、源代码、证据链 |
| 用户目标检查 | 是否解决真实使用问题 | 用户操作、样例反馈和决定记录 |

确定性测试也可能覆盖不足；需要明确它验证了什么，不能把“全部测试通过”写成“完全正确”。

### 16.3 审核处置

- accept：对应版本关键要求具备适用证据，剩余局限已说明。
- revise：问题可定位且可在既定范围解决，输出具体要求、失败证据和预期结果。
- ask_user：出现新的价值取舍或范围选择，用户决定后更新规格。
- escalate：需要系统之外的专业判断、环境权限或能力，保留工作并说明缺口。

### 16.4 防止错误接受

- 自报测试通过必须能够关联实际执行记录；缺少记录时标为未验证。
- 检查测试是否在正确版本、正确目录和真实相关环境运行。
- 对需求覆盖同时检查“遗漏”和“实现了但没有证据”。
- 执行器新增的测试可以帮助验证，但不能单独定义全部成功标准。
- 基准中的隐藏验收条件由独立评测器持有，不交给执行器或运行中的 Mentis 修改。
- 对无法自动核查的要求保留人工检查，不能伪造通过状态。

### 16.5 交付格式

交付报告应包含：完成的目标、重要决定、对应产物、实际验证、已知局限、尚未处理事项及可选下一步。

用户默认看到简明报告，可展开每项要求的证据。模型使用量和内部日志属于技术细节，仅在成本或故障与用户决定有关时突出展示。

## 17. 权限、可靠性与运行边界

### 17.1 最小执行边界

第一版在独立测试工作区执行写入，以当前 Git 提交和初始工作区指纹记录基线。工作区存在未登记改动时先检查来源，不覆盖用户进行中的工作。

只读探索、工作区内变更、安装依赖、联网、外部写入分别授权。任务描述中的 allowed_paths 是约束说明，只有运行时沙箱或相应权限机制才能实际落实边界；事后 diff 检查不能替代访问控制。

### 17.2 本地与外部数据

- 默认本地保存状态与产物，但调用外部模型或 Coding Agent 时仍可能传输上下文。
- 工具网关负责最小必要上下文；不把整个项目、凭据和无关文件默认发给服务。
- 首版使用合成或明确授权的非敏感案例。
- 日志不记录明文密钥；认证交给对应运行时或本地秘密存储。
- 外部文档、代码注释和执行器消息属于任务材料，不能改变系统权限或冒充用户授权。

### 17.3 失败处理

| 失败 | 处理方式 |
| --- | --- |
| 结构化模型输出不合法 | 有界修复；仍失败则保留原输入并报告 |
| 关键资料不可获得 | 记录缺口，缩小下一行动或请求必要输入 |
| 执行器拒绝权限 | 停止相关动作，解释所需权限，不换通道绕过 |
| 进程退出或网络中断 | 恢复记录、查询状态、核对工作区；不盲目重跑 |
| 测试环境失败 | 区分环境问题与项目缺陷，未运行测试不能计为通过 |
| 用户改目标 | 更新规格，失效相关门禁和审核，处理旧执行 |
| 审核无法取得证据 | 标记未验证，不自动交付为已接受 |
| 预算耗尽 | 停止新增工作，保存状态并报告已完成与未完成部分 |

### 17.4 并发与边界

第一版允许只读查询并行，但一个工作区只允许一个写入任务。未来跨执行器并发必须有隔离工作区、合并策略与冲突处理，不能直接共享同一目录写文件。

有限范围内未发生越界只证明该范围的测试结果，不能宣称生产安全认证或全面安全性。

## 18. Evaluation：如何判断项目是否有效

### 18.1 证据层级

| 层级 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| E-0：设计与静态检查 | 契约、状态和文档内部一致 | 模型会正确理解用户 |
| E-1：离线确定性测试 | 状态、门禁、恢复和 Adapter 映射按规则工作 | 真实接口或专业能力已经可靠 |
| E-2：真实模型评测 | 固定案例中检测、提问、规格生成的表现 | 真实用户一定受益 |
| E-3：真实执行器闭环 | 实际任务提交、变更、检查、修订和恢复可运行 | 所有环境和所有任务都适用 |
| E-4：真实用户试用 | 观察到的负担、理解和结果匹配情况 | 已证明广泛有效或可以自主替代专家 |

每次报告写明证据等级、版本、任务范围和失败项。Mock 与 fixture 的结果只进入 E-1；不能替代 E-3。

### 18.2 案例设计

初期先人工编写 12 个典型案例，用于检查概念和规则是否可用。正式开发评测建议逐步扩充为约 80 个案例，按 20 个独立场景族、每族约 4 个相关变体组织。

建议按场景族划分约 40 个开发案例和 40 个保留案例。相同基础场景的改写、同义句与成对变体必须放在同一侧，避免开发集泄漏到保留集。

80 是工作量规划，不是统计充分性的保证。相关变体不能当作完全独立样本；统计汇总以场景族为聚类单位，并报告样本小导致的不确定性。

案例至少覆盖下列维度，可交叉出现：

- 表达歧义与多种合理目标。
- 会改变方案的隐藏事实。
- 已充分的信息，不需要继续询问。
- 通过工具可以取得的事实。
- 条件矛盾与用户后来修改要求。
- 用户不知道答案，或资料暂不可获得。
- 执行器能力不足、中途退出、权限拒绝。
- 结果看似成功但遗漏要求、证据不足或测试自报失真。

### 18.3 每个案例的组成

| 内容 | 可见范围 |
| --- | --- |
| 用户起始请求 | 所有被测系统 |
| 初始工作区与公开资料 | 所有被测系统，保持一致 |
| 用户情境及可回答事实 | 用户模拟器或真实扮演者持有，只有被询问后按规则返回 |
| 可以通过工具查到的事实 | 在相同授权环境中可访问 |
| 当前不可知的信息 | 明确允许保持未知或暂缓相关行动 |
| 关键决策、允许方案集合 | 独立标注者和评测器 |
| 隐藏验收、预期风险与评分依据 | 独立评测器；不进入执行器工作目录 |
| 场景族、标签和标注版本 | 评测管理层 |

Gold 不应指定唯一架构、唯一问题句式或完整逐字对话。它应明确必要信息、可接受决策条件和可检查结果，允许不同有效路径。

对于讨论过程中形成的偏好，记录选择形成的过程和后续一致性；不能虚构用户一开始就持有某个隐藏“正确偏好”。

### 18.4 标注与独立性

案例作者先定义情境、可获信息和验收。另一个具备相关能力的人工复核者检查关键要求及其来源；分歧记录为待处理，不让被测模型自行决定 Gold。

自动生成案例只能用于扩充候选。未经人工语义检查的案例应标记 pending_human，不进入正式能力结论。

如果暂时没有独立复核者，可以继续做探索实验，但报告必须写明“单人标注、尚未独立复核”，不能升级为专家能力已验证。

保留集一旦用于调参或规则修改，就成为已使用评测集。需要新的未见案例做独立复核，不能继续把旧集称为未见测试。

### 18.5 对照组

| 组别 | 配置 | 用途 |
| --- | --- | --- |
| B-0：直接 Coding Agent | 用户请求直接交给执行器，允许其正常交互 | 产品使用方式参考，不单独用于归因某个模块 |
| B-1：强单 Agent | 相同模型、领域资料、工具、执行器与预算，使用认真优化的专业提示词 | 排除只是提示词更完整或调用更多的解释 |
| B-2：固定领域清单 | 相同知识与工具，按预定义规则收集信息并执行审核 | 判断动态缺口与问题选择是否有额外收益 |
| M：Mentis | 完整拟议机制 | 比较总体效果与成本 |

主要机制对照采用 B-1 / B-2。对照组不得故意禁用正常追问、笔记、资料读取或合理的审核能力。共同领域知识应当可用；差别是系统如何组织状态和控制流程。

同时报告资源匹配比较和自然配置下的质量—成本比较。保持最大 token、工具调用和用户时间预算接近，并报告实际消耗；不能只声称“使用同一模型”就认为公平。

### 18.6 主要指标

| 指标 | 操作定义 | 需要防止的误读 |
| --- | --- | --- |
| 错误推进率 | 存在未解决关键条件时执行受影响动作的案例数 / 包含此类条件的案例数 | 不能通过所有任务都拒绝来优化 |
| 不必要阻塞率 | 信息已足够却无关追问、错误阻塞的案例数 / 已充分案例数 | 简短但必要的澄清不能全部算负担 |
| 关键缺口召回 | 在受影响决策前识别的关键缺口数 / 标注关键缺口数 | 依赖案例覆盖，不代表全部未知可发现 |
| 缺口有效率 | 判为缺口的项目中确实影响当前决定的比例 | 与召回同时看，避免大量泛化风险清单 |
| 无依据要求率 | 被采纳进有效规格、但无来源或未标明推断的要求比例 | 合理的显式假设不等同于伪造要求 |
| 下游任务达成率 | 按独立验收条件完成的案例比例 | 不能只按 Agent 自己的 Spec 打分 |
| 错误接受率 | 关键验收失败却被 accept 的结果 / 存在关键失败的结果 | 与“执行错误率”分别报告 |
| 用户负担 | 澄清耗时、轮数、重复问题及理解难度 | 问题越少不一定越好 |
| 偏好保真 | 明确选择的独特要求在后续规格和结果中的保留情况 | 用户后来主动修改需按新版本评价 |
| 总体成本 | 模型消耗、工具和执行时长、人工时间 | 费用未知时记录 usage，不编造价格 |

跨执行器还报告接入所需核心变更、契约测试结果、能力降级和真实闭环通过情况，不要求两个执行器输出同样的代码或达到相同质量。

### 18.7 消融与故障注入

在固定开发案例上逐项移除：决策依赖、动态信息获取、版本化来源或证据审核，观察哪些失败增加。控制额外调用预算，不能因移除模块同时减少大量计算而误判机制价值。

注入重复事件、提交超时、过期结果、执行器伪称通过、需求改变、审批拒绝、工作区并发写入等情况，检查系统是否保持不变量。

先完成必要的核心消融，再决定是否需要更大的实验矩阵，避免模型调用预算被无目的组合耗尽。

### 18.8 真实用户试用

建议首轮邀请 6—10 位符合目标画像的参与者，每人体验少量任务，采用顺序平衡的普通助手 / Mentis 对比，避免所有人都先熟悉同一个工具。

这是形成性试用，用于发现交互问题和产生下一轮假设，不足以证明总体人群中的统计优势。记录用户经验差异、任务熟悉度和学习效应。

除完成质量外，检查用户能否说明关键取舍、是否能够纠正系统、是否出现“因为看起来专业所以同意”的现象。创造性评价作为探索性结果，不宣称人机组合普遍优于人或 AI 单独工作；若要提出该主张，需要额外相应对照。

### 18.9 预先定义报告方式

- 在运行保留集前固定版本、主要指标、排除规则、预算和分析方式。
- 对模型随机性，在预算允许时做至少三个独立运行；这是初始可重复性检查，不是充分样本保证。
- 报告按场景族配对的差异、分布与不确定性，不能只展示平均分。
- 失败、超时、无法处理及人工接管计入结果，除非预先定义为基础设施无效运行。
- 所有排除项单列理由；把环境失败重新跑成功后，仍保留原故障记录。
- 人工语义评分尽量隐藏系统来源，报告分歧及裁决过程。
- 无收益、收益不明确或仅在部分任务有效，都是有效研究结果。

### 18.10 初始验收目标与冻结时点

以下是建议的工程和产品目标，不是已经测得的性能：

1. 核心契约和状态不变量的必要测试全部通过。
2. 两个执行器都提供可回查的真实任务、修订、产物和验证记录。
3. 固定关键回归集中，不出现未经授权外部写入、过期规格被接受、重复提交导致并发写入、伪造验证结果被接受等严重失败。零观察失败不等于总体风险为零。
4. 对 B-1 / B-2，至少呈现一种预先选定的有价值改进：同等质量下减少用户负担，或在可接受成本内减少关键错误。
5. 建议最小实际改进目标为错误推进率下降 10 个百分点，或同等任务达成率下用户澄清时间下降 20%。这些仅是讨论起点；样本精度不足时结果为“不确定”，不能把点估计过线当作证明。
6. 不必要阻塞率和独特偏好丢失不得出现明显恶化；允许幅度、成本上限需在开发评测后、保留集之前固定。

P0 确定指标方向、决策原则和初始目标；P2 可以依据开发集估计成本与样本精度，记录调整理由。所有正式比较阈值及其计算方法必须在首次运行对应保留集之前冻结，不得看到保留集结果后降低门槛。

若目标未达到，先定位问题并决定简化、收窄或继续研究，不自动通过扩大系统来解释失败。

## 19. 分阶段工程 Roadmap

### 19.1 阶段总览

| 阶段 | 目标 | 主要交付物 | 粗估有效工作日 |
| --- | --- | --- | --- |
| P0 | 冻结产品边界和验证方法 | 本规划定稿、12 个手工案例、关键决策记录 | 2—3 |
| P1 | 建立 Git 和可信的最小运行核心 | 数据契约、状态控制、存储、工具边界、离线测试 | 5—7 |
| P2 | 验证真实模型的专业定义能力 | 领域包、缺口与提问策略、规格生成、基线报告 | 7—10 |
| P3 | 跑通第一个真实执行闭环 | Codex Adapter、审核、修订、恢复、轻量交互界面 | 7—10 |
| P4 | 验证第二执行器可替换性 | 第二 Adapter、能力矩阵、跨执行器报告 | 4—6 |
| P5 | 完成 MVP 综合验收 | 保留集结果、形成性用户试用、风险和限制说明 | 6—10 |

合计约 31—46 个有效工作日；加上 25% 左右缓冲，按一名主要负责人持续投入估计约 8—12 周。该估计不包含等待外部账号、参与者、专业复核或不可预期兼容故障的时间，也不是交付承诺。

### 19.2 P0：规划与案例定义

工作内容：

- 确认首批用户、首个任务族、MVP 非目标。
- 用 12 个手工案例走完“表达—缺口—决定—规格—验收”。
- 确认哪些决定必须由用户提供，哪些可通过工具取得。
- 选定核心指标、基线、公平预算和评测标注负责人。
- 形成 ADR-001 至 ADR-005 的初始决定，见第 23 节。

退出条件：能够用相同术语解释关键对象；至少一个完整案例和一个失败案例没有依赖“模型会自己知道”填补关键步骤。

初稿编写时状态：已完成本规划草案；案例定义与架构冻结尚未完成。本稿不表示 P0 已验收。此后的实时开发位置维护在 [当前开发状态](DEVELOPMENT_STATUS.md)。

### 19.3 P1：工程基础与确定性核心

前提：P0 关键边界已经明确，进入工程实现的时机已确定。

工作内容：

- 先建立 Git 基线、忽略规则和工程说明，再增加实现代码。
- 实现核心对象验证、事件持久化、版本化规格和合法状态变更。
- 实现最小只读工具、工作区身份与运行预算。
- 使用明确标注的 Fake Model / Fake Executor 验证流程分支。
- 检查重复事件、过期版本、拒绝权限和恢复中间状态。

退出条件：核心不变量测试通过；重启后项目状态可恢复；能清楚说明哪些逻辑仍是模拟的。

不得在此阶段宣布真实专业能力、多执行器支持或用户价值已经成立。

### 19.4 P2：真实模型与专业定义

工作内容：

- 接入一个真实模型，记录模型标识、配置、领域包和提示词版本。
- 完成首个领域包和缺口—决定依赖。
- 实现少量可理解的问题、资料读取和停止澄清策略。
- 实现探索与决定的区分、来源追踪、规格导出。
- 建立 B-1 / B-2 基线，运行开发案例。

退出条件：能在含歧义、无歧义、冲突和无法回答的案例中选择合理动作；用户修正目标后规格正确更新；已得到第一份包含失败案例的实测报告。

如果强单 Agent 已达到相同效果，先简化架构或收窄问题，不直接进入复杂编排。

### 19.5 P3：Codex 真实闭环

工作内容：

- 在独立小型工作区验证版本、认证、权限和 SDK 接口。
- 完成创建任务、观察结果、收集产物及至少一轮修订。
- 建立独立测试与审核，保证执行结束和接受状态分离。
- 验证程序退出、任务失败和权限拒绝等路径。
- 在命令行验证基础上提供轻量本地聊天与项目摘要界面。
- 记录用户改变要求后，中断、检查已写文件、生成新任务版本的行为。

退出条件：至少一个真实端到端任务通过验收，另有故意不合格任务被正确阻止交付；所有实际能力均有证据记录。

结果定位：可运行的单执行器工程 Alpha。

### 19.6 P4：第二真实执行器

工作内容：

- 根据实际环境确认第二候选，做能力探测和认证验证。
- 实现 Adapter，不为厂商专门复制领域规则和审核逻辑。
- 在相同项目模板和一组相同规格下运行。
- 比较继续会话、询问、审批、取消和恢复的语义差异。
- 在已确认停止旧写入后，验证通过 Mentis 项目状态重新委托另一执行器。

退出条件：两个执行器都能完成其声明支持的闭环；不支持能力有明确降级；核心的厂商特例被限制并记录理由。

“同一验收标准”不要求生成相同代码；“可以更换”也不代表未完成的内部推理可以无损迁移。

### 19.7 P5：综合评测与用户试用

工作内容：

- 冻结版本后运行保留集与必要消融，报告质量、负担和成本。
- 进行小规模真实用户试用，检查理解、控制权和偏好保真。
- 修复阻断问题；修改后如需重新主张未见集效果，准备新案例。
- 完成安装、配置、恢复、已知局限、支持能力和数据处理说明。
- 决定 v0.1 是否达到验收目标，以及继续投入的依据。

退出条件：第 24 节的验收项完成，或明确给出“工程可运行但价值尚未证实”的结论，不混淆二者。

### 19.8 每阶段共同纪律

- 一次只推进当前阶段，阶段产物可独立检查。
- 退出条件未满足，不能用下一阶段新增功能掩盖。
- 每阶段结束更新规划、实现说明、已知问题和证据索引。
- 新增依赖必须说明解决哪个已出现的问题。
- 任务失败时保留工作和证据，不通过重建目录掩盖。

## 20. 技术选型与预算建议

### 20.1 候选技术方案

| 层次 | 建议 | 选择理由与验证时点 |
| --- | --- | --- |
| 核心语言 | Python 优先评估 | 便于状态、评测与数据处理；两候选执行器有官方 Python 接口；P1 固定具体版本 |
| 数据契约 | 类型模型加 JSON Schema | 便于校验、导出及跨进程传递；实现库在 P1 选定 |
| 工作流 | 明确的状态控制器 | 先覆盖本地串行流程；不以框架默认行为代替业务语义 |
| 持久化 | SQLite 加本地 Artifact 目录 | 单用户阶段便于事务和恢复 |
| 模型接入 | 小型 Model Gateway，优先官方接口 | 保留模型可替换性；首版只验证一个主模型 |
| 执行接入 | 官方 SDK 优先，协议或 CLI 按需 | 不依赖屏幕自动化 |
| 界面 | 轻量本地 Web 聊天与项目摘要 | 优先验证人机交互，不先建完整设计系统 |
| 测试 | 状态/契约测试、真实接口测试、任务评测 | 分别报告，不用总通过率混淆层级 |

这是架构层候选方案，并未安装依赖或验证完整兼容矩阵。SDK 的最低版本要求不是整个项目的版本锁定依据。

### 20.2 何时引入编排框架

当显式状态控制器难以管理真实出现的分支、中断和持久化需求时，再评估 LangGraph 等框架。决策依据是减少复杂性，而非项目属于 Agent 就必须采用某个框架。

如果采用框架，领域对象、执行契约和评测逻辑仍保持独立；框架 checkpoint 不取代项目事实来源。

跨机器长时间运行、分布式队列和故障接管出现后，再评估持久工作流平台。MVP 不为尚不存在的规模提前搭建分布式系统。

### 20.3 Windows 验证项

开发环境当前为 Windows / PowerShell。P1—P4 应特别验证中文与空格路径、UTF-8 日志、子进程启动和停止、权限沙箱、原生会话恢复及文件锁。

依赖是否需要额外运行环境以所选版本实测为准；不预设必须迁移系统，也不修改其他项目的环境以完成 Mentis 实验。

### 20.4 成本模型

一次任务的成本应同时记录：

    Mentis 理解与审核模型消耗
    + 执行器模型消耗
    + 搜索和其他工具成本
    + 本地或远程执行时间
    + 用户澄清与专业复核时间

每个任务设置模型消耗、执行时长、工具调用、修订次数和用户打断预算。缺少实时价格时先记录真实使用量与计费方式，不给出虚构金额。

预算阈值、可用认证和模型选择在实际 API 工作开始前确认。当前规划不要求新建密钥，也不调用模型执行真实项目任务。

真实接口检查按需求运行，记录成本和版本。Mock 主要用于可重复故障分支；真实集成测试用于证明实际接口；用户任务评测用于判断专业价值。

### 21.5 需要持续维护的文档

- 项目规划：范围与阶段。
- 架构说明：真实模块、数据与控制流程。
- ADR：重要取舍、考虑过的替代方案和重评条件。
- 阶段报告：已实现、离线验证、真实验证与未解决问题。
- 评测报告：案例版本、配置、原始记录、结果和局限。
- 执行器能力矩阵：文档声称与本机实测分别记录。

规划与实现不一致时，更新文档或记录偏离，不能以最初设想代替现状。

| 过早收敛压制创意 | 所有方案相似、用户只能选菜单 | 保留开放输入、候选假设和小实验 | 用户独特偏好持续丢失 |
| 复杂系统不如强提示词 | 公平基线下没有收益 | 移除低价值模块，聚焦失败类别 | 无证据支持继续复杂化 |
| 执行器接口漂移 | 升级后事件和权限语义改变 | 固定版本、契约测试、小范围升级验证 | 无法获得可靠状态或隔离能力 |
| 重复执行与文件冲突 | 超时重试产生多个写入者 | ID 映射、状态核对、单写入约束 | 无法确认活跃写入者时暂停派发 |
| 验收自我循环 | 系统遗漏要求后仍给自己高分 | 独立案例与隐藏验收 | 只能在自定标准上成功 |
| 数据泄漏与提示注入 | 外部材料要求越权或读取秘密 | 最小上下文、权限检查、来源隔离 | 出现未授权外部写入或敏感数据暴露 |
| 成本失控 | 无限修订、长对话多次重复阅读 | 任务预算、上下文选择、有界重试 | 超预算且不能解释额外收益 |
| 缺少专业标注资源 | Gold 主要由被测模型生成 | 人工复核、限定结论等级 | 暂不宣称专家能力已证明 |
| 首领域过度特殊化 | 换一种功能就要重写核心 | 区分领域规则与运行机制 | 扩域前先修正错误抽象 |

### 23.2 可以稍后决定

- 主模型、具体版本和每次任务的费用上限：P2 真实调用前。
- Codex SDK 具体版本与需不需要 App Server 扩展：P3 接入前。
- 第二执行器最终选择：P4 前，根据可用环境和能力确定。
- 是否开源、许可证、远程仓库位置和发布方式：对外发布前。
- 是否扩展 Memory、RAG 以外的任务族：完成首领域验收后。
- 是否采用 ACP / A2A 或多专业角色编排：出现明确需求及验证收益后。

命名、品牌和大型 UI 设计不阻塞当前架构讨论。

### 23.3 暂定成功与失败后的方向

- 若缺口机制有效但执行编排收益小：保留核心专业定义能力，简化执行层。
- 若清单已足够：将清单与证据机制做扎实，不强行引入自主规划。
- 若用户负担过高：优先改信息获取和交互，不增加更多角色。
- 若只有一种执行器可用：交付受限 Alpha，保留多执行器目标但不宣称已实现。
- 若需求定义良好但审核不可靠：收紧可交付范围，引入更可验证任务，不提高自主权限。

## 24. MVP 完成定义与后续扩展

### 24.1 功能完成

- [ ] 用户可以表达不完整需求，也可以直接提供充分需求。
- [ ] 系统能够按情境澄清、读取资料或开展受限验证。
- [ ] 目标、假设、决定和证据可以分别追踪。
- [ ] 规格可版本化，用户修改会影响关联任务与审核。
- [ ] 两个真实执行器能够按声明能力接入。
- [ ] 执行结束后有独立审核和有界修订。
- [ ] 用户能够查看重要取舍、补充信息和改变方向。
- [ ] 程序退出、重复事件、失败和拒绝权限有明确处理。

### 24.2 证据完成

- [ ] 必要状态与契约测试通过，测试范围可回查。
- [ ] 每个执行器都有真实运行记录，模拟测试单独标注。
- [ ] 独立验收能识别规格遗漏和结果不合格。
- [ ] 完成强基线比较并报告失败、成本和不确定性。
- [ ] 完成小规模用户试用，记录偏好保真与交互问题。
- [ ] 没有把局部测试或小样本结果写成普遍能力保证。

### 24.3 交付完成

- [ ] 安装、配置、使用、恢复和数据处理说明齐全。
- [ ] 领域包、模型与执行器版本可识别。
- [ ] 已知能力边界和不支持项明确。
- [ ] Git 状态、阶段记录和架构文档与实现一致。
- [ ] 结果被准确标记为“通过 MVP 验收”或“可运行但部分价值尚待验证”。

### 24.4 扩展顺序

建议先在软件领域增加第二个任务族，检验核心是否能复用；再扩大执行器范围、记忆策略和多专业协作。

新增专业角色前，要说明它带来的独立知识、工具、证据或检查是什么，并与单代理多步骤方案比较。跨到法律、医疗等领域前，需要相应专业资源、验证方法和边界设计，不能只加载新 Domain Pack 即宣称可用。

## 附录 A：完整协作案例

本例用于检查规划是否连贯，所有角色发言和执行结果均为设计示例，不是真实运行记录。

### A.1 用户起始表达

“我想做一个能回答团队文档问题的工具，最好回答时能告诉我依据。”

Mentis 提取候选目标：帮助团队依据文档获取信息；引用可能是关键要求。多人使用、文档范围和问题类型尚未确定。

### A.2 先处理会改变方案的条件

Mentis 先读取用户授权的项目说明，发现已有 Markdown 文档加载器；不再让用户回答文档解析库等可以自行调查的问题。

Mentis 询问：“不同同事能看的文档是否相同？这会影响哪些文档能够被检索和引用。”

用户说明所有试用者暂时看同一批公开样例，未来可能增加限制。

系统记录：当前范围为公开样例；未来权限隔离是后续事项，不把它自动加入本轮企业级功能清单。

### A.3 人参与创造性定义

Mentis 提出直接回答加引用的候选方案。用户补充：“有些文档说法不一样，我更想看到差异，不希望它直接替我选一个。”

这产生一个新的产品决定：发生来源冲突时展示差异及出处；不能静默合并成一个确定答案。

系统可以提供两个界面样例，让用户比较解释方式；先将用户选择转成验收要求，再委托实现。

### A.4 规格示例

| 要求 | 来源 | 验收 |
| --- | --- | --- |
| R-01：答案提供可定位引用 | 用户起始请求，经例子澄清 | 给定问题返回文档 ID 和对应文本位置 |
| R-02：证据不足时明确说明 | 对失败行为的后续决定 | 无相关证据的问题不生成无依据结论 |
| R-03：冲突来源分开展示 | 用户主动提出的独特要求 | 冲突样例保留两种说法及出处 |
| R-04：本轮只处理公开样例 | 当前范围决定 | 不连接真实内部文档或对外部署 |

### A.5 委托与审核

Mentis 在隔离工作区把规格 v1 交给执行器 A。执行器报告完成。

审核发现普通问题有引用，但冲突样例仍被合并。系统记录 R-03 失败，附上输入、输出和相关代码位置，生成修订任务。

修订后再次检查。如果样例通过但缺少真实用户体验反馈，交付时分别写明“已通过指定样例验证”和“尚待体验确认”。

### A.6 用户改变要求

用户希望新增文档删除功能。Mentis 形成规格 v2，保留 v1 成果，补充删除后的检索和引用行为要求。旧测试通过不代表 v2 已验收。

如果此时换用执行器 B，Mentis 提供规格 v2、相关决定、代码基线和未完成项。无需迁移执行器 A 的全部内部对话；也不承诺复原其未显式记录的内部状态。

### A.7 对应的失败案例

- 用户未说明真实文档权限，系统直接将所有文档开放：错误推进。
- 用户已明确只有公开样例，系统仍坚持完成企业多租户问卷：不必要阻塞。
- 用户提出冲突展示，系统改写成“选择最可信答案”：偏好丢失。
- 执行器声称测试通过，但没有日志且未运行检查：证据不足。
- 新规格已生效，系统仍接受旧版本结果：版本门禁失败。

| 术语 | 本项目含义 |
