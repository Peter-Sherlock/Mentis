## 问题

MVP 验收的最低构成是什么；做到哪一步可以从"工程可运行"升级为"MVP 完成"。

## 建议方案

MVP 完成 = 以下三者同时具备（PROJECT_PLAN §6.3、§24）：

1. **功能完成**：F-01 至 F-11 全部具备，含**两个真实执行器**顺序接入且同一任务契约可复用（F-10）。
2. **证据完成**：必要状态/契约测试可回查；每个执行器有真实运行记录；独立验收能识别规格遗漏与结果不合格；完成**强基线（B-1/B-2）对照评测**并报告失败、成本与不确定性；完成 **6—10 人小规模形成性用户试用**，记录偏好保真与交互问题。
3. **交付完成**：安装、配置、恢复、数据处理说明齐全；能力声明均有证据；结果被准确标记。

单执行器真实闭环（P3 结束）只称**工程 Alpha**，不称 MVP。

## 理由

1. 产品主张（§1.3）是"比强通用助手更好、更容易验证"——没有对照评测就无法支撑。
2. 执行器可替换性（U-09、H-05）是核心主张之一，只有一个执行器时该主张无法验证，也无法证伪。
3. "用户理解、控制并受益"（§1.4）属于 E-4 证据，只有真实试用能提供；LLM 模拟用户不能替代。
4. U-10 要求以真实任务和对照评测决定扩展，不能只依赖 Demo；此定义把"功能做完"与"价值成立"分开。

## 替代方案

- **收窄：单执行器 + 开发集评测即 MVP**。第二执行器与用户试用列为 MVP 后目标。优点：更快得到可用品、工期缩短约 10—16 个有效工作日（P4 约 4—6 天、P5.2 相关部分）；缺点：U-09 的可替换性主张失去证据，H-05 无法检验，跨执行器风险后置到产品承诺之后。
- **中间档：两执行器 + 评测，用户试用改为"有参与者才做"**。优点：工程与执行器证据完整；缺点：E-4 缺失时，理解/负担/偏好保真主张必须全部降级为"未验证"，MVP 结论只能写"可运行、部分价值尚待证实"。

## 影响范围

- P4、P5.1、P5.2 是否计入 MVP 验收范围。
- 总工期估计（完整定义约 31—46 有效工作日 + 缓冲）。
- 若收窄，DEVELOPMENT_PLAN 中 P4/P5 的定位需改写为"MVP 后工作包"，PROJECT_PLAN §24 验收清单相应调整。
- P0.2 案例设计不受本项直接影响，但"验收依据"的严格程度与其一致。
