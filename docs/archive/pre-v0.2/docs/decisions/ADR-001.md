## 问题

Mentis 第一版为谁服务，在什么专业任务族上验证其核心主张。

## 建议方案

- 首个专业领域：软件工程。
- 首个任务族：在一个准备好的小型项目中，定义并实现**文档问答功能的有限变更**（初始文档为 Markdown/TXT，小规模、可检查的合成或明确授权的非敏感语料）。任务变体围绕引用定位、无证据回应、文档更新后的检索行为、可见范围边界与回答形态（PROJECT_PLAN §6.2）。
- 首批用户：有明确软件目标、但架构和验收经验不足的个人开发者与小团队负责人（PROJECT_PLAN §4.1 前两行画像）。

## 理由

1. 成果、修改记录和测试相对容易获得，能在本地隔离工作区，便于建立可检查证据（§6.1）。
2. 便于在相同任务上比较多个真实 Coding Agent，支撑 MVP 所需的两执行器验证（U-09、F-10）。
3. 项目负责人具备该领域评审条件，P0.2 案例的人工复核可执行。
4. 文档问答变体能覆盖歧义、权限边界、证据引用、条件冲突等缺口类型，足以检验缺口检测与协作机制（§6.2、§10.1）。

## 替代方案

- **保留软件工程、更换任务族**：如"现有小项目的缺陷修复"或"小型工具/脚本开发"。同样可本地验证，但执行边界更开放，案例的预期行为与验收更难固定，P0.2 案例设计成本上升。
- **更换专业领域**（法律、医疗、金融等）：专业责任、验证资源和外部后果差异大，当前无法提供相应专业复核资源，不适合第一版（§6.1 已排除，仅作记录）。

## 影响范围

- P0.2 全部 12 个案例的起始输入、可获得事实与验收依据都按此任务族编写。
- P2.1 首个领域包（software_doc_qa）的内容与规则来源。
- P2.4 开发集评测与基线比较的场景族划分。
- P3 真实委托、审核与修订的验收样例。
- 若更换任务族或领域，上述工作包需整体重排，P0.2 不能开始。

## 决定来源

- 用户确认：2026-09-27，用户在 P0.1 决定确认中选择"确认建议"，批准上述领域、任务族与用户群。
- 规划建议：PROJECT_PLAN §2.2、§6.1—6.2（原稿标注为"尚待确认的建议"，经本次确认转为已定）。
- 用户方向 U-02（进入不熟悉专业领域）与 U-09（不绑定 Codex）间接支持以 Coding Agent 相关的软件任务起步。

## 重评条件

- P0.2 案例演练发现该任务族难以覆盖关键缺口类型或验收无法检查。
- 用户目标或使用场景发生变化。
