## 问题

Mentis 默认在哪些节点要求用户参与，哪些工作可以自动推进。

## 建议方案

- **持续共同设计，重要取舍可见，常规工作在已授权范围内自动推进**（PROJECT_PLAN §23.1）。
- 重要取舍以决定卡呈现：需要决定什么、为什么现在需要、可理解的选项、主要后果、建议及依据；允许用户自行描述答案，不用选项穷尽意图（§7.2）。
- Readiness 与 Authorization 分离：信息充分不等于操作获授权；沉默、超时或"看起来不错"不构成新授权；已明确授予且仍适用的授权复用，不反复打断（§7.4、§10.6）。
- 单轮通常 1—3 个相关问题，为初始交互建议而非固定问卷；"不知道"触发实例展示、读取环境或小实验，而非重复追问（§7.4）。
- 草案、偏好、决定和执行授权分别记录（§7.4）。

## 理由

1. 本方案是用户方向 U-08（保留人的参与及创造性贡献；人能探索、质疑、修改目标和决定取舍）的直接落实。
2. 只保留"重要取舍可见"这一档参与，同时以授权分离防止越权，是 U-08 与 U-05/U-07（闭环与证据纪律）共同约束下唯一自洽的默认档位：更激进的自动推进会违反授权分离原则，更保守的逐项确认会退化为固定长问卷（§3.3 明确避免的退化形态）并加重交互负担（与 T-02/H-02 的研究目标相悖）。
3. 交互成本可控，且"信息已充分时直接推进也是正确行为"（§6.5），避免为展示能力而强制提问。

## 替代方案

- **更保守**：每个规格版本形成前逐项征询用户确认。被弃原因：交互负担高，与用户方向 U-08 中"减少重复劳动"的意图及 §4.3（用户不应被迫完成的工作）冲突。
- **更自主**：信息充分即自动委托执行，仅硬约束冲突时询问。被弃原因：与 Authorization 分离原则（§10.6）及"沉默不构成授权"（§7.4）冲突；MVP 阶段执行后果不可逆风险高。

## 影响范围

- P0.2 案例中"不必要追问""不应追问""充分信息直接推进"等案例的预期行为基准。
- P2.3 CLI 协作路径的询问策略与确认节点。
- P3.4 界面的项目摘要、决定卡与审批呈现。
- P5.2 试用中"理解、控制权、澄清负担"的评价维度。

## 决定来源

- 用户方向 U-08（PROJECT_PLAN §2.1，2026-09-27 产品讨论记录）。
- 机制细节为规划 §7.2—7.4、§10.6 的落实，属于在用户已定方向内的设计具体化；**用户未逐条确认这些细节**。

## 重评条件

- P5.2 真实用户试用显示澄清负担过高或控制感不足。
- 出现授权相关的失败案例（越权推进或过度打断）。
- 用户对此默认档位提出新指令（届时按新指令更新本记录）。
