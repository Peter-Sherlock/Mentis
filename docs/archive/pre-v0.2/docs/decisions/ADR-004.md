## 问题

第一版以什么形态运行、用什么技术基座实现。

## 建议方案

- **运行形态**：本地运行、单用户、单项目、同一可写工作区单写入者（PROJECT_PLAN §2.2、§17）。
- **核心语言**：Python 优先评估，具体版本在 P1.1 固定。
- **持久化**：SQLite + 本地产物目录（哈希与路径关联）（§12.4、§20.1）。
- **执行器接入**：官方 SDK 优先（Codex SDK → Claude Agent SDK），协议或 CLI 按需，不使用屏幕自动化（§15.6—15.9、§20.1）。
- **界面**：P2 阶段用 CLI 验证协作路径；P3.4 提供轻量本地 Web 聊天与项目摘要；不先建设计系统（§20.1）。
- **默认动作边界**：不自动部署、不推送代码、不创建外部业务记录（§2.2）。

## 理由

1. SQLite 便于单用户阶段的事务一致性、状态恢复与审计（§12.4）。
2. Python 与两个候选执行器的官方接口均兼容，且适合状态管理、评测与数据处理（§20.1）。
3. 本地单用户形态匹配首版验证目标（验证专业协作机制，而非运营能力），避免过早引入多租户、计费等复杂度。
4. Windows 开发环境的具体验证项已列出（中文/空格路径、UTF-8、子进程、文件锁等，§20.3）。

## 替代方案

- **TypeScript/Node 作为核心语言**：与 Codex TypeScript SDK 天然匹配，前端同栈；但评测脚本与数据处理生态需重新评估，P1 全部工程方案需重写。仅在 Python 在本机与两执行器 SDK 实测均受阻时启用。
- **仅 CLI、不建 Web 界面**：省去 P3.4（约 1—2 个工作包工作量）；但 P5.2 用户试用的交互形式受限，"项目摘要、决定卡"等交互设计无法按 §7.2 验证。
- **更早引入编排框架（LangGraph 等）**：按 §20.2，仅在显式状态控制器难以管理真实分支/中断/持久化需求时评估，不作为初始选择。

## 影响范围

- P1.1 按此建立最小包配置、运行入口与 Git 忽略规则（语言未定则 P1.1 不能开始）。
- P1.3 存储层实现选型。
- P3.1 Codex 接入选用 Python 还是 TS SDK、是否需要 App Server。
- P3.4、P5.2 的界面与试用形式。

- 用户对运行形态或语言的新指令。
