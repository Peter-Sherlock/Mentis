# Mentis 开发协作约定

本文件帮助接手本项目的 Coding Agent 识别开发位置、范围和停止点。用户当前明确指令优先；不要把旧文档状态当作覆盖用户新授权的规则。

## 1. 接手时先读

1. `docs/DEVELOPMENT_STATUS.md`：当前阶段、工作包、已完成证据和下一步。
2. `docs/DEVELOPMENT_PLAN.md`：开发节奏、当前工作包、前置条件和退出门槛。
3. `docs/PROJECT_PLAN.md`：产品目标和相关架构章节；首次接手至少阅读第 1、2、6、7、8、18、23 节。
   领域选择、组合和边界另读 `docs/DOMAIN_STRATEGY.md`；`docs/archive/` 只用于追溯，不作为现行实施规则。
4. 如果已有代码，检查 Git 状态、当前实现和最近阶段报告；文档与实际不符时先核对，不直接沿用旧状态。

不要假定任何 Agent 会自动加载本文件。转交给其他工具时，应在交接消息中明确要求读取上述文件。

## 2. 开发节奏

- P0—P5 保留原工作包分类；v0.2 新增 P0.3、P0.4、P5.2a。实际执行先后以开发计划的依赖表为准，不能按数字排序；先验证真实指导闭环，再完善持久化和恢复。
- 默认每轮只完成当前一个工作包：实现必要内容、完成适当验证、更新状态和交接，再结束本轮。
- 完成当前包后说明推荐的下一包，不自动扩展到它。
- 用户明确授权多个工作包或整个里程碑时，可按顺序连续推进；逐包检查退出条件，不因默认节奏重复请求确认。
- 用户只说“继续”时，从状态文件中最近一个未完成的当前包继续；不要从头重建项目。
- 包过大时，在该包内拆分小步骤；不因此开始后续包。
- 用户已经明确作出的产品决定和已授予的适用权限应复用。仅对缺失且影响当前工作的决定提问，并继续不依赖该答案的工作。

## 3. 工作前后必须清楚的事情

开始前简述：当前工作包、本轮目标、主要交付和验收方式。

结束前更新 `docs/DEVELOPMENT_STATUS.md`，并按开发计划中的模板记录：变更、实际验证、失败与限制、未完成事项、下一步。代码工作另写 `docs/progress/<工作包编号>.md`；文档包的证据可以直接链接决策或案例文件。

只有退出门槛具备证据才能把包标为完成。业务决定仍待用户处理、真实接口尚未验证或测试未运行时，分别写明；不要用“基本完成”掩盖这些状态。

## 4. 工程边界

- 先按 P1.1 建立 Git 基线，再实现业务逻辑；不要为后续阶段预先生成完整目录和空模块。
- 保护用户未提交的工作。只处理当前包相关文件；不得清空目录、覆盖状态或修改无关项目以获得通过结果。
- 初始化本地 Git、创建远程仓库和对外发布是不同动作，不能互相推定授权。
- 具体 SDK、模型、认证和运行能力在对应真实接入包核对，不能把文档描述当成本机实测。
- 接入其他执行器时维持统一任务语义；不能以换执行器绕过权限拒绝。
- 不默认增加多 Agent、图数据库、向量记忆、分布式队列或复杂前端。新增机制必须解决当前已观察到的问题。
- 测试应验证状态、版本、权限、恢复和关键行为。文案或低影响格式调整只需适当检查，不为形式编写测试。

## 5. 必须保留的项目原则

- Mentis 是专业协作代理；Coding Agent 是可替换的执行资源。
- 核心验收是委托与反馈能否改善实际产物；不能用更长规格、更多追问或流程通过代替效果证据。
- 领域知识、观察能力、执行能力与已验证判断范围分别记录；加载资料不等于成为专家，更换执行器不等于跨领域验证。
- 案例作者材料、预期行为、根因标签与评分答案不能整份输入受测 Mentis 或执行器。草案交付不等于人工复核。
- 用户确认偏好，不等于专业结论已验证。
- 信息足够，不等于操作已获授权。
- 执行器结束，不等于 Mentis 验收通过。
- Mock / fixture 只证明对应离线逻辑，不能冒充真实模型、真实执行器或真实用户证据。
- 用户目标、规格、决策和证据由 Mentis 保有，不能全部寄存在执行器的聊天历史中。
- 一个可写工作区同时只有一个写入者；超时后先核对状态，不盲目重复提交。

当前开发位置只维护在 `docs/DEVELOPMENT_STATUS.md`。不要在本文件复制动态阶段状态，避免交接时出现多个相互矛盾的版本。

## 6. 每轮可观察交付要求

为避免"Agent 说做了什么 → Agent 说检查通过 → Agent 更新状态"的黑盒感，每轮结束时除变更报告外，必须提供：

1. **实际入口或产物路径**：文件、命令或页面地址，能直接定位到结果。
2. **用户可亲自完成的一次操作及预期结果**：步骤足够简单，用户不依赖 Agent 也能执行。
3. **实际观察到的结果**：真实执行输出或截图，不是转述或预期。
4. **Mock、人工样例与未实现部分清单**：明确标注哪些不是真实能力。

涉及页面或产物修改时，提供同条件下的前后版本供用户对照。只有文档交付的轮次，明确说明"本轮无新增可运行功能"。人工制作的样例、Mock 演示与真实 Mentis 运行必须分别标注，不得混用——漂亮的演示不能代替可验证的行为。

进度展示围绕用户可体验的变化组织（例如：能输入需求 → 能讨论方向 → 能看到首稿 → 能提出不满意 → 能看到有依据的改进）。工作包仍按技术依赖拆分与验收，两条线分开记录，不互相替代；不以完成的技术包数量代替体验进展。

对 Mentis 的真实任务交付，至少提供三个入口：**看结果**（当前作品在哪里，能否直接打开和操作）、**看变化**（上一版与这一版有什么不同，哪些部分保留）、**看依据**（哪句话触发修改、看到了什么证据、给执行器发了什么指令、复检结果是什么）。这些外部记录应足以让用户检查系统有没有误解目标、越界修改或虚报完成，而不需要阅读模型内部推理。
