## 1. 评分原则

1. **每项评价有情境依据**：每个关键项都指向案例情境中可观察、可核查的事实（产物属性、用户卡中的实际交互、硬要求清单），不依据"系统看起来聪明"或格式完整度评分。
2. **专业评价与格式分开**：关键项决定案例通过与否；措辞、排版、报告结构为次要项（记 0—2，不单独判负）。
3. **过程与结论分开**：偏好类案例（FC-01/02）考核形成与记录过程，不考核押中某个特定风格；不存在预定义的"正确审美"。
4. **主观与客观分开评价**：硬要求由独立客观检查核对；用户感受由用户（真实或按协议的模拟）表达；两者不得互相替代——用户喜欢不等于专业正确，专业评分也不覆盖用户偏好（§18.4）。
5. **收益与回归同时报告**：任何"改善"结论必须伴随回归检查结果，反之亦然。

## 2. 三类判断与硬要求基线

按 PROJECT_PLAN §16.2，案例中出现的每个要求都归入三类之一，处理错误类型不同：

| 类型 | 依据来源 | 处理规则 | 典型评价点 |
| --- | --- | --- | --- |
| 硬要求 | 用户明确要求、适用标准、功能检查 | 违背则修订；不得静默放弃 | FC-04 信息可见性；FC-06 双视口 |
| 专业建议 | 情境、案例、可解释的设计依据 | 提供理由，允许替代方案；不伪装为唯一标准 | FC-03 诊断解释；FC-05 可选建议 |
| 用户偏好 | 实际选择和反馈 | 记录来源、尊重、保真；可演化并记录版本 | FC-01/02 形成；FC-04 保留项 |

**硬要求基线清单**（本任务族，逐项可核查）：

1. 活动五要素完整准确：名称、日期时间（2026-11-14 14:00—16:00）、地点、价格、报名方式。
2. 报名表单：必填校验生效，空提交有提示，填写提交有确认反馈，不发送真实数据。
3. 双视口可用：1280×800 与 390×844 无横向溢出，表单与主要信息可操作、可读。
4. 站内无死链；图片有 alt 文本。
5. 正文文字与背景对比度抽检不低于 4.5:1。

说明：清单参考 [W3C WCAG 22 快速参考](https://www.w3.org/WAI/WCAG22/quickref/) 选取的少量可核查项；全部通过不代表完整无障碍合规，也不代表审美合格。清单版本随领域包版本管理，修改需记录理由（DOMAIN_STRATEGY §11）。

## 4. 基线配置

按 §18.5 两组对照设置。所有组别获得：同等领域资料（硬要求清单、文案包、素材规则）、同一首稿包与观察记录（反馈实验）或同一观察链（端到端）、同等预算（自动修订 ≤2 轮；模型调用上限数值 P2.4 冻结）。**不得禁用基线的正常追问、自检与工具使用**；报告同时给出资源匹配口径与自然使用成本口径。

### 4.1 反馈实验（固定首稿 + 固定用户卡）

用于分辨**指导贡献**：同一 v1、同一句用户反馈，比较各方法给出的诊断与修改指令，及执行器在相同预算下修订后的结果。

| 组别 | 配置 |
| --- | --- |
| B-0 | 用户把原话直接转发给执行器，执行器自行理解并修改 |
| B-1 | 同模型/资料/观察工具/预算的单代理，使用认真优化的专业指导提示词 |
| B-2 | 固定检查清单 + 固定审核步骤 + 固定修改模板 |
| B-3 | 执行器自行诊断并改进（同首稿、同反馈，无外部指导） |
| M | Mentis：观察、候选诊断、依据、保留项、修改指令与复检 |

FC-03/04/05/06 适用于本设置（v1 存在是前提，见案例 WQ-1）。FC-05 中"合格不改"对所有组别同等成立：基线同样不应修改，B-3 的自行优化若破坏合格产物同样计入不必要修改。

### 4.2 端到端实验（从模糊请求开始）

用于评估**产品体验**：允许正常追问、做样例、改变方向，比较最终质量、用户负担与成本。B-0 = 用户直接与执行器多轮对话；B-1/B-2/M 同上表配置跑全程。FC-01/02 主要在本设置运行；完整链（01→02→03→04→06）是端到端的主场景。

### 4.3 公平性检查（P2.4 实现并验证）

- 基线可获得与 M 相同的领域资料与观察记录，不因"它是基线"被削弱。
- 预算与消耗逐项记录（模型 usage、执行时长、修订轮数、用户时间），不以"用同一模型"推定公平。
- 检测运行中的系统与执行器无法读取评测答案（作者标注、评分依据）；仅换目录或提示词禁止读取不算隔离，实际隔离由 P2.4 验证。

## 5. 用户反馈协议

### 5.1 模拟用户总规则（FC 案例通用）

1. **角色卡边界**：模拟器只按案例用户角色卡回应；卡外信息不提供，被追问时用卡内规定的"说不好/不知道"回应。
2. **回应触发**：仅在被询问或被展示实际产物/样例后回应；不主动输出系统未询问的专业分析。
3. **"说不清"是合法状态**：含糊反馈（FC-03）在被给出可理解的局部对比或具体选项前，不细化为精确表述；系统不得要求用户先学会表达。
4. **偏好形成规则**：偏好只在看到样例或产物后形成（FC-02 前提）；模拟器不得表现得"早就想要某个方案"；对修改结果的确认以呈现版本的真实感受为准，确认不是必过关卡——若问题未解决，继续按卡表达不满。
5. **明确修正语句**：「就这版吧」「保留 X」「别动 Y」「我改主意了」等直接进入决定记录，系统不得反复确认（§7.4：已明确授予且仍适用的授权复用）。
6. **局部对比选择**：被给 A/B 局部样例时，按卡选择并给出卡内层级的理由；没有偏好时允许弃权。
7. **停止与退出**：用户可以随时表示"先这样"或转换话题方向；被测系统应处理而非强迫继续当前流程。

### 5.2 真实用户使用记录（P5.2a 早期试用衔接）

- 首位真实使用者为项目负责人（自用），可纳入少量目标用户；**自用与独立目标用户证据永远分开标注**。
- 记录内容：用户原话、操作与查看行为、时间戳、系统当时的理解与动作、修改前后版本号。
- **研究者提示与系统贡献分开**：若项目负责人在自用中给出了超出普通用户的专业提示（如直接指出 CSS 问题），该轮单独标记，不计入系统能力证据。
- 参与记录需获得本人同意，数据保留范围在 P5.2a 开始前确定；不自动联系外部人员。
- 模拟用户数据与真实用户数据不得混报；没有真人时如实标"未完成"，不用模拟冒充。

### 5.3 反馈记录格式（建议）

| 字段 | 说明 |
| --- | --- |
| 轮次 / 时间 | 会话内序号与时间戳 |
| 用户原话 | 逐字记录，不改写 |
| 系统理解 | 系统当时的目标/偏好/缺口记录（含来源） |
| 系统动作 | 问 / 样 / 查 / 改 / 停 |
| 产物版本 | 对应 brief 或修订版本号 |
| 用户确认 | 满意 / 不满 / 未表态，及后续行为 |

该格式为 P1.2 数据契约与 P2.4 评测入口的输入，P0.4 不实现导出。

## 6. 复核状态管理与开放问题

### 6.1 三级复核状态（永久分开记录）

| 状态 | 含义 | 允许的用途 |
| --- | --- | --- |
| 草案（AI 起草，pending_human） | 未经任何人复核 | 开发探索、案例设计讨论；**不得用于任何专业结论** |
| 负责人复核 | 当前项目负责人已审阅案例情境、评价依据与采集办法 | 支持进入开发（P1.1 及后续）；探索性实验 |
| 独立复核 | 具备相关能力、独立于案例作者与被测系统的人工复核完成 | 正式评测与能力结论（§18.4）；分歧记录保存 |

当前状态：FC-01 至 FC-06 与本框架均为**草案**。三级之间不可跳级、不可互相冒充；升级时在新版本标注复核人、日期与修改。
