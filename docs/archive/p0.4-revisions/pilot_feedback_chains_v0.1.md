## 1. 使用规则

1. **六类反馈链**对应开发计划 P0.4 要求：模糊目标（FC-01）、看样例后形成偏好（FC-02）、含糊不满意（FC-03）、保留与局部修改（FC-04）、合格不改（FC-05）、修改引入回归（FC-06）。每例可独立运行，也可按 01→02→03→04→06 串成一条完整链。
2. **可见性白名单**：运行中的 Mentis 与执行器只能得到用户当轮实际表达、授权工作区与真实工具返回。四类字段的可见范围在每例中标注：【用户角色卡】由用户模拟器或真实扮演者持有；【运行输入】是被测系统实际可见内容；【作者标注】与【评测视图】仅供作者与独立评测器，不进入运行上下文。
3. **案例编号与标题不进入运行端**：FC-05"合格不改"等标题本身暗示预期答案。运行端只接收中性化的情境描述；导出与隔离由 P2.4 实际实现并验证。
4. **不虚构隐藏偏好**：用户偏好只在其看到样例或产物后形成并被记录；用户角色卡中不含"用户其实一直想要 X"式的预设答案。预埋的缺陷特征属于**产物的客观属性**（可观察、可核查），与隐藏偏好是两回事。
5. **尚无真实首稿**：本文件所有"首稿""修订稿"均为材料要求与采集办法设计，不是已存在的作品；不得把书面描述当真实产物（P0.4 边界）。采集办法见第 3 节。
6. **不批量生成 80 例**：正式规模在 P2.4 依据成本、差异和评分稳定性设计，并在保留集使用前冻结（PROJECT_PLAN §18.7）。

## 2. 试点场景基线（合成任务）

所有案例围绕同一个合成任务族：**本地单页活动介绍页**。

- 虚构主体：「拾光咖啡」（合成品牌，不指向任何真实商家）的"周六手冲入门工作坊"活动页。
- 文案包（合成，运行系统可见）：活动名称、一句活动简介、日期时间（2026-11-14 周六 14:00—16:00）、地点（合成地址）、价格与人数上限、讲师简介（虚构人物）、3 条常见问题、报名方式说明。
- 素材规则：图形使用自制 SVG/CSS 或明确记录来源的 CC0 素材；不含真实人物肖像、真实品牌、真实联系方式或可拨号信息。
- 主要交互（一种）：本地报名表单——姓名与联系方式必填校验、提交后前端确认提示，无后端、无真实数据发送。
- 视口：桌面 1280×800 与移动 390×844 两个视口都必须可用（任务族明确要求，无横向溢出，表单可操作）。
- 技术约束：单页静态 HTML/CSS 与少量原生 JS 即可完成；不预设网页框架，不把试验载体做成平台（DOMAIN_STRATEGY §1）。
- 基线硬要求清单（评分用，详见评价框架第 2 节）：活动五要素完整准确（名称/日期时间/地点/价格/报名方式）；表单校验与确认可用；双视口可用；站内无死链；图片有 alt；正文对比度抽检不低于 4.5:1。通过这些少量可核查项不等于完整无障碍合规，更不等于审美合格。

## 3. 首稿与修改后产物的采集办法

**原则：一切"作品"必须是真实可运行的页面文件与真实观察记录；文字描述不是作品。**

### 3.1 固定首稿（反馈实验用）

- 来源二选一，均记录生成者与版本：(a) 用固定 brief 委托真实执行器生成一次；(b) 作者手工制作真实可运行页面。
- 生成后**冻结**：页面文件、内容哈希、版本号、生成方式、日期。同一首稿包对所有被测方法（Mentis 与 B-0/B-1/B-2/B-3 基线）一致发放。
- 首稿观察记录包（每次采集的最小集合）：
  1. 两个视口的渲染截图（1280×800、390×844）。
  2. 结构清单：标题层级、按钮及链接清单、文本内容、图片清单。
  3. 交互记录：表单空提交与填写提交的实际行为、确认提示内容。
  4. 客观检查输出：死链检查、正文对比度抽检结果。
- 缺少某项观察能力（如无法截图）时，依赖该观察的评价维度记**未验证**，不得用代码阅读或执行器总结替代视觉判断（PROJECT_PLAN §16.1）。

### 3.2 端到端实验

首稿由各被测系统自行委托产生，观察链与 3.1 相同。首稿本身的差异是被比较的一部分，分析时分别报告，不与反馈实验混用。

### 3.3 修改后产物

- 与修改前同链路采集观察记录，另加：文件级 diff、保留项检查清单执行记录（如首图文件哈希未变、配色变量未改）。
- 前后产物与观察记录成对归档，形成修订收益与回归的唯一证据来源；执行器的自述不作为证据（§16.5）。

## 4. 六类反馈链案例

### FC-01 模糊目标：主观词不静默翻译成唯一方案

- **场景族**：WF-01-vague-goal｜**状态**：草案（AI 起草，pending_human）｜标注版本 v0.1
- **【运行输入】起始请求**：「帮我做一个周六手冲入门工作坊的活动页，要温暖、简洁一点，我不懂设计。」（无其他上下文；文案包与素材清单按第 2 节提供。）
- **【用户角色卡】（模拟器持有）**：目标是吸引附近居民报名周末工作坊。"温暖"对用户意味着"像朋友家的聚会，不是商场促销"，但用户不会主动说出这个对照——被问"温暖指什么"答"说不好，就是别太商业"；被展示两种氛围的局部样例后能够选择。"简洁"指页面上东西别太多，具体密度没有概念。卡中不存在预先确定的正确方案。
- **【运行输入】首稿与材料**：无现成首稿；本例按端到端路径运行（首稿由被测系统委托产生），或按 FC-02 先出样例。
- **【作者标注】（作者/评测专用）**：允许路径——(a) 先做 1—2 个氛围小样再收敛；(b) 用可理解的语言澄清 1—3 个影响方案的事项后直接做首稿。共同要求：主观词（温暖、简洁）不被静默翻译成唯一专业方案，处理方式有记录（候选、样例或标注为待验证假设）；首轮动作（问/样/做）有说明的目的。失败模式——抛出设计术语问卷；无依据宣称某风格"专业正确"；既不问也不做样、直接赌一个方案且不说明可调整；把用户"不懂设计"当作需要用户先学术语的条件。
- **【评测视图】（独立评测器专用）**：关键项——①首轮动作有记录的目的且与当前缺口对应；②对主观词存在候选解释、样例比较或显式假设标注，而非静默单选；③用户的每次实际选择被记录且来源可追溯；④无虚构偏好（不得出现角色卡交互中不存在的"用户选择了 X"）。次要项——澄清轮数与表达可理解性。情境依据：任务族定义用户"有自己的想法和审美反馈，但不会写设计任务书"（DOMAIN_STRATEGY §1）。

### FC-02 看样例后形成偏好：偏好形成过程可追溯

- **场景族**：WF-02-preference-from-samples｜**状态**：草案（AI 起草，pending_human）｜标注版本 v0.1
- **【运行输入】起始请求**：「先别直接做整页。给我两三种感觉不一样的方向看看，我再定。」
- **【用户角色卡】（模拟器持有）**：用户原本没有明确偏好（这是本例的前提，不是隐藏答案）。看到方向样例 A（暖棕纸质感、衬线标题、大图）与 B（白底、几何色块、无衬线）后选择 A，并补充两条："字不要太花""日期要显眼"。被问"为什么选 A"答"更像周六下午的感觉"。对未选的 B 没有敌意，也说不出 B 里有没有想留的元素。上述偏好仅在看到样例后才存在。
- **【运行输入】首稿与材料**：无首稿；被测系统需先产出真实的方向样例（局部即可），再根据用户选择继续。
- **【作者标注】**：首稿材料要求——两个方向样例必须是真实渲染的局部小样（如首屏区块），差异真实（配色气质 + 字体气质 + 信息密度），不是同一模板换色；样例不得预埋与文案包硬要求冲突的元素。预期行为——样例差异用用户能理解的方式呈现；用户选择与补充要求被记录为偏好（来源：样例选择 + 用户补充）；所选偏好进入后续委托的保留项；未选方向不被静默全盘否定（用户没有要求删除 B 的所有元素，系统不得自行断言）；A 的选择只适用于本页，不被推广为跨页面规则。失败模式——只给一个方案假装"让用户选"；样例间无实质差异；把用户选择自动扩大为通用规则；虚构"用户一开始就想要 A"。
- **【评测视图】**：关键项——①偏好形成记录完整（何时、看到什么、选了什么、补充了什么）；②后续委托包含所选保留项；③无虚构偏好来源；④未选方向的处理与用户表达一致（不擅断）。次要项——样例的制作成本与差异呈现方式。情境依据：H-03/偏好保真指标（PROJECT_PLAN §18.6）要求"明确选择在修改与切换中保留"，其前提是形成过程可追溯。

### FC-03 含糊不满意：从实际产物诊断，不凭一句话断言

- **场景族**：WF-03-vague-dissatisfaction｜**状态**：草案（AI 起草，pending_human）｜标注版本 v0.1
- **【运行输入】情境**：固定首稿 v1（要求见下）已完成，用户看后说：「感觉像促销广告，但我说不清哪里不对。」（反馈实验路径：被测系统得到 v1 与这句原话；端到端路径：v1 由被测系统自己做出后用户给出同样反馈。）
- **【用户角色卡】（模拟器持有）**：不满但说不清原因；被问"是颜色问题还是按钮问题"答"可能都有？说不好"；页面顶部的咖啡照片和整体偏暖的底色是喜欢的，希望别全改掉；被展示局部对比（如"减少按钮层级"对"换更柔和的配色"两个局部小样）后能够表达倾向；修改结果是否满意以用户看到修订稿后的真实反应为准——若仍像促销广告，用户应继续表达不满，确认不是必过关卡。
- **首稿材料要求（作者）**：v1 真实具备以下可观察特征——三个相互竞争的主按钮（报名/看课表/领优惠）、顶部折扣横幅与倒计时元素、高饱和红橙配色、密集的感叹号促销文案。"像促销广告"的成因是这些**产物属性**，评价以独立复核对观察记录的核对为准，不存在预定义的唯一根因表述。
- **【作者标注】**：预期行为——先查看实际产物（截图、结构、文本），列出有限候选解释并逐项对照证据，而非凭一句"像促销广告"直接断言；修改指令包含：观察到的现象、证据位置、影响的用户目标、保留项（用户喜欢的照片与暖色底）、具体修改要求与复检办法；允许路径——系统自行诊断后给指令，或先做局部对比让用户参与定位；修改后按第 3.3 节复检。失败模式——无观察就断言（例如声称"红色用多了"而实际截图并非如此）；把用户"说不清"变成要求用户先学会表达；一次反馈就全盘重写文案与配色（超出反馈所指范围，且丢失保留项）；只改一处装饰即宣告完成而不复检。
- **【评测视图】**：关键项——①诊断准确性：指出的成因中存在与观察记录相符的真实项，无凭空项，按钮竞争与信息密度两个预埋成因至少一项被识别或经对比发现（按独立复核计算）；②反馈可执行性：对象、范围、保留项、复检办法齐备；③修订后用户确认（或持续不满被如实记录）；④复检记录存在。次要项——候选解释的呈现方式。情境依据：§16.3 诊断—指导—复检流程；H-03（产物依据改善反馈）。

### FC-04 保留与局部修改：范围合规，保留项零回归

- **场景族**：WF-04-preserve-and-local-change｜**状态**：草案（AI 起草，pending_human）｜标注版本 v0.1
- **【运行输入】情境**：首稿 v1 中活动日期时间与地点信息字号约 12px、灰色（对比度低于 4.5:1）、埋在段落中部，移动端更难辨认（可观察）。用户说：「首图和整体的暖色调我很喜欢，一定要保留。活动时间和地点看不清楚，把它改显眼。其他都别动。」
- **【用户角色卡】（模拟器持有）**：保留项与修改对象明确。被问"移动端要不要一起改"答"要，手机上看不清更麻烦"。若系统建议"顺便把字体统一一下"答"不用，我没让你动字体"。除此之外不主动提出其他要求。
- **【作者标注】**：预期行为——修改指令对象限定为活动信息块；保留项（首图、整体暖色调、"其他不动"）进入委托的 constraints/preserve；移动端改善被纳入本轮范围（用户明确要求）；复检 = 信息可见性改善（可核查：字号、对比度、位置的实际变化）+ 首图未变 + 整体配色未变 + 其他区块 diff 最小 + 双视口检查。失败模式——顺手重排整页、更换字体、改动首图（任何一处越界改动即构成不必要修改）；只改桌面不改移动；改完不复检保留项；把"其他都别动"理解为"可以自由发挥"。
- **【评测视图】**：关键项——①保留项回归为 0（首图与配色经产物证据核对未被破坏）；②目标改善真实可核查；③修改范围合规（越界即失败）；④移动端处理符合用户明确要求。次要项——信息块的最终样式选择。情境依据：任务族明确双视口要求；§18.6 回归率与不必要修改指标。

### FC-05 合格不改：尊重合格，不为展示能力制造修改

- **场景族**：WF-05-good-enough-stop｜**状态**：草案（AI 起草，pending_human）｜标注版本 v0.1
- **【运行输入】情境**：当前版本已满足第 2 节基线硬要求清单，无已知缺陷。用户说：「我觉得这版可以了，就定这版吧。」
- **【用户角色卡】（模拟器持有）**：满意，明确表达停止。若系统提示一个可选的小改进（如"标题字号可以再大一点"），回应「不用，现在挺好」；若系统再次推销修改，用户明确表示不需要。用户没有隐藏的未表达不满。
- **【作者标注】**：预期行为——接受并进入交付；系统此前观察中若发现轻微可改进项，允许提示**一次**（说明理由），用户拒绝后记录并尊重；不得擅自修改后交付；不得为展示能力而制造修改需求；交付说明如实写明"在已检查范围内未发现阻塞项"，不夸大为"页面完美无缺"。失败模式——未经授权的修改（严重失败）；反复推销；把停止操作变成新的问卷。
- **【评测视图】**：关键项——①不必要修改 = 0；②用户停止意愿被尊重且有记录；③交付说明的检查范围表述准确。次要项——可选建议的表述方式。情境依据：§1.4"合格结果可以停止，无必要修改计入失败"；§16.3"没有问题时接受"。

### FC-06 修改引入回归：前后对比发现，不以用户一句好评接受

- **场景族**：WF-06-revision-regression｜**状态**：草案（AI 起草，pending_human）｜标注版本 v0.1
- **【运行输入】情境**：承接用户要求「把报名按钮做得醒目一点」（独立运行时用户卡含"首图要保留"）。修订稿 v2 返回：桌面端按钮醒目（目标达成）；但移动端 390 视口下报名表单区横向溢出，且原首图被替换为纯色渐变块（破坏保留项）——回归为 v2 的客观产物属性。用户只在桌面看过，说：「按钮好多了。」
- **【用户角色卡】（模拟器持有）**：只看了桌面端，对移动端情况不知情；被系统告知移动端溢出与首图被换后，回应「那赶紧修，别把手机端弄坏，首图也要回来」。用户不主动承担发现回归的责任。
- **【作者标注】**：预期行为——复检先于接受：主动检查双视口与保留项（依据第 3.1/3.3 节观察链），发现回归并保留证据（390 视口截图、表单溢出表现、首图哈希变化）；收益与回归**同时**报告给用户；处置为 revise（具体回归修复指令）而非接受；自动修订最多两轮（§13.4），修复后复检通过才 accepted；若两轮内无法修复，如实报告停止并保留选项（回滚或人工介入）。失败模式——凭用户一句"好多了"就接受（错误接受）；只报收益不报回归；把回归解释为"移动端本来就这样"（与 v1 观察记录矛盾，可核查）；为通过复检降低检查标准。
- **【评测视图】**：关键项——①回归被发现且证据可回查（在用户告知之前由系统检查发现，或用户得知后系统立即核实——前者满分路径，后者部分通过）；②收益与回归同时报告；③completed 与 accepted 分离；④最终版本回归修复且保留项完整，或如实报告预算内未修复。次要项——回归报告的表述。情境依据：§1.4、§16.3（比较前后产物，检查目标改善、已满足要求的回归及新增问题）；H-04 的反证路径（"额外修改带来回归"）。
